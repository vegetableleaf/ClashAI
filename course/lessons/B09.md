## Why this matters for ClashBot

An Icebow decision involves several related values: a card's identity, its cost, a unit's remaining health, and the options controlling a decision. Dictionaries can hold those values. Classes provide another way to keep related data and operations together.

The real file `pipeline/decision_options.py` defines `DecisionOptions`, a record of choices used when interpreting model outputs. Reading its declaration becomes much easier once you understand construction, attributes, and defaults. You do not need to understand the neural network behind those outputs yet.

The tiny Card, Unit, and Tower examples below are teaching models. They are not replacements for RoyaleSim or crforge. Those engines contain many more rules. The same programming ideas also appear in imitation-learning and reinforcement-learning code, where objects group model settings and state.

## 1. From separate variables to one object

A **class** describes a kind of object. An **object**, also called an **instance** of its class, holds particular values and can provide operations that use them. A **method** is a function defined on a class and normally called through an object.

Without a class, you might keep `card_name` and `card_cost` in separate variables. With several cards, it becomes easy to pair the wrong name with the wrong cost. A dictionary already helps. A class adds a named structure and a place for related methods.

```python
class Card:
    def __init__(self, name, cost):
        self.name = name
        self.cost = cost

xbow = Card("Xbow", 6)
print(xbow.name)
print(xbow.cost)
```

It prints `Xbow` and `6`. The call `Card(...)` constructs an instance. Python then uses `__init__` to initialise its contents. An **attribute** is a named value attached to an object, such as `xbow.cost`. The dot selects that attribute.

The values in these examples are simplified teaching inputs. A constructed object does not look up current game tables automatically. If you pass the wrong cost, the object will store the wrong cost unless you explicitly validate or replace that input.

## 2. Understand self

The parameter `self` refers to the instance whose method is executing. Python supplies it when you call a method through an object. It is an ordinary parameter name by convention, but using that convention makes code understandable to other Python readers.

In `self.cost = cost`, the left side is an attribute on the object. The right side is the argument supplied to `__init__`. They have the same spelling after the dot, but they play different roles. After the constructor finishes, the attribute remains available on the object.

```python
class Card:
    def __init__(self, name, cost):
        self.name = name
        self.cost = cost

a = Card("Xbow", 6)
b = Card("Skeletons", 1)
print(a.cost, b.cost)
```

It prints `6 1`. Each instance has its own attributes. Changing `a.cost` would not automatically change `b.cost`. This separation is essential when two units of the same type have different remaining health during a simulated match.

Do not omit `self` from a method definition and then wonder why Python reports too many arguments. A call such as `card.can_afford(5)` supplies both the card instance and the explicit value five to the method.

## 3. Put a calculation next to its data

A method can read attributes without changing them. Here the method answers whether this particular card fits a supplied elixir budget:

```python
class Card:
    def __init__(self, name, cost):
        self.name = name
        self.cost = cost

    def can_afford(self, elixir):
        return self.cost <= elixir

card = Card("Xbow", 6)
print(card.can_afford(5))
print(card.can_afford(6))
```

It prints `False` and `True`. The method returns a boolean, just like a free-standing function from B05. A class does not introduce a different kind of arithmetic. It provides a way to associate the calculation with the object whose data it uses.

This method checks only cost against a number. Actual play availability may also involve hand position, timing, or other constraints. Naming the exact question prevents a small teaching helper from being mistaken for the full live decision rule.

## 4. Model changing health

**State** means the values that describe an object at a particular moment. A unit's health changes when it takes damage. A **mutation** is a change to an existing object rather than creation of a separate result.

```python
class Unit:
    def __init__(self, hp):
        self.hp = hp

    def take_damage(self, amount):
        self.hp = max(0, self.hp - amount)

unit = Unit(100)
unit.take_damage(30)
print(unit.hp)
unit.take_damage(100)
print(unit.hp)
```

It prints `70` and `0`. The built-in `max` returns the larger value. **Clamping** means keeping a value within a chosen limit; here zero is the lower limit. The method assumes nonnegative damage. Negative damage would increase health, so a broader implementation would need an explicit input rule.

Notice that `take_damage` has no explicit return statement. It therefore returns `None`. Its result is the changed attribute. Writing `unit = unit.take_damage(30)` would replace your reference to the unit with `None`, which is almost certainly not what you intended.

## 5. Distinguish an object from a reference

A **reference** is a way a variable refers to an object. Assigning one object variable to another does not automatically make a copy. Both names can refer to the same instance.

```python
class Unit:
    def __init__(self, hp):
        self.hp = hp

unit = Unit(100)
target = unit
target.hp = 60
print(unit.hp)
print(target is unit)
```

It prints `60` and `True`. There is one instance and two names referring to it. This matters when a tower stores a target. Damage through the target reference should affect the unit on the board, not an unrelated copy of its old health.

By contrast, `Unit(100)` called twice produces two instances. Equal starting health does not make them the same unit. This distinction becomes important when reading simulator state and later when studying independent replay states. For now, practise drawing one box per constructed object and arrows from variable names to boxes.

## 6. Let one object use another

**Composition** means building behaviour by having objects use other objects. Our tower receives a target object and calls its damage method. It does not need to duplicate the clamping rule.

```python
class Unit:
    def __init__(self, hp):
        self.hp = hp

    def take_damage(self, amount):
        self.hp = max(0, self.hp - amount)

class Tower:
    def __init__(self, damage):
        self.damage = damage

    def shoot(self, target):
        target.take_damage(self.damage)

target = Unit(100)
tower = Tower(20)
tower.shoot(target)
print(target.hp)
```

It prints `80`. `self` inside `Tower.shoot` is the tower, while `target` refers to the unit. When `target.take_damage` runs, its own `self` refers to that unit. Follow the call carefully: the same conventional parameter name does not mean every method operates on the same object.

There is no range, cooldown, targeting priority, or projectile travel in this example. A **cooldown** is a waiting period between actions. We name those missing behaviours to define the model's boundary. The exercise verifies object interaction, not accurate Clash Royale combat.

## 7. Use a dataclass for records

A **dataclass** is a class for which Python can generate common record behaviour, including an initializer and a readable representation. A **decorator** is a callable applied using an `@` line above a definition to adjust or augment it. You can use the dataclass decorator without writing decorators yourself.

```python
from dataclasses import dataclass

@dataclass
class Card:
    name: str
    cost: int

card = Card("Xbow", 6)
print(card)
print(card.cost)
```

It prints `Card(name='Xbow', cost=6)` and `6`. The statements `name: str` and `cost: int` are **type annotations**, notes describing intended value types. The decorator uses the declared fields to build methods. Ordinary Python annotations do not automatically reject every incorrectly typed value.

A **default** supplies a value when a caller omits an argument. Defaults make large option records easier to construct, but they also create behaviour you need to understand before changing an experiment.

```python
from dataclasses import dataclass

@dataclass
class Options:
    card_choice: str = "argmax"
    card_ratio: float = 0.7

print(Options().card_ratio)
print(Options(card_ratio=0.5).card_ratio)
```

It prints `0.7` and `0.5`. **Argmax** means choosing the position of the largest score. Here it is only a string naming an option. The record does not implement that choice merely by storing the word.

## 8. Freeze a configuration record

An **immutable** value cannot be changed in the relevant way after creation. A dataclass with `frozen=True` prevents ordinary assignment to its fields after construction. This can make experimental settings easier to reason about.

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class Options:
    card_ratio: float = 0.7

options = Options()
print(options.card_ratio)
```

It prints `0.7`. Trying to assign `options.card_ratio = 0.2` afterwards raises `FrozenInstanceError`. Constructing `Options(card_ratio=0.2)` is allowed because that creates a new record rather than modifying an existing one.

Frozen fields do not automatically make every object nested inside a record immutable. A list stored in a frozen record may still have mutable contents. Today's options use simple numbers and strings, so the distinction does not complicate the exercises, but it prevents overgeneralising the guarantee.

The excerpt prints nothing; it declares the start of a class. Line 1 asks for generated dataclass behaviour and frozen fields. Line 2 names the class. Line 3 declares a string field with its default. You can now read the structure without guessing the advanced decision mathematics. The full file validates option values and contains more fields. A six-line declaration does not establish every allowed combination or the setting used by a particular live run. A constructor default is source-level behaviour, while the actual run configuration is runtime evidence.

This line prints nothing. It brings the decorator and a helper for constructing modified copies into the module's namespace. B08's import vocabulary and this lesson's object vocabulary now explain the shape of the record together.

## Common mistakes

- Forgetting `self` in a method definition.
- Assigning only a local variable instead of `self.hp`.
- Assuming two variable names always mean two separate instances.
- Assigning the `None` return from a mutating method back to the object variable.
- Assuming annotations validate all inputs automatically.
- Treating a simplified tower object as a complete simulator.
