# G02 - Fine-tuning and distribution shift

**Time:** about 4 hours ? **You will be able to:** identify population shift, split live data chronologically, and fine-tune without hiding regressions.

## Why this matters for ClashBot

An opponent model trained on general human replays may see different behaviour when facing ClashBot's Icebow deck. Live opponents respond to this bot's actual X-Bow placements and timing. The source `scratchpad/gauntlet/L74/plan1026/opp/live_rows/LIVEROWS.md` documents converting those observations into opponent-seat training rows.

**Distribution shift** means the statistical pattern of data changes between the data used to fit a model and the data where it is evaluated or used. It can involve deck mix, player skill, game mode, observation quality, or how humans react to the bot. The model's parameters may be unchanged while its measured accuracy changes.

**Fine-tuning** means continuing training from already learned parameters on a new dataset or objective. The project notes compare a live-adapted model with its starting model. This lesson teaches how to make that comparison interpretable, using small local examples.

## 1. Name the source and target populations

The **source population** generated the original training data. The **target population** is the one on which performance now matters. A source replay corpus may contain many decks and opponents, while a target live block contains people responding to a particular Icebow bot version.

Do not describe the change only as ?new data.? Specify what changed. Were there more hog decks? Did Ranked opponents replace ladder opponents? Did the reader begin recording a different set of visible actions? Did the bot itself become more aggressive?

```python
source = {"hog": 50, "bait": 50}
target = {"hog": 80, "bait": 20}
print(source["hog"]/sum(source.values()))
print(target["hog"]/sum(target.values()))
```

This prints `0.5` and `0.8`. A model's pooled score can change because the mixture changed, even if its within-group performance did not.

A **stratum** is one subgroup used for analysis, such as a deck archetype. An **archetype** groups decks with a similar broad plan. Compare both pooled and stratified metrics when those groups are meaningful and sufficiently large.

## 2. Separate composition changes from within-group changes

Suppose a model predicts one group well and another poorly. The overall score weights each group's score by its frequency. Changing frequencies changes the overall result.

```python
accuracy = {"hog": 0.8, "bait": 0.5}
source_mix = {"hog": 0.5, "bait": 0.5}
target_mix = {"hog": 0.8, "bait": 0.2}
source_score = sum(source_mix[g]*accuracy[g] for g in accuracy)
target_score = sum(target_mix[g]*accuracy[g] for g in accuracy)
print(round(source_score, 2), round(target_score, 2))
```

This prints `0.65 0.74`. The model did not improve; the target mixture contains more examples from the easier group. Reweighting can clarify this effect, but it cannot create observations for an entirely missing target group.

Record counts alongside rates. A dramatic change in a five-match subgroup is much less stable than the same change in thousands of independent matches. Decision rows within a match do not all provide independent evidence.

## 3. Align observations with the information available

A live screen reader sees an action after it becomes visible. A simulator may record the exact tick when an action is accepted. These timestamps represent different events.

**Observation delay** is the gap between an event and its recorded sighting. If a training input is taken after the labelled action, the row can leak its answer. If an input is taken too early, the model may be asked to predict a decision without the information the person actually had.

The live-row source describes subtracting a sighting delay, snapping frames to a grid, and reconstructing hand information. Those are measured processing choices, not perfect access to a human's internal state.

For the teaching exercises, assume rows already contain valid pre-action features. We do not reconstruct the live engine. But the real source reading should prompt a question for every field: observed directly, inferred by a rule, or missing?

A **self-check** compares a reconstructed quantity with a known reference on a subset where that reference exists. High agreement on the bot's own seat is useful evidence for the extraction pipeline. It does not prove the hidden opponent hand is always known.

## 4. Freeze chronological boundaries

A **chronological split** separates records using time order. It is useful when the target is future play rather than a random replay from the past. Choose boundaries before comparing model variants.

```python
rows = [{"tick": 10}, {"tick": 20}, {"tick": 30}]
train = [r for r in rows if r["tick"] < 20]
validation = [r for r in rows if 20 <= r["tick"] < 30]
test = [r for r in rows if r["tick"] >= 30]
print(len(train), len(validation), len(test))
```

This prints `1 1 1`. Real splits use match timestamps, not arbitrary decision ticks. The numeric example isolates boundary logic. Use half-open intervals: include the start, exclude the end. That prevents a boundary match from appearing twice.

A **sealed block** is held back until the evaluation plan reaches its final test step. Do not read it repeatedly while adjusting the fine-tune. Otherwise it becomes validation data, whatever the filename says.

The source's live row pipeline distinguishes training, a newest portion for validation, and a later calibration block. **Calibration** in these project notes names an evaluation/reference block; it is not necessarily a synonym for the untouched final test.

## 5. Continue from existing weights

Fine-tuning starts by copying or loading the original parameters into a compatible model. If you initialise a fresh model, you are training from scratch, even if you use the same architecture.

```python
import copy
import torch
from torch import nn
base = nn.Linear(2, 3)
adapted = copy.deepcopy(base)
print(all(torch.equal(a, b) for a, b in
          zip(base.parameters(), adapted.parameters())))
print(base is adapted)
```

This prints `True` and `False`. **Deep copying** creates an independent object with copied parameter values. Updating adapted should not mutate base. Keeping the baseline intact makes before/after evaluation possible.

Use an explicit update budget and a reasonable learning rate. A smaller learning rate is common for fine-tuning, but not a guarantee of better results. The right choice depends on the amount and quality of target data.

The exercise performs a bounded number of updates on a synthetic target set. Its test verifies that target loss falls and the original model remains unchanged. It does not establish a real live improvement.

## 6. Decide which parameters may change

**Freezing** a parameter means setting `requires_grad=False`, so autograd does not compute its training gradient. You can freeze a representation and update only an output layer when that matches the experiment's purpose.

```python
from torch import nn
model = nn.Sequential(nn.Linear(2, 4), nn.ReLU(), nn.Linear(4, 3))
for parameter in model[0].parameters():
    parameter.requires_grad = False
trainable = sum(p.numel() for p in model.parameters() if p.requires_grad)
print(trainable)
```

This prints `15`, the final layer's parameter count. Freezing changes the adaptation capacity. It is a design choice to record, not a universal recipe.

The exercises fine-tune all parameters of a one-layer model to avoid adding an unnecessary architectural choice. In a real comparison, changing the frozen layers, learning rate, and training mixture simultaneously would make the cause of an improvement hard to identify.

## 7. Monitor forgetting

**Catastrophic forgetting** is a substantial loss of earlier capabilities after training on new data. Even a small fine-tune can improve target loss while worsening source loss.

A **rehearsal mixture** includes some source examples during adaptation. The opponent README describes a live fine-tune mixed with HF examples. The purpose is to retain broader behaviour while adapting to current opponents; the appropriate ratio is an experimental choice.

```python
before = {"source": 0.9, "target": 1.2}
after = {"source": 1.0, "target": 0.8}
print(round(after["source"]-before["source"], 2))
print(round(after["target"]-before["target"], 2))
```

This prints `0.1` and `-0.4`. Because these are losses, positive source change is worse and negative target change is better. Reporting only the -0.4 would hide the trade-off.

A **guardrail** is a predeclared condition a candidate must satisfy alongside its main objective. For the teaching exercise, require a strict target-loss reduction and a source-loss increase no larger than a specified tolerance. This is a simple acceptance rule, not the project's full promotion policy.

## 8. Evaluate on the same rows

Before/after comparisons should score the same held-out records with compatible feature and decoding settings. If one model sees a different reader output or deck subset, the difference combines model and dataset changes.

For uncertainty, resample whole matches rather than individual rows when rows are correlated. This follows C06's grouped design. A large row count can make a naive interval look precise while the number of independent games remains small.

Fine-tuning results remain conditional on the chosen time block. Opponents may change again. A successful adaptation is a measured improvement on that reference period, not proof the model will remain calibrated forever.

## 9. Complete the evidence chain

The first exercise isolates chronological boundaries. The second measures group proportions so a changed population becomes visible. The third adapts a copied tiny model while preserving its baseline. The fourth applies an explicit source/target loss rule.

After those tasks, write one sentence identifying what was held fixed and one naming what changed. For example: the evaluation rows and baseline parameters were fixed; only the copied model's training on target examples changed. That sentence is often more informative than a long list of training settings.

For ClashBot, continue the chain beyond row-level prediction: a fine-tuned opponent may look more like the current humans yet still defend an X-Bow poorly in simulator matches. G03 explains why that is a separate test rather than a contradiction.

## Common mistakes

- Calling a changed opponent mixture a model improvement.
- Reading the sealed block during fine-tune selection.
- Reinitialising instead of continuing from baseline values.
- Mutating the baseline in place and losing the comparison.
- Reporting target improvement without source regression.
