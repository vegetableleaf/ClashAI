# H09 · Distributed training: actors, learners and throughput

**Time:** about 5 hours · **You will be able to:** calculate pipeline throughput, policy lag and useful data rate without confusing speed with learning progress.

## Why this matters for ClashBot

Simulating matches and updating a neural network are different kinds of work. crforge advances game state, while PyTorch evaluates and trains the policy. If one part waits unnecessarily for the other, a fast GPU can sit idle while an experiment progresses slowly.

`scratchpad/gauntlet/L74/plan1026/pilot/loop/LOOP_INT.md` records the fast-loop integration, correctness comparisons and measured timings. It includes both rollout-only and overall match rates. Those rates answer different questions and must not be substituted for one another.

This lesson uses arithmetic and small queue records to explain the design. It launches no processes and uses no remote machine. The aim is to understand a benchmark table before deciding whether a proposed optimization addresses its actual bottleneck.

## 1. Separate producing experience from learning

An **actor** runs a policy in an environment and records experience. A **learner** uses recorded experience to update model parameters. A **producer** manages the work that supplies such experience; in a particular implementation it may coordinate several simulated matches.

A **consumer** receives produced items. In this pipeline the learner consumes batches of trajectories. A **queue** is the buffer holding items between producer and consumer. These terms describe data flow rather than requiring a particular multiprocessing library.

```python
queue = []
queue.append({"policy_version": 4, "matches": 32})
batch = queue.pop(0)
print(batch["policy_version"], batch["matches"])
```

It prints `4 32`. This list is only a conceptual queue. We do not use it as a production concurrency implementation.

Each trajectory should identify the policy version that generated its actions. The learner needs old action probabilities as H04 explained. A record labelled with the newest version after collection would misrepresent its origin, even if the file was written later.

A complete data contract includes observations, actions, rewards, terminal markers and relevant policy metadata. Faster transport is useless if any of these change meaning between the reference and optimized paths.

## 2. Measure wall time and the bottleneck

**Wall time** is elapsed real time. **Throughput** is completed work per unit of wall time, such as matches per hour. **Latency** is the time one request takes from start to finish. High throughput does not necessarily mean low latency for one decision.

If 120 matches finish in 60 seconds, rollout throughput is 7,200 matches per hour.

```python
matches = 120
seconds = 60
rate = matches / seconds * 3600
print(rate)
```

It prints `7200.0`. The denominator must correspond to the work counted in the numerator. Using only the simulator's active time while counting an entire training update overstates overall throughput.

A **bottleneck** is the part that limits total progress. If collection takes 90 seconds and learning takes 120 seconds, speeding collection alone has diminishing benefit once learning dominates. Profiling means measuring where time is spent before selecting an optimization.

Separate startup from steady-state measurements. Loading a model or warming an execution path may make the first update unusual. Exclude it only under a declared rule, and still report the startup cost if it matters for short experiments.

## 3. Overlap changes the critical path

**Overlap** means doing different stages at the same time. In a sequential pipeline, collection plus learning plus overhead determines an update period. With ideal overlap, the slower of collection and learning dominates, plus overhead that cannot overlap.

```python
collect = 90
learn = 120
overhead = 10
sequential = collect + learn + overhead
overlapped = max(collect, learn) + overhead
print(sequential, overlapped)
```

It prints `220 130`. This is an idealized steady-state model, not a promise of a 130-second real update. Synchronization, shared GPU use, memory transfer and initialization can add costs.

The **critical path** is the chain of dependent work that determines completion time. A stage cannot start before its inputs exist. Overlap is possible only where dependencies allow it. Updating the model while actors use its weights requires a coherent snapshot or versioned inference service; partially updated weights would break the behaviour-policy record.

A **policy server** batches inference requests from actors. Batching can improve hardware efficiency but may add waiting time. In a live emulator, decision latency matters directly. In training, overall experience rate may matter more. The best batch size can therefore differ between the two settings.

## 4. Faster actors can produce staler data

**Policy lag** is the difference between the learner's current version and the version that generated a batch. A deeper queue can keep the learner busy, but it can also make collected data older. H04's decoupled PPO addresses part of this mismatch; it does not eliminate the need to measure it.

```python
current_version = 8
recorded_versions = [8, 7, 5]
lags = [current_version - old for old in recorded_versions]
print(lags)
```

It prints `[0, 1, 3]`. Version lag is not elapsed age in seconds. Store timestamps too if wall-clock freshness matters. A version can last a short or long time.

**Backpressure** means slowing or limiting production when the consumer cannot keep up. A bounded queue prevents unbounded memory growth and can limit staleness. Throwing away old data may also change the effective sampling distribution, so record what was discarded.

An update's useful data can be smaller than its collected data. KL stopping may end optimization before all planned minibatches are used. Multiplying rollout throughput by a rows-used fraction gives a rough diagnostic of consumption, but not a direct measure of learning value.

```python
raw_rate = 10000
used_fraction = 0.2
print(raw_rate * used_fraction)
```

It prints `2000.0`. Call this a rough used-data rate under the stated proportionality assumption. Do not call it 2,000 improved matches per hour: matches are samples, not units of improvement.

## 5. More samples per update can stop helping

A **critical batch size** is a practical scale beyond which adding more data to one update yields diminishing optimization benefit relative to its cost. It is not one universal constant for the repository. It depends on gradient noise, task, model, optimizer and hardware.

Increasing batch size can reduce gradient variance and reduce updates per hour. The final effect on learning progress must be measured. Compare held-out performance against wall time and compute, not only against update number.

```python
runs = [
    {"batch": 128, "updates_per_hour": 20},
    {"batch": 512, "updates_per_hour": 7},
]
for run in runs:
    print(run["batch"] * run["updates_per_hour"])
```

It prints `2560` and `3584`. The larger batch processes more matches per hour in this toy calculation. It still takes fewer parameter updates, and neither figure tells us which run learns more.

An optimization should first preserve semantics. Compare identical seeded jobs between the old and new collection paths: outcomes, recorded actions, memory state and log probabilities. Some floating-point differences need a declared tolerance; discrete actions should not be excused by a tolerance intended for numeric output.

Then measure the intended benefit. A report should separate correctness evidence, rollout speed, learner speed, total update period and evaluation gain. “GPU busy” is a utilization observation, not proof that the training system is efficient.

The LOOP-INT report also illustrates a concurrency defect: identifiers reused across matches could select the wrong memory body when several matches stopped together. More threads exposed a state-association problem. Performance work therefore needs identity checks at the match level, not just an aggregate win rate.

Rounded values need not reproduce exact ratios from already-rounded times.

A second excerpt states:

This line interprets that benchmark's observed bottleneck. It does not establish that every future configuration needs only five cores. Both excerpts are report text and print nothing. Reuse the measurement method, not an assumption that these historical rates remain current.

## Practice plan

The first exercise computes a rate with unit checks. The second compares sequential and ideal-overlap periods. The third summarizes recorded policy lags and rejects a batch from a future version, which indicates inconsistent metadata.

The fourth converts a compact benchmark row into rollout and overall rates. Its tests use synthetic numbers with exact relationships, not the report's rounded historical values. Real benchmark data changes, so hard-coding a measured rate would teach the wrong habit.

Write a final note identifying which metric would answer “Is collection faster?” and which would answer “Does the model improve faster?” The first needs rollout timing; the second needs held-out performance over wall time. Keeping those questions separate prevents a speed optimization from being reported as a learning breakthrough.

## Common mistakes

- Dividing full-update work by rollout-only time.
- Assuming max(stage times) is the exact real pipeline period.
- Relabelling old trajectories with the current policy version.
- Treating a busy GPU as proof of useful learning.
- Skipping semantic identity checks when changing concurrency.
