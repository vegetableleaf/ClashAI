# F11 - Model size and scaling curves

**Time:** about 3 hours ? **You will be able to:** count parameters and interpret ClashBot's held-out scaling curve without confusing size with playing strength.

## Why this matters for ClashBot

A larger ClashBot model might predict human card choices more accurately, but it also costs more to train and run. During live play on a phone emulator, decisions arrive under time pressure. During simulator training, the same model may be evaluated on many observations. These are different workloads.

The measured table in `scratchpad/gauntlet/L74/scale/v1/CURVE_V1.md` compares models from about 2.5 million to 20.8 million parameters. We will read its actual rows, distinguish seed variation from size effects, and write a small parser that does not depend on a fixed number of rows.

A **scaling curve** shows how an outcome changes as a resource such as model size increases. It is evidence under a particular dataset, training budget, and evaluation method. It is not a universal law that doubling a model improves Icebow's win rate.

## 1. What counts as model size?

A **parameter count** is the number of learned scalar values. A linear layer with a inputs and b outputs has a times b weights and b biases. Embedding tables contribute one parameter for every table entry.

```python
def linear_parameters(inputs, outputs):
    return inputs*outputs + outputs

print(linear_parameters(2, 3))
print(linear_parameters(128, 8))
```

This prints `9` and `1032`. The second example could represent a small output layer, but the full board model has many more components. Counting only its last head would badly underestimate total size.

PyTorch can count registered parameters directly. This avoids hand-counting every layer in a complicated architecture.

```python
from torch import nn
model = nn.Sequential(nn.Linear(2, 4), nn.ReLU(), nn.Linear(4, 3))
print(sum(p.numel() for p in model.parameters()))
```

This prints `27`: twelve in the first linear layer and fifteen in the second. ReLU has no trainable parameters. Changing its placement can alter the model's function without changing the count.

Parameter count is not the same as every byte needed during training. Gradients, optimiser states, and intermediate activations require memory too. F12 separates those quantities.

## 2. Choose the vertical axis carefully

The source table reports **held-out NLL**, negative log-likelihood on examples excluded from fitting. Lower is better for the stated prediction objective. It also reports component losses, top-one accuracy, and training time.

A total objective may combine several heads with particular weights. Do not reconstruct it by blindly adding every visible column. Read the experiment's definition. A table's card loss and cell loss describe different classification problems and need not have similar numerical scales.

```python
small_loss = 5.4401
large_loss = 5.2724
gain = small_loss-large_loss
print(round(gain, 4))
print(round(100*gain/small_loss, 2))
```

This prints `0.1677` and `3.08`. Those are an absolute NLL reduction and a relative reduction of about 3.08%. Neither is a gain of 3.08 percentage points in win rate.

**Percentage points** measure differences between percentages. A move from 60% to 63% accuracy is three percentage points, or a 5% relative increase. Always attach units to a claimed improvement.

## 3. Use comparable held-out groups

The source contains multiple tables: general HF held-out rows, pro rows, and Icebow-deck rows. **HF** here labels the project's human replay corpus; the file calls the first group `heldout_hf`. A **group** is a subset scored under a stated selection rule.

A model can improve on one group and plateau on another. The Icebow subset is closer to a particular deck context, but it may be smaller and noisier. The general corpus covers more variety. Neither should silently replace the other after seeing which result looks better.

Read the table heading before the numbers. Record the group name together with the model label. If you merge rows from several tables and choose the lowest NLL, you may be choosing the easiest dataset rather than the best model.

In the real-data exercise, stop parsing when the next heading begins. This boundary is part of the measurement contract. It prevents later tables with identical row labels from being mistaken for repeated seeds of the first experiment.

## 4. Seeds expose variation

A **training seed** controls random initialisation and other random choices during training. Two runs with the same architecture and data can end at different losses. The source includes two 11.10-million-parameter runs, labelled m10 s0 and m10 s1.

```python
losses = [5.3121, 5.3342]
mean = sum(losses)/len(losses)
gap = abs(losses[0]-losses[1])
print(round(mean, 5))
print(round(gap, 4))
```

This prints `5.32315` and `0.0221`. The mean is a convenient centre for these two runs. The absolute difference is a rough observed seed variation, not a confidence interval and not a reliable estimate of all possible training variability.

The source's step-gain table uses this absolute difference as a noise unit. A gain divided by that unit is a descriptive comparison. It is not a formal statistical significance test. With only two seeds at one size, we cannot assume the same noise distribution at every size.

If the noise unit is zero, report that the ratio is unavailable. Dividing by zero or declaring infinite certainty would misrepresent the evidence.

## 5. Compute marginal gains

A **marginal gain** is the improvement from one step to the next. The question is not merely whether the largest model has the lowest loss, but what additional improvement each added resource buys.

```python
points = [(2.53, 5.4401), (5.36, 5.3820), (11.10, 5.32315)]
for (p0, l0), (p1, l1) in zip(points, points[1:]):
    print(round((l0-l1)/(p1-p0), 4))
```

This prints `0.0205` and `0.0103`: NLL reduction per additional million parameters for these steps. The smaller second value suggests diminishing improvement per extra parameter in this comparison.

A curve flattening in one dataset is not proof that all larger models are pointless. More data, longer training, another architecture, or a different target population could alter it. Conversely, a smoothly falling training loss does not show that a larger model generalises better.

If you fit a curve, resist extrapolating far beyond the measured sizes. Four sizes and a repeated seed at one size cannot establish a broad asymptotic law. A descriptive plot is often more honest than an impressive-looking formula.

## 6. Training and held-out gaps

The **generalisation gap** here is held-out loss minus training loss under matching definitions. A larger positive gap means the model fits the training examples better than the held-out examples.

```python
training = 5.2003
held_out = 5.2724
print(round(held_out-training, 4))
```

This prints `0.0721`. The largest model in the first table has a wider gap than the smallest one, yet its held-out loss is lower. Both statements can be true. A growing gap alone does not decide which model is better for prediction.

Compare losses measured with compatible settings. Training-time dropout or data weighting can complicate a raw training-versus-evaluation comparison. A report should state whether both were recomputed under the same evaluation procedure.

Choosing a checkpoint using validation data is reasonable; repeatedly choosing architectures using a supposedly final test set turns that set into development data. F06's warning remains important even when the table has many decimal places.

## 7. Size is not latency

**Latency** is the elapsed time for one request. **Throughput** is the amount of work completed per unit time. A big batch can improve throughput while being unsuitable for a single urgent live decision.

```python
batch_size = 128
batch_seconds = 0.04
print(batch_size/batch_seconds)
print(batch_seconds*1000)
```

This prints `3200.0` examples per second and `40.0` milliseconds per batch. It does not mean a single observation takes 0.3125 milliseconds in the actual live loop. That division describes amortised work within the batch, not an independently measured single-request latency.

The source has a separate latency table. It records hardware and execution modes because parameter count alone cannot predict timing. Model loading, board preparation, decoding, and emulator communication may add latency outside the neural-network call.

A **Pareto trade-off** occurs when improving one objective worsens another, such as lower loss but higher latency. A model is **dominated** if another measured model is no worse on every chosen objective and strictly better on at least one. We need not implement a full Pareto analysis here; the concept explains why there may be several reasonable choices.

## 8. Read the real table with a narrow parser

Markdown tables are text. Split a row on the vertical-bar character, strip whitespace, and select known columns. Use the heading as an anchor rather than depending on a fixed line number.

```python
line = "| m2 | 2.53 | 160 x 4 | 5.4401 |"
cells = [part.strip() for part in line.strip().strip("|").split("|")]
print(cells[0], float(cells[1]), float(cells[3]))
```

This prints `m2 2.53 5.4401`. The architecture description stays text. The parameter and loss columns become numbers. Header and separator rows must be excluded before conversion.

Our parser intentionally supports this particular table format. It is not a general Markdown reader. If the file changes column meaning, a structural check should fail rather than silently reinterpret the data.

## 9. Write a bounded conclusion

A good conclusion identifies the group, the size range, the measured improvement, and the missing evidence. For example: the first table's held-out objective decreases across the listed sizes, while the repeated m10 runs differ by 0.0221 NLL. That supports a prediction-loss trend within this setup.

It does not establish a live win-rate increase, a universally optimal model size, or a deployment decision. Those require separate evaluations. Learning this distinction is useful throughout ClashBot: a model can imitate human cards better without creating a harder simulator opponent, and a stronger simulator policy may still face a live observation gap.

In the exercises, count parameters, parse the real table, summarise repeated seeds, and compute adjacent gains. Keep numbers attached to their definitions. The final answer to ?is bigger better?? should name the metric and cost rather than returning an unconditional yes.

## Common mistakes

- Calling an NLL reduction a win-rate gain.
- Combining rows from different held-out groups.
- Calling a two-seed difference a confidence interval.
- Counting only weights and forgetting biases.
- Choosing the best seed and concealing the others.
