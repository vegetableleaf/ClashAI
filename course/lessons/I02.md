# I02 · Keeping a research log: ledgers, STATUS files and restart points

**Time:** about 3 hours · **You will be able to:** write a structured experiment record that preserves evidence, ownership, and a safe restart point.

## Why this matters for ClashBot

ClashBot research spans simulator changes, opponent models, policy training and live execution. A teammate returning after a day needs to know which result belongs to which run, what finished, and what remains uncertain. A memorable headline is not enough to resume the work correctly.

`.foreman/ledger.md` assigns tasks and write sets. `scratchpad/gauntlet/L74/plan1026/STATUS.md` provides a dated handover. These documents show two complementary jobs: tracking ownership across work and summarizing a restart point.

The exercises create records in memory. They do not edit the real ledger, change process state or launch a restart command. The writing practice is about making evidence reviewable before anyone decides what operation is authorized.

## 1. Separate the record of events from the current summary

A **research log** records what was attempted, under what conditions, and what was observed. A **ledger** is an organized record of tasks or events. A **status summary** describes the current state as of a stated time.

A ledger can be append-oriented: add a new event rather than rewriting history. A status summary can change as work progresses, but it should point back to evidence. These roles prevent the latest narrative from erasing a failed attempt or an important correction.

```python
events = [
    {"time": "2026-10-29T10:00:00Z", "state": "started"},
    {"time": "2026-10-29T10:05:00Z", "state": "finished"},
]
print(events[-1]["state"])
```

It prints `finished`. The first event remains available. If the run failed instead, recording the failure would be useful evidence, not clutter to remove.

A **timestamp** identifies when an event occurred. Use a timezone-aware format so two machines' local clocks do not create ambiguous ordering. The examples use UTC with a trailing Z. A document's last-modified time is not always the time of the experiment it describes.

## 2. Give each run an identity and a question

A **run identifier** distinguishes one execution from another. A **checkpoint identifier** distinguishes one saved model state within that run. Names should carry enough context to avoid confusion, but structured metadata is more reliable than a long encoded filename.

```python
record = {
    "run": "toy_ppo_seed17",
    "update": 24,
    "question": "Does PPO beat the uniform policy in the toy duel?",
    "status": "evaluated",
}
print(record["run"], record["update"])
```

It prints `toy_ppo_seed17 24`. The run and update together identify the model state more precisely than “the latest model.”

Write the question before recording the answer. Otherwise a general training run can acquire a convenient story after its results are known. A question such as “Does a lower opponent anchor improve strength without increasing style distance?” specifies two outcomes to inspect.

The record should also identify the baseline, treatment and evaluation protocol. A treatment is the intended changed factor. If multiple settings changed, list them rather than presenting the run as a one-change experiment. An honest multi-change record is more useful than a misleading clean narrative.

## 3. Store counts before percentages

A percentage without its denominator is difficult to audit. Store wins and decisive games separately, then derive the displayed rate. Keep draws and unknown outcomes in their own fields.

```python
result = {"wins": 18, "losses": 12, "draws": 1, "unknown": 4}
decisive = result["wins"] + result["losses"]
rate = result["wins"] / decisive
print(f"{result['wins']}/{decisive} = {rate:.1%}")
```

It prints `18/30 = 60.0%`. The formatting displays a percentage, while the stored integers retain exact accounting. A rounded rate alone cannot reconstruct the original count.

An **evidence pointer** is a path or identifier locating the material that supports a claim. It should identify a specific source and, where useful, a line, run or record identifier. “See logs” is too vague when dozens of logs exist.

Do not copy whole raw records into a summary merely because they are available. Extract the fields needed for the research question. The course's match exercises read the named outcome file and return aggregate counts; that is enough for a denominator audit.

If a result is unavailable, write that explicitly. A failed evaluation process does not produce a zero-percent win rate. A missing output file is a missing measurement, not evidence about model strength.

## 4. Make a restart point operationally clear

A **restart point** states where work can safely resume. It includes the last completed unit, the next intended action, required inputs, known failures and any approval boundary. It should also say whether a process is known to be running, known to be stopped, or unverified.

These states are different. “No recent log output” does not establish that a process stopped. A stale status document does not establish that a machine is idle. The person resuming work must verify mutable runtime state before acting.

```python
restart = {
    "completed": "toy evaluation",
    "next": "review the interval and write limitations",
    "runtime": "no background process created by this exercise",
    "authority": "offline analysis only",
}
print(restart["next"])
```

It prints `review the interval and write limitations`. This is a complete next action for the course without any operational command.

A production handover may require exact commands, but copying an old command is not authorization to run it. Record the intended action separately from permission. If the source document is historical, preserve its date and do not transform its past-tense state into a current assertion.

For the learner's project, the safest restart point is usually simpler: identify the last passing milestone, the settings used and the next unverified result. There is no need to invent process details for a program that already ended.

## 5. Track ownership and corrections explicitly

A **write set** is the collection of files a task is allowed to change. Explicit write sets reduce accidental overlap in a shared repository. A task record should name its owner and its allowed outputs before implementation begins.

```python
task = {
    "owner": "course learner",
    "outputs": ["in-memory report"],
    "status": "needs review",
}
print(len(task["outputs"]), task["status"])
```

It prints `1 needs review`. The output description makes the task's scope visible. A reader should not have to infer file ownership from who last mentioned a filename.

A **correction** supersedes an earlier claim without pretending the earlier claim was never made. Record the original claim, the new evidence and the revised conclusion. If a percentage was computed with unknown outcomes in the denominator, correct both the number and the method.

A **registry** maps stable identifiers to artifacts and metadata. It can answer which checkpoint a label refers to, which parent produced it and which evaluation supports it. A registry is useful only if labels are not silently repointed without recording the change.

The log should distinguish measured results, plausible explanations and contradicted claims, which I03 examines in detail. Avoid compressing them into one sentence such as “The run failed because the critic is bad” when only the failure is observed.

Finally, record what did not run. A planned fresh evaluation is not a completed confirmation. A handover that lists both completed and pending evidence lets a teammate continue without repeating expensive work or accidentally skipping a required check.

## In the real project

The task table in `.foreman/ledger.md` begins:

```text
## Tasks (write sets disjoint)
| id | ticket | seat | write set | status |
|---|---|---|---|---|
```

Line one states that task outputs should not overlap. Line two names the fields needed for coordination. Line three is Markdown table syntax. This excerpt is structure, not evidence that every task in the document is currently active.

The handover file `scratchpad/gauntlet/L74/plan1026/STATUS.md` begins:

```text
# plan1026 STATUS -- start here (updated 2026-10-26 ~14:25 EDT, account 1 handing over)
```

The single line names the scope, gives an update time and identifies a handover. It is older than several documents examined in these lessons. Its timestamp is therefore important evidence about freshness; it must not be presented as a current runtime inventory.

Both excerpts print nothing. They show why task ownership and dated summaries belong in a research workflow even when the numerical analysis is correct.

## Practice plan

First validate a small run record for required fields. Then generate a summary from integer outcome counts, preserving unavailable rates. The third exercise appends an event without mutating the original list so the previous record remains inspectable.

The final exercise renders a restart note from a structured handover. Its output must include completed work, next work, evidence and authority. Use short complete sentences so a reader can understand it without opening this lesson.

For your P07 project, write a real note using your measured outcome rather than the lesson's illustrative numbers. Include one unresolved limitation and one concrete next analysis. That is enough to make a small project restartable without creating unnecessary process bureaucracy.

## Common mistakes

- Treating an old STATUS file as a live process inventory.
- Recording a percentage without wins and denominator.
- Replacing a contradicted claim without preserving the correction.
- Leaving ownership and allowed outputs implicit.
- Copying a restart action as though it granted permission to execute it.
