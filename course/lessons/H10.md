# H10 · From SIM to live: gates, trials and promotion

**Time:** about 4 hours · **You will be able to:** evaluate an offline promotion dossier and distinguish evidence of improvement from authority to deploy.

## Why this matters for ClashBot

A simulator win rate can rise while the bot still loses on the phone emulator. The simulator may have different mechanics, the opponents may be unrepresentative, or the reader and tap loop may execute decisions differently. Passing a simulator test addresses only part of that chain.

`scratchpad/gauntlet/L74/plan1026/PLAN.md` describes an evaluation ladder that requires more than a single aggregate score. It includes identity checks, incentive audits, subgroup requirements and a live stage started by the owner.

The syllabus mentions a 30-match safety trial and a 150-match block. The inspected plan instead specifies a 60-match block with alarms, then 300 matches. We teach both as examples of staged evidence and explicitly preserve the discrepancy. The course does not choose or execute a live trial.

## 1. A gate is a decision rule with evidence

A **gate** is a predeclared requirement that a candidate must satisfy before advancing to a later evaluation stage. A **candidate** is the model or configuration under consideration. A **parent** is the reference model from which it was derived or against which it is compared.

A gate needs a metric, threshold, dataset and comparison protocol. “Looks better” is not enough. A useful gate might require a confidence interval for a paired win-rate difference to lie entirely above zero, along with minimum subgroup performance.

```python
lower_bound = 0.01
required_minimum = 0.0
passes = lower_bound > required_minimum
print(passes)
```

It prints `True`. A lower bound exactly zero would fail this strict rule. The rule is about evidence of improvement under the declared test, not certainty that every future match will improve.

A failed gate blocks the candidate from advancing. It does not necessarily mean abandoning the underlying research goal. The plan's iterate loop calls for diagnosing the failing component, making a justified change and testing again.

## 2. Pair candidates and preserve the unit of comparison

A **paired comparison** evaluates parent and candidate under matched conditions, such as the same opponent, starting setup and random seed. For each pair, calculate candidate outcome minus parent outcome, then summarize those differences.

```python
parent = [1, 0, 1, 0]
candidate = [1, 1, 0, 1]
deltas = [c-p for p,c in zip(parent,candidate)]
print(deltas, sum(deltas)/len(deltas))
```

It prints `[0, 1, -1, 1] 0.25`. The average improvement is 25 percentage points in this tiny artificial set. Four pairs provide weak precision; the example demonstrates bookkeeping, not a useful promotion test.

A **pooled estimate** combines several groups according to a specified rule. Pooling counts weights large groups more heavily. Averaging subgroup rates weights groups equally. Predeclare which question the estimate answers and retain subgroup results.

Unknown outcomes cannot be assigned zero and treated as losses. For paired outcome analysis, a pair with an unavailable result on either side cannot supply a complete difference. Report incomplete pairs separately. Draws require an explicit scoring convention; the exercises use decisive 0/1 fixtures to avoid silently choosing one.

## 3. Confidence intervals need a denominator

Part C introduced confidence intervals. Here we use a **Wilson interval**, an interval for a binomial probability that behaves better near zero or one than the simplest normal approximation. It describes uncertainty in one win proportion under its sampling assumptions.

A Wilson interval for a single rate is not a paired-difference interval. To compare paired policies, use the paired differences and an appropriate paired uncertainty method. Confusing the two can waste the benefit of matching seeds.

```python
wins = 30
losses = 20
unknown = 7
rate = wins / (wins + losses)
print(rate, unknown)
```

It prints `0.6 7`. The seven unknown records remain visible and do not dilute the denominator to 57. Also report draws separately if present.

A small safety block can reveal crashes or severe execution failures but has limited statistical power for modest win-rate changes. A larger confirmation block improves precision, yet repeated inspection and stopping when results look best can bias conclusions. Predeclare the stopping rule and distinguish safety alarms from efficacy claims.

An **alarm** detects a condition requiring review, such as repeated execution failures. An **automatic revert** would restore an earlier configuration under a previously approved rule. In this course, we simulate such decisions as returned strings; no program changes live settings.

## 4. Stages answer different questions

An identity stage asks whether training and evaluation decode the same actions. An incentive audit asks whether the learning signal rewards the intended outcome. A simulator gate asks whether a candidate improves under controlled simulated conditions. A scenario test asks about important specific states.

A predicted-live interval is a forecast connecting simulator evidence to expected live performance. A live trial observes the deployed system, including reader, decision latency and tap execution. Each stage adds evidence about a different part of the chain.

```python
dossier = {"identity": True, "incentive": True, "sim": False}
ready_for_next_stage = all(dossier.values())
print(ready_for_next_stage)
```

It prints `False`. Two passes do not cancel one required failure. An unavailable check should also block advancement, not be treated as a pass because no failure was recorded.

The syllabus's 30/150 sequence is useful for discussing a short safety stage followed by a larger estimate. The inspected plan's 60/300 sequence is the concrete historical source we cite. Neither set of numbers is a universal statistical prescription. Required sample size depends on baseline rate, effect size, variance and decision costs.

The automatic-revert concept is likewise a design topic here. Do not infer an implemented revert mechanism merely from a syllabus phrase. A concrete operational claim needs the actual rule, implementation and test evidence.

## 5. Promotion requires both evidence and authority

**Promotion** means adopting a candidate for the next operational role, such as the live bot. An offline gate result is evidence for a decision. **Authorization** is permission from the responsible owner to perform that action. The two are separate inputs.

```python
evidence_passed = True
owner_authorized = False
decision = "eligible for review" if evidence_passed else "needs diagnosis"
can_operate = evidence_passed and owner_authorized
print(decision, can_operate)
```

It prints `eligible for review False`. The candidate can be ready for review without being authorized for live use. A course exercise should return a decision record, not operate the emulator.

A **promotion dossier** is the collection of evidence needed for review: candidate identity, parent identity, engine and table versions, evaluation design, counts, uncertainty, subgroup results and unresolved limitations. Include execution failures and unknown outcomes rather than leaving them out of the summary.

After promotion, monitoring remains necessary. Opponent populations, game versions and execution conditions change. A model selected under one environment can degrade under another. Monitoring should preserve the same outcome definitions so a falling rate is not merely a changed denominator.

A responsible conclusion may be narrow: “The candidate passed these simulator checks and is eligible for an owner-reviewed trial.” That sentence is useful because it distinguishes completed evidence from the next unperformed step. It does not weaken the measured result; it states exactly what the result supports.

## Practice plan

First classify a synthetic outcome list with wins, losses, draws and unknowns. Then implement Wilson bounds for observed decisive games, returning None when there are none. Test both extreme and balanced outcomes.

The third exercise applies a simplified simulator gate with a strict pooled lower bound and an inclusive subgroup bar. It is deliberately smaller than the real ladder and must be labelled as such. The fourth implements a pure safety-stage decision using configurable minimum sample size and a supplied alarm flag.

Use the final decision strings in a written mock dossier. Explain which result is measured, which next stage is proposed and who would authorize it. No exercise starts, stops or changes live play.

## Common mistakes

- Treating a simulator pass as permission to deploy.
- Substituting a single-rate interval for a paired-difference interval.
- Putting unknown records into the loss denominator.
- Treating absent checks as passed checks.
- Presenting the syllabus's trial sizes as the inspected plan's current values.
