# A03 - Text formats the project lives on: Markdown, JSON, JSONL, YAML, CSV

**Time:** about 3 hours - **You will be able to:** recognize five text formats and inspect structured experiment records.

## Why this matters for ClashBot

ClashBot uses several text formats because different tasks need different structures. A handoff needs readable explanation. A match record needs named measurements. A training configuration needs settings. A table needs consistent columns. Treating all of these as interchangeable text loses important information.

`scratchpad/gauntlet/L74/loss_review/matches.jsonl` records match-related operational measurements. `scratchpad/gauntlet/L74/plan1026/opp/learner/opp_learner_calib.yaml` describes an opponent-learning configuration. Reading them by eye is the first step toward later analysis of imitation learning and reinforcement learning.

A simulator result and a phone-emulator result can use the same format while measuring different things. The format tells you how to read the structure; it does not tell you whether the bot won, whether an experiment finished, or whether a model should be used live.

## 1. Separate content from its format

A **format** is a set of rules for organizing stored content. A **parser** is a program that reads those rules and turns text into values a program can use. A file may look almost correct to a person but fail to parse because of one missing quote or bracket.

A **field** is a named part of a structured record, such as `n_plays`. A **record** groups related values, often describing one event or item. A field's name is not always a complete definition. Before calculating a result, establish what each value measures and how missing information is represented.

A02 taught you to view lines. Today you learn what those lines mean structurally. We will still use Bash for exercises, so you do not need Python variables, loops, or file-reading code yet. B06 covers programmatic JSONL reading properly.

## 2. Markdown is text for people

**Markdown** is a plain-text notation for headings, emphasis, lists, links, and code blocks. A **renderer** turns that notation into a formatted page. The underlying file is still readable text. The course lessons themselves use Markdown.

One `#` followed by a space begins a main heading. Two begin a smaller heading. A pair of asterisks around text makes it bold when rendered. A dash followed by a space begins a bullet. Backticks mark code or literal names, so readers can distinguish a path from ordinary prose.

```bash
printf '# Icebow report\n\n- Source: simulator\n'
```

It prints a heading line, a blank line, and `- Source: simulator`. In a terminal you see the Markdown characters. A Markdown viewer would render a heading and a bullet. Printing the heading does not create a report file; these exercises only request output.

A Markdown table uses vertical bars to separate columns and a line of dashes beneath its header. Table layout helps readers compare rows, but Markdown does not automatically validate the numbers. A beautifully rendered table can still contain a mistaken claim.

A code block preserves spacing and signals an example or excerpt. Its language label helps display it but does not execute it. A document containing a Bash command is not itself a Bash script. Reading an example never requires running every command appearing in that document.

## 3. JSON stores named values

**JSON**, JavaScript Object Notation, is a structured text format. An **object** is a group of name/value pairs enclosed in braces. Names are double-quoted strings. A colon separates each name from its value. Commas separate pairs.

```bash
printf '{"card":"X-Bow","cost":6}\n'
```

It prints `{"card":"X-Bow","cost":6}`. Here `card` names a text value and `cost` names a numeric value. The single quotes belong to Bash; the double quotes are characters in the JSON output. Both kinds of quotation have a job, but at different layers.

A **string** is a text value. A **number** is a numeric value. JSON also supports the truth values `true` and `false`, and `null`, which represents an explicit lack of a value. These words are lowercase in JSON. Python uses different spellings, introduced in B02.

An **array** is an ordered sequence enclosed in square brackets. For example, `{"hand":["X-Bow","Tesla"]}` holds an array of two names. Objects use braces; arrays use brackets. You will use corresponding Python collections in B03, but you can recognize their text shapes already.

JSON requires double quotes around names and strings. A trailing comma after the final item is invalid. Standard JSON does not allow comments. These strict rules help different programs agree on the same content. Do not assume an editor's highlighting means a file is valid.

## 4. JSONL stores one JSON value per line

**JSONL**, also called JSON Lines, places one complete JSON value on each line. This project's match file uses objects as those values. There is no enclosing array around the entire file and no comma between adjacent lines.

```bash
printf '{"n_plays":2}\n{"n_plays":5}\n'
```

It prints two lines: `{"n_plays":2}` and `{"n_plays":5}`. Each is a separate JSON object. Together they are JSONL, not one ordinary JSON document. A standard JSON parser asked to parse both as a single value would encounter extra data.

This layout is useful for a growing record: a program can append another complete line. **Append** means add to the end. It also lets a reader process records one at a time. A program that stops while writing can leave an incomplete final record, so successful line counting does not prove successful parsing.

```bash
printf '{"n_plays":2}\n{"n_plays":5}\n' | wc -l
```

It prints `2`. You counted two newline-terminated records in this controlled example. You have not added the plays; that total would be seven. Distinguishing record count from a sum of a field is essential before analyzing the bot.

```bash
head -n 1 scratchpad/gauntlet/L74/loss_review/matches.jsonl
```

It prints the current first JSON object, with fields such as `file`, `n_states`, and `n_plays`. The full line can be long. Its values may change as the dataset changes, so exercises should check structure rather than memorize a count.

## 5. YAML describes settings

**YAML** is a structured text format often used for configuration. A **configuration** is a collection of settings determining how a program is meant to run. YAML commonly writes a name, a colon, a space, and a value on each line. Comments begin with `#` outside quoted strings.

```bash
printf 'action_delay_ticks: 26\nhero_abilities: true\n'
```

It prints two YAML settings on separate lines. The first is numeric. The second is truth-valued. These lines describe choices; printing them does not apply them to ClashBot.

**Indentation** means leading spaces. In YAML, indentation can describe nesting, where one group belongs inside another. Changing indentation can change meaning even when the words are unchanged. Use spaces consistently. Decorative alignment and structural indentation are not interchangeable.

Some YAML readers interpret words differently depending on the YAML version. Quoting intended text can remove ambiguity. For this lesson, recognize simple numeric and `true`/`false` values; later configuration lessons examine the actual parser's behavior. Never infer that a setting is active merely because it appears in a file.

## 6. CSV makes rows and columns explicit

**CSV**, comma-separated values, represents a table as lines of fields. A **header** names the columns. Each following row supplies values in the same order. A **delimiter** is the character separating fields; here it is a comma.

```bash
printf 'card,cost\nX-Bow,6\nTesla,4\n'
```

It prints three lines: a header followed by two data rows. `wc -l` would report three because it also counts the header. Calling that three cards would be off by one.

If a value contains a comma, CSV normally surrounds that field with double quotes. A quoted field can even contain a newline. Real CSV is therefore not always safely parsed by splitting each line at every comma. Later Python tools handle these rules; these small examples avoid embedded commas.

CSV text does not itself establish numeric types in the same explicit way as JSON. A program may read `6` as text before converting it to a number. Two visually similar tables can behave differently if one contains unexpected spaces or missing cells.

## In the real project

From `scratchpad/gauntlet/L74/plan1026/opp/learner/opp_learner_calib.yaml`:

```yaml
action_delay_ticks: 26
extrapolate_ticks: 26
hero_abilities: true
ability_policy: v2
heroiw_press: live
forms_mode: deck
```

This excerpt prints nothing. Line 1 gives a delay setting in ticks, discrete game steps. Line 2 gives an extrapolation setting, used when estimating a later state. Line 3 enables an ability-related option in this configuration. Line 4 names a policy version. Line 5 names a press mode. Line 6 names a forms mode. These are syntax-level observations, not proof of settings loaded by a current process.

The match file's complete first record is long, so inspect it with the bounded `head` command rather than copying a shortened fragment and pretending it is valid JSON. At inspection, it included `n_states`, `n_dec`, `n_plays`, and `has_end`. These describe operational measurements and whether an end was recorded. They are not automatically win/loss labels.

## Practice reading before calculating

Take the small two-record JSONL example and explain it without using a computer. There are two records, each with one named numeric field. Their values are two and five. The number of records is two, the sum of plays is seven, and the average number of plays is three and a half. Those are three different questions about the same text.

Now imagine one record has no `n_plays` field. Missing is not automatically zero. It could mean the measurement was unavailable. A later analysis must make that distinction explicit rather than silently inventing a value. This is why learning structure comes before calculating impressive statistics.

For the interactive tasks, keep quotation layers separate. First decide the exact output text. Then surround it with Bash's single quotes and add the newline escape. Finally run it and compare the output character by character. You are practicing both the format and a reliable way of producing it.

## Common mistakes

- Using single quotes inside JSON because Python sometimes allows them.
- Adding commas between JSONL records.
- Counting a CSV header as a game.
- Treating a YAML configuration as proof of a completed run.
- Confusing record count with the sum of a field.
