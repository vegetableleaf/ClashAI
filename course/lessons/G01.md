# G01 - Behaviour cloning from replays

**Time:** about 5 hours ? **You will be able to:** turn replay events into imitation examples, handle sampled waiting rows, and audit real match outcomes.

## Why this matters for ClashBot

ClashBot's opponent models learn from human replay data. A useful simulated opponent must turn a board observation into a plausible action, not merely know which eight cards belong to a deck. The opponent workflow in `scratchpad/gauntlet/L74/plan1026/opp/README.md` describes replay conversion, waiting rows, training, and held-out scoring.

**Behaviour cloning** is supervised learning that trains a policy to imitate observed actions. A **policy** maps available observations to action choices or their probabilities. Here the labels come from people. In reinforcement learning, introduced in Part H, a policy instead receives a learning signal based on rewards from interaction.

The real outcome audit uses `scratchpad/gauntlet/L74/loss_review/matches.jsonl`. That file can support a win/loss report but is not itself the ordered replay-state dataset used to train the full opponent. Keeping those data roles separate prevents invented training examples.

## 1. Identify observation and action

An **observation** is the information available at the decision time. An **action label** is the recorded choice the model is asked to predict. A training pair contains the observation before the action, together with that action.

For a teaching row, observation might include elixir and whether an enemy X-Bow is visible. Action might be one of three teaching card IDs. A real board observation contains much more information, including units, positions, towers, hand estimates, and history.

```python
event = {
    "before": {"elixir": 4, "enemy_xbow": True},
    "action": {"card": 1},
    "after": {"elixir": 0}
}
x = [event["before"]["elixir"]/10,
     float(event["before"]["enemy_xbow"])]
y = event["action"]["card"]
print(x, y)
```

This prints `[0.4, 1.0] 1`. The after-action elixir is deliberately excluded. It could reveal the card's cost and leak the answer. When reading extraction code, ask when every feature was observed, not merely whether its name sounds reasonable.

A **replay** is a record from which a sequence of game events can be reconstructed. The conversion from replay to model rows is a data-processing step with its own possible errors. Training cannot repair a systematically shifted action label.

## 2. Human actions are examples, not guaranteed optima

Behaviour cloning learns what recorded humans did under the represented conditions. It does not prove those actions were optimal. Different players can choose different sensible responses to the same visible threat.

Suppose two equally plausible cards are used half the time each. A probabilistic model assigning one half to each has an honest distribution, even though greedy top-one accuracy may be limited. Conversely, a model can achieve high accuracy by copying a common action while missing rare critical defences.

The **demonstration population** is the collection of people and situations generating the examples. ClashBot's notes distinguish a broad human replay corpus, called HF in the tables, from pro replay rows and from live opponents facing the current bot. These populations need not have the same deck mix, skill, timing, or strategic pressures.

Treat "human" as a data description, not one universal behaviour distribution. G02 studies what happens when the target population differs from training.

## 3. Keep waiting in the task

Many decision opportunities contain no card play. A **wait label** represents such an opportunity. If training includes only actual plays, it cannot directly learn how often to wait from those rows alone.

For a fixed-slot task, each time slot can have a play/no-play label and, when a play occurs, card and placement labels. **Conditional loss** means scoring a component only on rows where its target is defined. A no-play row has no ordinary card-placement target to invent.

```python
rows = [{"play": True, "card": 2},
        {"play": False, "card": None},
        {"play": True, "card": 1}]
card_labels = [row["card"] for row in rows if row["play"]]
print(card_labels)
```

This prints `[2, 1]`. Waiting remains part of the overall dataset even though it is excluded from this card-only label list. Do not mistake missing conditional labels for bad rows that must be dropped from every head.

Sampling fewer waiting rows can reduce storage and computation. But it changes the observed class balance unless the objective accounts for the sampling scheme.

## 4. Weight sampled rows

An **inclusion probability** is the probability that a row is retained. **Inverse-probability weighting** gives a retained row weight equal to one divided by that probability. A waiting row retained with probability one eighth gets weight eight.

```python
keep_probability = 1/8
weight = 1/keep_probability
print(weight)
```

This prints `8.0`. The project's opponent README explicitly describes retaining one eighth of no-play slots with weight eight. That statement motivates our exercise; it does not mean every dataset in ClashBot uses that sampling rule.

A simple weighted mean loss is sum(weight times loss) divided by sum(weights). This normalised estimator is a useful reconstruction of the full-data objective; with random sampling it is not an exact copy of the full dataset on every draw.

```python
losses = [0.2, 0.8]
weights = [1, 8]
weighted = sum(w*l for w,l in zip(weights,losses))/sum(weights)
print(round(weighted, 3))
```

This prints `0.733`. The retained waiting example contributes more because it represents more original slots. If you merely duplicate rows, you may reproduce a weighted objective in a simple case, but you also increase memory and can alter batch behaviour.

For conditional heads, use the correct valid-row mask and denominator. A card loss should not acquire an invented target for a waiting row just because that row carries a weight.

## 5. Split by the unit that creates dependence

Rows from one replay share players, decks, and a trajectory. Randomly splitting those rows can put nearly identical states on both sides of an evaluation. Split complete matches before expanding them into rows.

```python
rows = [{"match": "a", "label": 1},
        {"match": "a", "label": 2},
        {"match": "b", "label": 0}]
train_ids = {"a"}
train = [r for r in rows if r["match"] in train_ids]
test = [r for r in rows if r["match"] not in train_ids]
print(len(train), len(test))
```

This prints `2 1`. Both rows from match a stay together. The tiny example uses only two groups to illustrate the boundary; a real training workflow also needs validation and may need player or time separation.

If labels are unavailable or reconstructed with uncertainty, preserve that fact. A **quality mask** marks which targets meet a specified criterion. It should be built from documented evidence, not from whether a model happened to predict the label correctly.

## 6. Distinguish imitation metrics from game metrics

Card accuracy and NLL answer how well the model predicts recorded human choices on recorded observations. They do not establish how the model behaves after choosing its own actions. Once the model acts, its future observations can differ from the replay.

A strong simulator opponent is useful for training the Icebow learner, but high imitation accuracy alone does not prove it is strong. A realistic opponent can also be weaker or stronger depending on the target population. G03 evaluates complete trajectories; G04 evaluates style.

When reporting a result, attach the dataset group, split, model identity, and decoding settings. A percentage without its denominator and population is hard to interpret.

## 7. Clean real outcomes before computing rates

The loss-review JSONL file stores one JSON object per nonblank line. Its observed outcome field, derived, contains strings such as WIN, LOSS, and DRAW. Some records lack an outcome. An absent outcome is unknown, not a loss and not a win.

For this lesson, define **decisive win rate** as wins divided by wins plus losses. Report draws separately because they are known non-decisive outcomes. Report unknown separately because their outcome is unavailable. This makes the denominator explicit rather than silently choosing a convention.

```python
rows = [{"derived": "WIN"}, {"derived": "LOSS"},
        {}, {"derived": "DRAW"}]
wins = sum(r.get("derived") == "WIN" for r in rows)
losses = sum(r.get("derived") == "LOSS" for r in rows)
draws = sum(r.get("derived") == "DRAW" for r in rows)
unknown = len(rows)-wins-losses-draws
rate = wins/(wins+losses) if wins+losses else None
print(wins, losses, draws, unknown, rate)
```

This prints `1 1 1 1 0.5`. A value of None means no decisive result exists. Reporting 0% in that case would falsely claim evidence of losses.

Unknown entries may occur for reasons related to recording or match conditions. Excluding them from a win-rate denominator is necessary, but it does not prove the remaining records form an unbiased sample. Report their count so the reader can assess coverage.

## 8. Read the file without freezing today's counts

Use pathlib and json.loads from B06. Skip blank lines; parse each remaining line as one object. In the exercise, keep the loaded rows in memory and compute all totals from that same snapshot, so a growing file does not create inconsistent denominators.

```python
import json
sample = '{"derived":"WIN"}\n\n{"derived":"LOSS"}'
rows = [json.loads(line) for line in sample.splitlines() if line.strip()]
print(len(rows))
```

This prints `2`. The real-data exercise substitutes the verified repository path. Its assertions recompute consistency from the loaded records, not a hard-coded total.

Malformed JSON is a different problem from an unknown outcome. Do not silently catch every exception and count the line as a loss. A parser failure should identify a broken input contract; a missing result should be counted as unknown.

## 9. Review the four exercises as one workflow

First, build teaching features from pre-action state. Second, compute a weighted imitation loss. Third, partition rows by complete match IDs. Fourth, read and audit actual match outcomes. These tasks teach related evidence habits without claiming that the outcome file is an imitation dataset.

Before training on real replay rows, inspect a few examples by hand: what was visible, what action occurred, what time alignment was used, and which labels were valid? Then run structural checks at scale. A model can fit incorrectly constructed examples very well, so an impressive training curve is not a substitute for this audit.

## Common mistakes

- Using post-action values as pre-action features.
- Treating every human action as uniquely optimal.
- Dropping waiting without correcting its sampling effect.
- Splitting adjacent rows from one match across train and test.
- Counting missing outcomes as losses or silently including them in win-rate denominators.
