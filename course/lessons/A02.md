# A02 - The terminal: Git Bash and PowerShell basics

**Time:** about 4 hours - **You will be able to:** compose read-only terminal commands and explain their output and limits.

## Why this matters for ClashBot

The live ClashBot system runs through several programs. A supervisor can start another process and record when it exits. The file `scratchpad/gauntlet/L70/live/supervisor.log` gives a concrete place to practice reading that record without controlling the emulator.

The file `.foreman/ledger.md` records coordinated work. It is a text document, not an instruction to launch everything it mentions. Terminal reading skills let you answer focused questions: what does the first heading say, what did the last few lines record, and where does a particular name occur?

Those skills also support later comparisons between live Icebow play and simulator experiments in RoyaleSim or crforge. A learning result is only useful when you can find the relevant record and understand what your command actually selected.

## 1. Command, arguments, and options

A01 introduced the terminal and shell. A command has a name followed by **arguments**, pieces of information passed to it. An **option**, also called a **flag**, changes how a command behaves. In `head -n 3 file`, `head` is the name, `-n` requests a line count, `3` supplies that count, and `file` supplies the input path.

Spaces separate words in a shell command. Quoting keeps a sequence together. Use straight single quotes for literal text in our Bash examples. Curly quotation marks copied from formatted prose are not substitutes. Keep path spelling exact; do not add spaces around path separators.

```bash
printf 'Icebow observation\n'
```

It prints `Icebow observation`. The space belongs to the printed text because the quotes keep it within one argument. The `\n` marks the end of that output line. You learned this form in A01 and will reuse it for controlled practice data.

A **process** is a running program. A shell starts a process when you invoke a command. Most reading commands finish quickly. Their completion does not mean a different process, such as the bot, has stopped or restarted. Commands in this lesson inspect text and directories.

## 2. Navigate deliberately

`pwd` reports the working directory. `cd` changes it. `ls` lists names. These commands operate in the current shell session. The course starts each exercise in the repository root, so a directory change in one answer does not carry into the next answer.

```bash
cd pipeline
pwd
```

It prints a path ending in `/ClashBot/pipeline`. The first line prints nothing on success. The second line displays the new working directory. The directory change does not edit the files inside `pipeline`.

```bash
cd pipeline
cd ..
ls -d pipeline/
```

It prints `pipeline/`. Entering the folder and then its parent returns to the repo root. Each command is on a separate line and executes in order. If the first command reports an error, investigate that error rather than assuming later output proves the earlier command worked.

`ls -a` includes names beginning with a dot, often called **hidden names** on Unix-like systems. The `.foreman` folder uses that convention. "Hidden" is a display convention; it does not make a folder inaccessible. Prefer an exact path when you already know the item you need.

## 3. Read a bounded amount of text

`cat` prints the contents of a file. `head -n N` prints its first N lines. `tail -n N` prints its last N lines. A **line** is a sequence ending at a newline character. A very long line can wrap on screen without becoming several file lines.

```bash
head -n 1 .foreman/ledger.md
```

At the inspected snapshot this prints `# Foreman ledger -- plan1026 days 0-3 + Pillar 4 (run started 2026-10-27 04:00 EDT)`. This is a historical example; the file may change. The command always asks for its current first line, not that specific text.

Use `cat` only when the chosen file is short and appropriate to display. For large records, bound your view with `head` or `tail`. Reading a ten-line window is easier to reason about than flooding the terminal with many thousands of lines. A bounded window also makes your evidence claim more precise.

```bash
printf 'start\nobserve\nstop\n' | tail -n 2
```

It prints `observe` and then `stop`, each on its own line. The symbol between commands is explained next. Here you can first predict the final two lines of the three-line practice record.

## 4. Connect commands with a pipe

A **pipe**, written `|` in Bash, sends the first command's standard output to the next command's standard input. **Standard output** is the normal text output stream. **Standard input** is the incoming stream a command can read. A stream is a sequence of data passed along while programs run.

The command after the pipe can work on that incoming text without a filename argument. It does not need a saved intermediate file. The pipe itself does not save results on disk. Avoid confusing `|` with a path separator: these symbols have entirely different roles.

```bash
printf 'X-Bow\nTesla\nRocket\n' | head -n 2
```

It prints `X-Bow` followed by `Tesla`. First `printf` produces three lines. Then `head` selects the first two. Reading the pipeline left to right tells you what information is available at each step.

You can use several pipes, but begin with two commands. Make sure you understand the output of each before adding another. This is a general debugging habit: locate the first step where the result differs from your prediction, rather than changing the last command blindly.

## 5. Select text with grep

`grep` prints lines matching a pattern. For ordinary literal text, `grep -F` treats the pattern as fixed text rather than a special pattern language. We use that option so punctuation such as square brackets has its visible meaning.

```bash
printf '[sup] start\n[bot] observe\n[sup] exit\n' | grep -F '[sup]'
```

It prints `[sup] start` and `[sup] exit`. The middle line does not contain the exact text. Matching text is not the same as understanding the event: the word "exit" does not tell you why the process exited.

Add `-n` to show matching line numbers:

```bash
printf 'start\nobserve\nstop\n' | grep -n -F 'observe'
```

It prints `2:observe`. The number is a position in the selected input, not a time or a match identifier. If the input is already a shortened window, its line numbers refer to that window. Do not report them as original-file line numbers.

A search may find no lines. That means the chosen pattern was absent from the selected input. It does not prove an event never occurred elsewhere. Case, spelling, the chosen file, and the time window all limit what a search can establish.

## 6. Count what you actually selected

`wc -l` counts newline characters. For normal newline-terminated records this is the line count. It is not a count of wins unless every selected line really represents one win. Blank lines count too. A final line without a newline can make a displayed record count differ from `wc -l`.

```bash
printf 'start\nobserve\nstop\n' | wc -l
```

It prints `3`, possibly with surrounding spaces. Every line in this practice input ends in `\n`, so there are exactly three newline characters. That detail is part of why this is a clean counting example.

```bash
printf '[sup] start\n[bot] observe\n[sup] exit\n' | grep -F '[sup]' | wc -l
```

It prints `2`. You counted supervisor-tagged lines, not matches, restarts, or successful games. Naming the counted unit is essential when studying the project. A number without a definition can sound impressive while answering the wrong question.

## 7. PowerShell is a different shell

Windows also provides **PowerShell**, a shell with its own command syntax. Its common commands include `Get-Location` for the working directory, `Set-Location` for navigation, `Get-ChildItem` for listing, and `Get-Content` for reading text. These are **cmdlets**, PowerShell's named commands.

The PowerShell form `Get-Content .foreman/ledger.md -TotalCount 1` reads the first line, like the Bash `head` example. `Get-Content .foreman/ledger.md -Tail 10` reads the last ten. PowerShell pipelines can carry structured objects, values with named properties, instead of only text. E02 covers that properly.

The interactive exercises here use Git Bash. Do not paste PowerShell cmdlets into a Bash answer. Conversely, do not assume every Bash option works on a PowerShell command with a similar nickname. When a command fails unexpectedly, identify the shell before changing the path.

## In the real project

The beginning of `scratchpad/gauntlet/L70/live/supervisor.log` contains this two-line excerpt:

```text
[sup] start 1 Fri Oct  2 20:31:02 EDT 2026
[sup] exit 127 Fri Oct  2 20:40:51 EDT 2026:
```

This is recorded text and prints nothing by itself. The first line records a supervisor start with a count and date. The second records an exit value and date. **Exit status** is a number a process reports when it finishes. Zero conventionally means success; nonzero indicates a problem or special outcome. Bash commonly uses 127 when a command cannot be found, but this excerpt alone does not identify the missing command.

From `.foreman/ledger.md`:

```text
## Tasks (write sets disjoint)
| id | ticket | seat | write set | status |
```

The first line is a heading about tasks. The second names table columns. A write set is the group of paths assigned to a task. These lines explain the ledger's organization; they do not tell you that a particular task finished. The Markdown table notation is covered in A03.

## Common mistakes

- Counting matching log lines and calling them completed matches.
- Confusing wrapped display text with actual file lines.
- Reading only a log's beginning and calling it the latest event.
- Using PowerShell syntax in the Bash exercise runner.
- Treating no search results as proof about every file and time period.
