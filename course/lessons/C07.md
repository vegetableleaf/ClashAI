## 1. Turn an idea into a contract

An **experiment contract** is a written description of what will change, what will stay fixed, and how the result will be judged. **Pre-registration** means recording that contract before looking at evaluation outcomes. It can be a small dictionary for a toy experiment; it does not require a formal publication system. Name a concrete question, such as whether one timing change improves paired decisive wins against the same opponent on the same engine. Include exclusions, unknown-outcome handling, and the exact stopping rule. A contract that says only make the bot better cannot decide a result honestly.

```python
plan = {'change':'timing only', 'metric':'paired win difference',
        'games':40, 'stop':'after 40 planned pairs', 'unknown':'report separately'}
print(plan['change'])
print(plan['stop'])
```

**Output:** `timing only` and `after 40 planned pairs`.

The example is deliberately small and invented. It does not authorize a live run. It demonstrates how an ambiguous intention becomes reviewable. A complete production record would also identify both code versions, input data, engine build, tables, and seed identifiers.

## 2. One change and a control

A **confounder** is another difference that could explain the observed effect. If a candidate uses different game tables and a different policy, a changed win rate cannot be attributed solely to the policy. A control should match every intended fixed condition. Comparing configuration dictionaries is a useful mechanical check, though it cannot prove hidden runtime conditions match. In a controlled simulation, use the same initial states and opponent behavior where feasible. In live play, matching conditions is harder, so conclusions often need more qualification.

```python
base={'tables':'v1','seed':7,'timing':False}
new={'tables':'v1','seed':7,'timing':True}
changed=[name for name in set(base)|set(new) if base.get(name)!=new.get(name)]
print(sorted(changed))
```

**Output:** `['timing']`.

The set union includes names present on only one side. Using get here treats absent and None as equivalent, which may be wrong for configuration auditing. The exercise strengthens this with explicit membership checks. A default that changes when a field is absent can be as important as a changed numerical value.

## 3. Development versus fresh evidence

A **development set** is data you may inspect while choosing or repairing a method. A **fresh set** is reserved for an evaluation whose outcomes have not influenced that choice. **Overfitting** means adapting too closely to observed examples so performance does not generalize to new ones. It can happen in manual simulator debugging as well as neural-network training. Once FRESH2 informs a repair, it can still test regressions, but the repaired method needs another untouched block for independent evaluation. FRESH1 through FRESH8 are block labels, not guarantees of independence or certificates of success.

```python
dev={'m1','m2'}
fresh={'m3','m4'}
print(dev.isdisjoint(fresh))
inspected={'m3'}
print(sorted(fresh-inspected))
```

**Output:** `True` and `['m4']`.

isdisjoint checks that sets share no elements. A numerical non-overlap check is necessary but insufficient: two different identifiers might refer to the same battle, or choices might be informed by aggregate fresh scores. Record information flow, not just filenames. Reusing a fresh set after seeing it should be explicit.

## 4. Freeze inputs and metrics

To **freeze** an experiment is to record the exact inputs and decision procedure before scoring. A **fingerprint** is a compact identifier calculated from content, often using a hash function. B11 introduced hashes; here we use one to detect changes to a JSON contract. Sorting dictionary names makes serialization independent of insertion order. A **serialization** is a representation of an object as bytes or text. Freezing does not mean the experiment can never be repaired. It means repairs create a new version, and evidence from earlier versions remains labeled accurately.

```python
import json, hashlib
plan={'metric':'decisive_rate','n':40}
text=json.dumps(plan,sort_keys=True,separators=(',',':'))
fingerprint=hashlib.sha256(text.encode('utf-8')).hexdigest()
print(len(fingerprint))
print(text)
```

**Output:** `64` and `{"metric":"decisive_rate","n":40}`.

encode turns text into bytes; hexdigest displays the hash using hexadecimal characters. The separators remove optional spaces, creating a stable representation for these simple dictionaries. A hash does not prove the design is good, that it was recorded before scoring, or that the program actually used the recorded inputs.

## 5. Controls, stopping, and evidence labels

A **positive control** is a case expected to trigger detection; a deliberately wrong health value can check a replay comparator. A **negative control** should not trigger detection, such as an identical replay compared with itself. A **regression check** asks whether a change breaks behavior that previously worked. Keep these separate from evidence of generalization. Label a bounded observation **measured**, an explanation not yet tested **plausible**, and a claim conflicting with evidence **contradicted**. Stopping after a predeclared number of games is different from stopping as soon as a favorable score appears.

```python
def compare_hp(recorded, simulated):
    return recorded == simulated
print(compare_hp(100,100))
print(compare_hp(100,99))
labels={'same trace':'measured','all future matches exact':'plausible'}
print(labels['same trace'])
```

**Output:** `True`, `False`, and `measured`.

The second comparison is a planted one-health-point defect. A comparator that always returns True would pass the negative control but fail the positive one. The label plausible does not mean likely or approved; it marks a statement awaiting evidence. If a strict all-frames claim already has counterexamples, its correct label is contradicted.

### Practice 2: Reject overlapping sets

Write fresh_ok(dev,fresh,inspected) returning True only if fresh is nonempty and shares no identifiers with dev or inspected. Example: fresh={'b'},dev={'a'},inspected={} passes.

The function checks this narrow contract only. Distinct IDs for the same match would require a separate duplicate-detection step.

### Practice 3: Fingerprint a plan

Only the contract is fingerprinted here. A full experiment must also identify the actual inputs and executable versions.

### Practice 4: Freeze the stopping rule

Write should_stop(completed,planned) returning completed >= planned. Example: 39 of 40 is False, 40 of 40 is True. Ignore whether the current score looks good.

This simple exercise emphasizes that a stopping rule is executable. More sophisticated sequential methods exist, but they require a different predeclared statistical procedure.

### Practice 5: Plant a comparator defect

Write exact(recorded,simulated) comparing dictionaries with hp,x,y. All fields must match, including equality of dictionary contents. Example: a one-HP difference fails.

The planted checks prevent a vacuous always-pass implementation. D04 will extend this principle to multiple objects, timing, and observation gaps.

Before running a finished answer, trace a tiny input by hand. Record the values before the function runs, the value returned, and whether any input was changed. This separates a wrong calculation from a wrong assumption about the data. Next try a boundary case: an empty collection, zero elapsed time, a missing observation, or the smallest legal input for that function. Choose the case that actually belongs to its contract.

When a check fails, read the assertion message before changing the code. Recreate that input in isolation, print the intermediate quantities, and compare them with your hand calculation. Remove temporary debug prints when you understand the discrepancy. ## Common mistakes

- Changing several features and attributing the result to one.
- Tuning on a fresh failure and continuing to label that set untouched.
- Changing the pass threshold after seeing the score.
- Dropping failed or unknown outcomes from the accounting without explanation.
- Confusing a descriptive before/after comparison with a causal experiment.
