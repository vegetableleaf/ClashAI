# F12 - Making training fast: GPUs, memory and batch size

**Time:** about 5 hours ? **You will be able to:** estimate training memory, accumulate correctly weighted gradients, and evaluate speed claims.

## Why this matters for ClashBot

ClashBot training combines model computation with simulator work, data preparation, and evaluation. Making a matrix multiplication faster does not automatically make learning progress faster. A learner can wait for crforge matches, spend time loading rows, or use more memory than the GPU can hold.

`scratchpad/gauntlet/L74/plan1026/pilot/lrn/SCALE.md` records measured acceleration work, including micro-batches and a compile probe. We will study those mechanisms on CPU. The exercises need no GPU and do not change a running training job.

The syllabus mentions an arm D u3 out-of-memory crash as motivation. The excerpts used here document the general memory remedy rather than establishing that crash's particular cause. Keep that distinction: an error category suggests what to investigate; it does not identify which tensor or process caused a historical failure.

## 1. Separate the units of work

A **minibatch** is the group of training examples used for one optimiser update. A **micro-batch** is a smaller chunk processed as part of that update. An **effective batch size** counts all examples whose gradients contribute to one update.

```python
total = 10
micro = 4
sizes = [min(micro, total-start) for start in range(0, total, micro)]
print(sizes)
print(sum(sizes))
```

This prints `[4, 4, 2]` and `10`. The last chunk is smaller. Correctly handling it matters for both gradient weighting and reported losses.

Larger batches can use hardware more efficiently, but they also change the learning process if the number of examples per update changes. Processing one fixed minibatch in smaller chunks is a more controlled memory experiment than changing the effective batch size and learning rate together.

Rows from one match can be strongly correlated. Ten thousand decision rows do not necessarily provide the same information as ten thousand independent matches. When comparing training runs, record both row counts and match counts.

## 2. Estimate memory before allocating

**Memory usage** includes more than parameters. Training may store parameter values, gradients, optimiser state, inputs, and **activations**, intermediate values retained for backpropagation. Attention can create large intermediate arrays depending on sequence length and implementation.

```python
rows, items, width = 32, 20, 128
bytes_per_float = 4
activation_bytes = rows*items*width*bytes_per_float
print(activation_bytes)
print(activation_bytes/(1024**2))
```

This prints `327680` bytes and `0.3125` **MiB**, where one mebibyte is 1024 squared bytes. This counts one tensor only, not the entire model's peak memory.

For a simple float32 estimate, parameters plus gradients plus two Adam state arrays use roughly sixteen bytes per parameter. Actual implementations may need additional memory. Mixed precision, temporary workspaces, allocator caching, and saved activations change the total.

An **out-of-memory error**, abbreviated **OOM**, means a requested allocation cannot fit in available memory. It does not necessarily mean the model's saved weight file is too large. A batch-dependent activation can be the limiting allocation.

When diagnosing an OOM, record the failing operation, shapes, batch size, and memory already occupied. Reduce one factor and remeasure. Repeatedly retrying the same allocation without changing conditions is not an experiment.

## 3. Accumulate the same gradient in chunks

**Gradient accumulation** means adding gradients from several forward/backward passes before one optimiser step. PyTorch already accumulates into `.grad`; the challenge is to scale losses correctly and clear gradients at the right time.

Suppose the full objective is the mean loss over N rows. A micro-batch of n rows returns its own mean. Multiply that mean by n/N before backward. Summing these contributions recovers the full-batch mean gradient, apart from floating-point order effects, when the computation otherwise treats examples independently.

```python
sizes = [4, 4, 2]
means = [1.0, 3.0, 5.0]
weighted = sum(n*loss for n, loss in zip(sizes, means))/sum(sizes)
unweighted = sum(means)/len(means)
print(weighted, unweighted)
```

This prints `2.6 3.0`. Averaging chunk means equally overweights the final two rows. The same mistake in backward overweights their gradients.

```python
import torch
from torch import nn
torch.set_num_threads(1)
model = nn.Linear(1, 1)
x = torch.tensor([[0.0], [1.0], [2.0]])
target = 2*x
model.zero_grad()
for start in range(0, len(x), 2):
    xb = x[start:start+2]
    yb = target[start:start+2]
    loss = ((model(xb)-yb)**2).mean()
    (loss*len(xb)/len(x)).backward()
print(model.weight.grad.shape == model.weight.shape)
```

This prints `True`. No optimiser step occurs in the loop. Clear gradients once before the chunks, backpropagate each weighted loss, then call the optimiser once after all chunks.

The equivalence has assumptions. A layer depending on batch-wide statistics can behave differently on smaller chunks. Dropout consumes randomness differently. A masked multi-head loss may use a denominator based on valid labels, not all rows. Our exercise uses independent linear regression rows to make the equivalence check precise.

## 4. Avoid retaining unnecessary computation

Calling backward normally frees the saved computation needed for that pass. Appending live loss tensors to a long list can retain references and increase memory. For logging, append `loss.item()` instead when you only need a number.

Evaluation should use `model.eval()` and `torch.no_grad()`, as in F08. Keeping gradient recording on during a large evaluation wastes memory if no derivatives will be used. Moving every intermediate tensor to a new device also adds copies.

A smaller micro-batch reduces some activation memory, not every memory category. The parameter and Adam-state storage usually remain. If those dominate, splitting rows cannot solve the whole problem.

## 5. Precision changes arithmetic

**Numerical precision** describes how finely numbers are represented. Float32 is the default in our examples. **Mixed precision** uses different number formats for different operations. **TF32** is a GPU matrix-computation mode that uses reduced input precision with float32-style storage and accumulation behaviour.

These modes can improve speed on suitable hardware, but arithmetic changes can alter gradients or decisions. A close loss does not imply identical action choices near a tie. Measure the outputs relevant to the project rather than assuming a format change is harmless.

The source's acceleration study explicitly specifies float32 with TF32 off. That is a constraint of the recorded experiment. It is not a universal claim that other formats are always wrong. Our course examples stay on CPU and make no CUDA precision-setting changes.

For a reproducibility report, distinguish **determinism**, repeating the same result under specified conditions, from **numerical agreement**, two methods producing sufficiently close values. Different summation orders can agree closely without being bit-for-bit identical.

## 6. Compilation and graphs address different overheads

**Eager execution** runs operations as Python requests them. `torch.compile` attempts to transform model computation into a more efficient execution form. It may have an initial compilation cost, unsupported patterns, or numerical differences.

A **CUDA graph** records a sequence of GPU operations for replay with less launch overhead. It often needs stable shapes and careful handling of memory addresses. A graph is not a saved neural-network checkpoint; the two serve different purposes.

The source's compile probe measured faster encoder execution but also found gradient differences outside that experiment's identity requirement. Speed and correctness were checked separately. A speedup that fails the required numerical contract is not an accepted optimisation.

We do not call torch.compile or capture CUDA graphs in the exercises. Their startup cost and hardware requirements do not fit the course's short CPU execution budget. You can understand the experiment and calculate its implications without reproducing the GPU benchmark.

## 7. Measure end-to-end speed

**Wall-clock time** is ordinary elapsed time. For a complete training iteration, it may include waiting for simulator results, loading data, computing gradients, updating parameters, and saving records.

```python
simulation_seconds = 8.0
learner_seconds = 2.0
new_learner_seconds = 1.0
speedup = (simulation_seconds+learner_seconds)/(simulation_seconds+new_learner_seconds)
print(round(speedup, 3))
```

This prints `1.111`. Doubling learner speed gives only about 1.11 times end-to-end speed here because simulation dominates.

This relationship is often called **Amdahl's law**: if fraction f of time is accelerated by factor s, total speedup is `1 / ((1-f) + f/s)`. It assumes the rest of the work is unchanged and the fractions describe the workload being measured.

GPU timing needs extra care because operations can be asynchronous: the CPU may finish submitting work before the GPU finishes executing it. Proper GPU benchmarks synchronise at measurement boundaries and include warm-up runs. CPU exercises avoid that complication.

## 8. Learning progress is the final resource question

Examples per second, updates per hour, and improvement per hour are different quantities. A larger batch can increase examples per second while reducing useful updates within a fixed time. A faster simulator can produce more rows from an unrealistic opponent.

For ClashBot, record the prediction or policy metric along with compute cost. Keep the simulator, opponent configuration, and evaluation seeds comparable. A speed claim should not silently include a different learning task.

The exercises make four narrow checks: memory arithmetic, row-weighted reporting, gradient equivalence with an uneven final micro-batch, and end-to-end speedup. The gradient comparison is especially important. It compares two independent paths through the same objective rather than simply checking whether a training loop runs without error.

Before moving to P06, explain which quantities you would hold fixed when testing micro-batching. Keep initial weights, examples, objective, optimiser update count, and effective batch size fixed. Then compare gradients and final values within a stated tolerance. Only after that correctness check should speed and memory measurements influence your choice.

## Common mistakes

- Averaging unequal micro-batch means equally.
- Clearing gradients inside every micro-batch.
- Calling Adam.step once per chunk while claiming an unchanged update.
- Estimating peak training memory from the weight file alone.
- Reporting kernel speed as end-to-end learning speed.
