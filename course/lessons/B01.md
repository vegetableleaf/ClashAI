## Why this matters for ClashBot

Much of ClashBot's shared logic is Python code in `pipeline/`. That code helps connect game observations to decisions and learning. Before studying those decisions, you need to understand what it means to execute Python and why the chosen interpreter matters.

The project has an environment at `icebow/.venv/`. The course uses its own environment at `course/.venv/`. They are separate locations with potentially different installed libraries. A successful command in one does not prove that the same program will run in the other.

Your first Python programs will print small Icebow messages and calculations. They will not control the phone emulator or run RoyaleSim or crforge. These tiny programs establish the execution model you will use later for imitation and reinforcement learning exercises.

## 1. Source code and an interpreter

**Python** is a programming language, a set of rules for expressing computations. **Source code** is the text written in that language. An **interpreter** is a program that reads and executes it. A **script** is a saved source file intended to be run, commonly ending in `.py`.

A terminal does not automatically know that every line you type is Python. Git Bash expects shell commands. Python expects Python statements. A **statement** is an instruction in the language. Confusing these two places is a common beginner problem because both display text and accept typed input.

```python
print("Icebow")
```

It prints `Icebow`. `print` is a built-in operation that writes output. The parentheses enclose what to print. The quotation marks create a string, the text value introduced in A03. They delimit the text but are not part of the output.

**Syntax** means the language's required arrangement of characters. Parentheses and quotation marks must match. Use straight quotes. Python does not understand curly quotation marks as string delimiters. The code is small enough that you can inspect every character before running it.

## 2. Read top to bottom

For these first programs, Python executes statements from top to bottom. Each `print` call normally ends its output with a newline. A **call** asks an operation to run. You will learn to define your own callable functions in B05; today you only use provided built-ins.

```python
print("Observe the arena")
print("Choose an Icebow card")
print("Record the decision")
```

It prints those three messages on three lines in the same order. This is a description of stages, not an implementation of an emulator reader or decision maker. Printing "Choose" does not choose an actual game action.

Change the order of the lines and predict the new output before running. This is a useful habit for every exercise: identify what each statement does, then trace the sequence. Do not rely on the visual layout of your editor alone; blank lines organize code but do not create extra printed output.

```python
print("simulator")

print("live emulator")
```

It prints two adjacent output lines, `simulator` and `live emulator`. The empty source line is not an empty print call. To print a blank line, use `print()` with nothing inside its parentheses.

## 3. Comments explain; they do not execute

A Python **comment** begins with `#` outside a string and continues to the end of the source line. Comments can explain a choice or mark work to do. A `# TODO` comment in an exercise means you must replace or extend the starter code; it does not perform the requested calculation.

```python
# This is a practice label, not a game command.
print("X-Bow practice")
```

It prints only `X-Bow practice`. Python ignores the comment during execution. Comments are useful for a reader but are not checked facts. A comment saying a value is six does not make code that prints five correct.

```python
print("# Icebow report")
```

It prints `# Icebow report`. The hash is inside quotes, so it belongs to the string. You saw that Markdown uses a leading hash for a heading; here Python simply outputs those characters. Different languages can give the same character different roles.

## 4. Calculate a small expression

An **expression** produces a value. You can give an expression to `print`. Python first evaluates it, then prints the result. We will cover types and arithmetic properly in B02; today we need just addition and subtraction.

```python
print(6 + 4)
print(10 - 6)
```

It prints `10` then `4`. The first line adds two numeric values. The second models ten elixir minus an X-Bow cost of six. These are toy calculations, not a claim about the emulator's measured state.

```python
print("6 + 4")
```

It prints the literal text `6 + 4`. Quotation marks change the interpretation: this is a string to display, not arithmetic to evaluate. Reading code carefully means noticing that difference before you look at its output.

A **built-in** is provided by Python itself. `print` is built in, so these exercises need no imported library. A **library** is reusable code made available to other programs. Later lessons introduce imports and packages; nothing in these first answers requires installing anything.

## 5. Running a saved script

Outside the course editor, a saved Python file is run by passing its path to a Python interpreter. In Git Bash, the course interpreter's repository-relative route is `course/.venv/Scripts/python.exe`. A filename after it would identify the script to execute.

To inspect which Python version that executable provides, use:

```bash
course/.venv/Scripts/python.exe --version
```

It prints a version line beginning `Python 3.13` in this course environment. The final patch number can differ. This is a Bash command invoking an executable, not Python source to paste into a Python exercise.

A **virtual environment**, usually shortened to **venv**, is a project-specific Python environment with its own interpreter entry points and installed packages. A **package** is a distributable collection of Python code and related resources. Different tasks can require different package versions.

Using the explicit interpreter path is enough to choose the course environment. **Activation** changes a shell's search setup so a short name such as `python` resolves to that environment. We do not need activation here because the full relative executable path is unambiguous.

## 6. Why environment choice matters

Suppose a script needs a numerical library installed in the course environment. Running it with another Python may fail even if the source file is unchanged. The source and the environment together determine what is available. This explains why "it works on my machine" is incomplete evidence.

The course provides Python 3.13 and several learning libraries. That does not mean every project script is appropriate to run there. Some depend on live devices, simulator installations, or project-specific settings. We will learn about those dependencies gradually rather than importing an entire operational program for a tiny demonstration.

The course's exercise runner writes your Python answer to a temporary `.py` file, adds checks after it, and runs it with the course interpreter. A **temporary file** is a file created for short-lived work and removed afterward. Its working directory is still the repo root, as in Part A.

## 7. Keep source input separate from program input

**Standard input** was introduced with Bash pipes in A02. It can carry data a program reads. Python can also be told to read its source from standard input. Using the same channel for source and later program data can be confusing and fragile.

For project launches, use saved scripts rather than piping source code into Python on standard input. A saved path makes the executed program easier to identify, inspect, and rerun. A pipe intended for input data then has a distinct role. The course runner follows the saved-script approach internally.

This rule does not mean a Python program can never read input. It means you should not blur the source of the program with the data it consumes. Later file-reading lessons use explicit data paths, making that distinction even clearer.

## In the real project

From `icebow/.venv/pyvenv.cfg`:

```text
include-system-site-packages = false
version = 3.13.14
```

These configuration lines print nothing. Line 1 says this environment is configured not to include the global package collection automatically. Line 2 records its Python version at inspection. This is evidence about the project environment, not a guarantee that every other environment has the same patch version.

From `pipeline/__init__.py`:

```python
"""Deck-agnostic observation pipeline shared by icebow and hogeq (S0 step 2, L63).

``BoardWarp`` from ``icebow/src/clashrl/actions.py`` lazily (the deck yaml names the src dir).

```

This excerpt prints nothing. Line 1 starts a **documentation string**, text stored in code to describe it. Line 2 is blank for readability. Line 3 describes deferred importing: bringing code into use later rather than immediately. Line 4 names the related source and configuration context. Line 5 closes the string. Imports are covered properly in B08; you are reading this passage as documentation today.

## Common mistakes

- Pasting a Bash launch command into Python source.
- Assuming a comment performs the TODO.
- Quoting arithmetic that should be calculated.
- Assuming all Python executables share installed packages.
- Thinking a printed action label controls the live game.
