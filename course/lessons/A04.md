# A04 - Git: history, commits, diffs and why we commit carefully

**Time:** about 4 hours - **You will be able to:** inspect history and differences without changing Git state.

## Why this matters for ClashBot

ClashBot has shared code, experiment records, and ongoing work from several contributors. A change helping one experiment can interfere with another. Git records selected changes, but using it carefully requires understanding which version of a file you are reading.

The syllabus points to `.foreman/scratch/loop_ops/safe_commit.sh`. It coordinates selected paths using a separate Git index. We will read its comments, not run it. Its name does not guarantee that invoking it is appropriate for a course exercise.

History helps explain which code an Icebow experiment used. It does not establish simulator quality or phone-emulator performance. A saved change and a measured improvement are separate pieces of evidence. This distinction matters throughout imitation and reinforcement learning.

## 1. Three places a change can live

A **version control system** records selected versions of files over time. **Git** is the system used here. A **commit** is a saved snapshot with identifying information and a message. A **commit identifier** labels that snapshot; Git commonly displays a shortened sequence of letters and digits.

The **working tree** is the set of files you currently see and edit. It can differ from saved history. The **index**, also called the **staging area**, holds changes selected for a future commit. A working-tree change is not automatically staged, and a staged change is not automatically committed.

Imagine correcting an experiment note. Saving it changes the working tree. Selecting it for a commit changes the index. Creating the commit adds a snapshot to history. These are three different operations. This lesson only inspects them.

A repository with local edits is sometimes called **dirty**. That does not mean its edits are bad. They may be valuable unfinished work. Do not remove or bundle them to make a display tidy. In a shared workspace, ownership matters as much as mechanics.

## 2. Ask a narrow status question

`git status --short -- path` reports one path's status. `--short` requests a compact display. The `--` separates options from file paths, removing ambiguity about what follows. Use the path you intend to inspect rather than surveying unrelated files.

```bash
git status --short -- course/syllabus.json
```

It prints no lines if the tracked file matches the index and saved version. Otherwise it prints a status code and path. The result depends on local work; an empty display is a meaningful possible outcome, not a failure to run.

In the short display, the first column concerns the index and the second the working tree. ` M` describes an unstaged modification. `M ` describes a staged modification. `??` describes an **untracked** file, one not yet included in Git's tracking. Spacing matters.

Do not memorize a status result as a permanent property. Another contributor can change the file. Status is a snapshot at inspection time. Write "this inspection showed an unstaged modification," rather than "this file is always modified."

## 3. Read commits with log

`git log` lists commits. `--oneline` uses one compact line per commit. `-n 3` limits output to three entries. `--format=%s` prints only each commit's subject, the first line of its message. These display options do not create history.

```bash
git log -n 3 --oneline -- .foreman/ledger.md
```

It prints up to three commit summaries affecting the named file in the current reachable history. Each line contains an identifier and subject. There may be fewer than three entries. The exact output depends on the repository at inspection time.

The path after `--` limits the question. With a directory path, you inspect commits affecting that directory. A count of commits touching a directory is not a count of training runs. One commit can change many files, and one run can produce many commits or none.

```bash
git log --format=%s -- scratchpad/gauntlet/L74/plan1026/opp/learner/ | wc -l
```

It prints the current count of returned commit subjects for that directory. Each subject is one line, so this counts the displayed entries. Its scope is the current default history, not every branch and not uncommitted work. State that scope when reporting the number.

A **reachable** commit is one Git can find by following history from the selected starting point. You do not need to draw the full history graph today. You do need to understand that changing the starting branch can change the answer to a history question.

## 4. Read differences with diff

A **diff** displays differences between versions. `git diff -- path` compares unstaged working-tree changes against the index. `git diff --cached -- path` compares staged changes against the current commit. The word `cached` here refers to the index.

```bash
git diff --stat -- course/syllabus.json
```

It prints a compact summary of unstaged changes for that file, or nothing if there are none. A summary can show that lines changed. It cannot explain whether a revised lesson order is pedagogically correct; that requires reading content.

In a patch display, a leading `-` marks a removed line and a leading `+` an added line. **Context lines** surround a change to help locate it. A **hunk** is one local block of differences. File headings also contain plus or minus signs, so do not blindly count every such line as code.

A replacement often appears as one removed line and one added line. That is Git's text representation of how to transform earlier content into later content. It does not necessarily mean that two independent conceptual changes occurred.

## 5. Inspect a saved file with show

`HEAD` names the currently selected commit in an ordinary working checkout. `git show` can display a commit or a file from a commit. The notation `HEAD:path` selects a saved file at that commit rather than its current working-tree contents.

```bash
git show HEAD:.foreman/scratch/loop_ops/safe_commit.sh | head -n 1
```

At authoring time, this prints no file content and Git reports that the path does not exist in HEAD, even though the local file exists. In a future HEAD version containing the script, it would print `#!/bin/bash`. Existence in the working tree and existence in HEAD are separate questions.

The first line is a **shebang**, a script header indicating the intended interpreter on systems using that convention. Displaying it does not execute the script. The pipe passes saved text to `head`, which selects one line.

Compare that with `head -n 1 .foreman/scratch/loop_ops/safe_commit.sh`, which reads the working-tree version. If a local edit changed the header, the commands could differ. When quoting evidence, say whether it came from saved history or the local file.

## 6. Branches and remote copies

A **branch** is a named line of development whose label points to a commit. A **remote** is a named connection to another repository location. A **push** sends commits and reference updates to another repository. We discuss its meaning; none of these exercises performs one.

A local commit is not necessarily present in a remote copy. Local files can also differ from both local history and remote state. "It is in Git" is therefore imprecise. Say which commit or branch you inspected, and distinguish observations from assumptions about other copies.

The course does not ask you to stage, commit, switch branches, or synchronize repositories. These operations change shared state. The reading commands above suffice for P01's historical questions. Understanding a write operation does not require performing it on this project.

## In the real project

From `.foreman/scratch/loop_ops/safe_commit.sh`, the first four lines are:

```bash
#!/bin/bash
# safe_commit.sh MSGFILE PATH... | REPO_PATH=LOCAL_FILE ... : commit ONLY the given paths on top of origin/main through a private
# index (other agents' staged files are never swept), push, move local main there, and sync the shared index for the touched
# paths (plus any paths origin brought in) only. Refuses when local main has commits origin lacks.
```

This excerpt prints nothing. Line 1 identifies Bash. Line 2 documents accepted arguments and selected-path intent. Line 3 says the script uses a private index and performs synchronization operations. Line 4 describes a refusal condition involving local and remote history. These comments summarize intent; the executable implementation is more complex and outside today's prerequisites.

A **private index** is a separate staging area for one operation, avoiding accidental inclusion of another contributor's staged work. That design idea does not make the script read-only. The exercises inspect its tracked header and never invoke it.

The course rule about `HANDOFF.md` matters especially in shared work: never make a pathspec commit of it. A **pathspec** is Git's way of selecting paths for an operation. Selecting a shared handoff can capture another contributor's edits along with your own. Naming a path is not proof that every change within it belongs to you.

## 7. Match claims to evidence

Suppose a commit subject mentions opponent calibration. You can say the history records a commit with that subject affecting the selected path. To say it improved the opponent, you also need measurements. To say it became live, you need a deployment record or other direct evidence.

History identifies code versions. Logs record events. Configurations describe intended settings. Statistical reports summarize measurements. These sources complement one another; none substitutes for all the others merely because it is stored in the repo.

For a useful practice comparison, read a file header from the working tree and from HEAD. If they match, report that the inspected headers match, not that the entire files are identical. If they differ, use a diff to locate the change. Keep the scope of your claim as narrow as the scope of your inspection.

The exercises progress from reading a saved header, to counting bounded history entries, to displaying a historical subject, to producing a labeled directory-history count. They deliberately avoid fixed commit identifiers. New commits should change the observed history without making a structurally correct answer wrong.

## Common mistakes

- Treating saved editor changes as committed history.
- Confusing `git diff` with `git diff --cached`.
- Counting commits and calling them experiments.
- Assuming a script named "safe" is appropriate to run.
- Treating a shared document's entire change as your own.
