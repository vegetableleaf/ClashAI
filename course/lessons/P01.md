# P01 - PROJECT 1: Explore the repo like an engineer

**Time:** about 5 hours - **You will be able to:** produce a reproducible repository investigation with clearly bounded conclusions.

## Why this matters for ClashBot

An engineer should explain where an answer came from. "The bot is CLXIII" is a claim; a dated line in `.foreman/ledger.md` is evidence for what that document recorded. The distinction matters when live emulator work and simulator experiments move independently.

This project combines A01's paths, A02's commands, A03's formats, and A04's history. Investigate three real questions: what evidence discusses CLXIII being live, how many commits touched the opponent learner, and what the last ten ledger lines currently say.

Use only the terminal and Git. Your final write-up will distinguish observed evidence, historical scope, and questions the selected records cannot answer. This is an investigation of the Icebow project, not a deployment task.

## Project contract

A **milestone** is a small deliverable checked independently. There are five milestones, each corresponding to one interactive exercise. Complete them in order. Each exercise starts a new shell session at the repository root, so do not rely on a previous answer's directory changes.

The checker recognizes required output structure. It cannot decide whether your prose interprets history honestly. After each successful exercise, read the result and retain the command and observation in your course notes. The final write-up is part of the project, even though its interpretation needs human review.

No new shell programming syntax is required. You use `printf`, `ls -d`, `head`, `tail`, `grep -F`, `wc -l`, and `git log`. A pipe passes text to the next command. Separate command lines run in order. Consult A02 or A04 when you cannot explain an option.

## Milestone 1: establish evidence locations

Confirm the ledger and handoff paths with `ls -d`. This is stronger than printing their names because the command consults the filesystem. Use separate commands to control output order.

```bash
ls -d .foreman/ledger.md
ls -d HANDOFF.md
```

It prints `.foreman/ledger.md` followed by `HANDOFF.md`, one per line. If a source is missing, report that limitation rather than inventing its contents. A useful investigation records unavailable evidence too.

Write down what each source is for. The ledger coordinates work and records progress. The handoff collects findings and restart context. Do not assume either is perfectly ordered by real event time without examining dates and corrections.

Deliverable: two verified paths and one sentence describing each source's purpose. This gives the rest of your investigation a clear foundation. You have established where to look, not yet established any conclusion about live performance.

## Milestone 2: locate CLXIII evidence

Search for references to CLXIII in the ledger. Line numbers help locate a record later, but they belong to the file version inspected. Inserted lines can move those positions.

```bash
grep -n -F 'CLXIII' .foreman/ledger.md | head -n 3
```

It prints up to three matching lines with numbers. At inspection, a matching line records CLXIII NOLEAK as live in Ranked. Other lines discuss planned trials and comparison results. These different kinds of statements must not be conflated.

The question is "when was CLXIII made live?" A line saying it is live establishes recorded state in that note's context. It does not necessarily establish the exact promotion time. Search the handoff as a follow-up:

```bash
grep -n -F 'CLXIII' HANDOFF.md | head -n 5
```

It prints up to five matching lines, or none if no matching text is present. Read surrounding headings before assigning dates to matches. A bounded terminal window can be made with `head -n 20 file | tail -n 5`, which selects the last five lines of the first twenty.

Deliverable: a supporting quote, its source, and an honest conclusion. "The ledger records it as live; this excerpt does not establish first promotion time" is valid when the evidence is insufficient. Never turn an approximate note time into a precise deployment time.

## Milestone 3: count opponent-learner history

Use the directory path to scope history. Print one subject per returned commit and count the lines:

```bash
git log --format=%s -- scratchpad/gauntlet/L74/plan1026/opp/learner/ | wc -l
```

It prints the current count, perhaps with surrounding spaces. No fixed number is provided because history can change. The scope is the current default reachable history and the selected directory.

Inspect a small sample without counting:

```bash
git log -n 3 --oneline -- scratchpad/gauntlet/L74/plan1026/opp/learner/
```

It prints up to three identifiers and subjects. This shows the unit being counted. One commit can affect several learner files. Uncommitted work produces no history entry. Zero returned entries would not prove that nobody worked on the directory.

Deliverable: the command, current numeric output, and a sentence defining the count. Do not compare it directly to training updates or matches. Those are different measurements. An experiment can generate numerous files yet be recorded in one commit, or remain entirely uncommitted.

## Milestone 4: inspect the latest file window

Read the ledger's final ten lines:

```bash
tail -n 10 .foreman/ledger.md
```

It prints the current final ten lines, or the entire file if shorter. Blank lines count. "Last in the file" does not guarantee "latest event in time," especially when a later note describes earlier work.

The exercise places this output between two printed labels. Labels make its boundaries visible. They do not validate the source's claims. Use `printf` on separate lines before and after the reading command.

Read status verbs carefully: planned, running, stopped, measured, failed, completed. A plan is not a result. A result needs measurement context. Avoid copying a performance percentage without its denominator, comparison, and relevant experimental conditions.

Deliverable: the window and a two-sentence paraphrase in your notes. One sentence says what the text records. The other states a limitation, such as that this window is not a complete audit of every task.

## Milestone 5: assemble the evidence packet

A **reproducible** investigation gives another person enough information to repeat the method. Results may change as new work arrives, but the commands and scope should remain clear. Produce labeled sections for CLXIII evidence, the history count, and the ledger ending.

The exercise checks those sections and output shapes. It does not freeze today's count or demand an unsupported deployment date. Run the real commands again so the packet reflects current evidence rather than remembered output.

Compare the count with milestone 3 and the window with milestone 4. If they differ, the project may have changed while you worked. Record that possibility. Do not replace a new observation with an old one merely to make the report appear consistent.

Deliverable: a readable packet another learner can recreate. You have combined file inspection, text selection, and history without starting the live bot or changing project implementation.

## In the real project

From `.foreman/ledger.md`:

```text
# Foreman ledger -- plan1026 days 0-3 + Pillar 4 (run started 2026-10-27 04:00 EDT)
```

This document heading prints nothing. The hash marks a main heading. The words name its work scope. The parenthesis supplies a recorded run start time. That is not automatically the time CLXIII first became live.

From `HANDOFF.md`:

```text
## 2026-10-15 ~18:15 EDT -- owner: "doesn't know when to counterattack and when to defend" (MK + Witch at a low tower)
```

This also prints nothing. The heading level organizes the note. The timestamp locates the concern approximately. The quotation records the concern, and the parenthesis describes a game situation. Neither this heading nor the ledger title supplies a complete deployment history.

## Final write-up

Write a short report in your study notes after the five exercises. Include inspection date, source paths, commands, and observed outputs. Answer each of the three research questions separately. If the first-live time remains unresolved, state what is established and what additional dated event record would resolve it.

Use three labels in your reasoning. **Observed** means directly visible in selected evidence. **Inferred** means concluded from evidence. **Unresolved** means the inspected evidence is insufficient. A ledger line can be observed, a likely timeline inferred, and an exact promotion time unresolved.

A good report's confidence matches its sources. Another learner should understand why you reached a conclusion even after the files change. Retaining the command alongside its output is more useful than copying a number alone.

Allow time to review your own wording. Replace "proved the bot improved" with the specific measured claim if your source only reports a simulator comparison. Replace "deployed at" with "recorded as live by" if you found a state note but not an event record. Precision here will help you later evaluate learning experiments.

## Common mistakes

- Treating the ledger start date as a promotion date.
- Reporting commit count as match count.
- Assuming the last file lines are a full chronological history.
- Copying old output into a new investigation.
- Omitting limitations because the checker passed.
