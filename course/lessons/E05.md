## Why this matters for ClashBot

The laptop can run the phone emulator while other computers run simulation or training. A command can therefore be syntactically correct yet run on the wrong machine, use the wrong interpreter, or exhaust a shared resource. Understanding where a process lives is essential when reading ClashBot experiment reports.

The syllabus names `.foreman/scratch/a2/COMMON.md`. It describes a shared checkout, shared laptop resources, and rules for remote workers. We will read brief relevant excerpts and perform local budget calculations. The exercises make no remote connections and use no accelerator.

## 1. Local and remote are locations

A **remote machine** is another computer reached through a communication connection. **SSH** is a protocol commonly used to obtain an authenticated shell on such a machine. The shell at the other end interprets its commands using that machine's files, programs, and permissions.

An **authentication identity** establishes who is connecting. A **public/private credential pair** is one way systems establish identity: public information can be registered with a service, while private material stays protected. We need only the concept here; no credential material or locations are used in this course activity.

A path beginning with C: usually describes a Windows drive. A path beginning with /workspace commonly appears in the project's remote Linux environments. Neither spelling guarantees that a similarly named file has the same contents on another computer.

```python
locations = {"laptop": "C:/practice/results",
             "worker": "/workspace/practice/results"}
print(locations["laptop"] == locations["worker"])
```

**Output:** `False`.

The strings are different locations. Even matching strings would not prove matching files across machines. A reproducible run records its machine context, interpreter, source version, data version, and output location.

## 2. Pods and containers

A **pod** here means a rented compute environment provided by a service such as RunPod. The provider's product terminology is separate from the programming language. A **container** isolates a process environment while sharing the host operating system's kernel.

A **host** is the underlying computer. It may have far more resources than a particular container is allowed to use. The container can see information about the host while still being constrained by its allocation.

A **resource limit** caps something such as CPU time or memory. A **cgroup** is a Linux mechanism used to account for and limit groups of processes. These limits can matter more than the host's advertised hardware.

For a hypothetical example, suppose the host reports 256 logical CPUs, while the environment allows 54 CPU equivalents and 62 GiB of memory. These are teaching numbers from the syllabus scenario, not measurements of today's pod. A plan based on 256 simultaneous workers would ignore the actual budget.

```python
host_cpus = 256
allowed_cpus = 54
reserve = 6
usable = max(0, allowed_cpus - reserve)
print(usable)
```

**Output:** `48`.

The host count is deliberately unused in the budget calculation. **Headroom** is unused capacity reserved for other processes and variability. Reserving it is a planning choice, not proof that a workload cannot exceed its estimate.

## 3. CPU and GPU jobs

A **CPU** performs general-purpose computation and coordinates a program. A **GPU** performs many similar arithmetic operations in parallel. Large batches of neural-network calculations can use a GPU efficiently. Small irregular simulation steps may depend heavily on CPUs.

The two are not interchangeable worker counts. A machine with one GPU does not support unlimited simultaneous model jobs. GPU memory is separate from the ordinary memory budget in many systems, and each job may need both.

```python
gpu_memory_gib = 24
reserve_gib = 4
job_gib = 12
jobs = max(0, (gpu_memory_gib - reserve_gib) // job_gib)
print(jobs)
```

**Output:** `1`.

This is capacity arithmetic, not permission to start a job. Runtime peaks and shared users can reduce what is practical. F12 covers training performance properly; here we only learn to distinguish resource categories and preserve their units.

A reported “GPU available” condition also does not prove that the installed Python environment supports it. The interpreter, packages, hardware, and driver must agree. Our course exercises avoid that setup by using tiny CPU calculations.

## 4. Combining limits

A simulation worker may require both CPU and memory. Compute a worker ceiling for each resource, then choose the smaller. **GiB** means 1,073,741,824 bytes. Keep units consistent rather than mixing bytes, decimal gigabytes, and GiB in one division.

```python
usable_cpus = 48
cpus_per_worker = 2
usable_gib = 50
gib_per_worker = 3
cpu_limit = usable_cpus // cpus_per_worker
memory_limit = usable_gib // gib_per_worker
print(min(cpu_limit, memory_limit))
```

**Output:** `16`.

CPU alone allows 24 workers, but memory allows only 16. The calculation assumes per-worker estimates are valid and excludes other constraints such as disk speed. Measure a small workload before increasing concurrency in a real experiment.

A **quota** can describe CPU time rather than a set of dedicated cores. Dividing a CPU-time allowance by its period gives CPU equivalents.

```python
quota = 5400000
period = 100000
print(quota / period)
```

**Output:** `54.0`.

The two values have matching time units, which cancel. Some systems represent “unlimited” with text rather than a number. Our exercise returns None for that case, meaning no finite quota was supplied. It must not turn None into permission to use every visible CPU.

## 5. Storage lifetime

**Persistent storage** is intended to survive a relevant lifecycle event. **Ephemeral storage** may disappear when an environment is removed or restarted. Exactly which event destroys which disk depends on the service and configuration.

Do not assume every /workspace directory has identical persistence. A file surviving one process restart does not prove it survives pod termination. A remote experiment needs an explicit output-retention plan before a long run begins.

```python
artifacts = [
    {"name": "summary", "retained": True},
    {"name": "worker-cache", "retained": False},
]
print([a["name"] for a in artifacts if not a["retained"]])
```

**Output:** `['worker-cache']`.

The exercise uses declared metadata, not an inspection of real storage. An unknown retention property should be reported as unknown. Do not silently promote an unverified disk into the persistent category.

A **checkpoint** is a saved state from which work may resume or which can be evaluated. Saving one is only useful if its path, compatibility, and lifetime are known. F06 will explain how learning experiments choose checkpoints; here the concern is whether the saved artifact still exists.

## 6. Sessions, background work, and logs

A **session** groups processes associated with an interaction. A remote connection ending can affect processes attached to it. Bash's ampersand, taught in E01, backgrounds a command but does not by itself guarantee survival after a disconnected session.

The program nohup changes how a command handles a hangup signal, a notification associated with a lost controlling session. The program setsid starts a new session. These names appear in the launchers. They do not guarantee that the machine stays alive, memory remains available, or output is saved correctly.

**Redirection** changes where a process reads or writes. The notation > sends stdout to a file; 2> sends stderr to a file. The form 2>&1 sends stderr to the current stdout destination. Order matters because these operations are applied from left to right.

```bash
printf '%s\n' 'toy job complete'
```

**Output:** `toy job complete`.

We deliberately keep this local example on stdout. In P05, workers write separate temporary files and the parent waits for them. The lesson is the same across machines: a launch message is not a completion record.

A **tar archive** packages files into one byte stream. A **tar pipe** connects a program producing that archive to another consuming it. This can avoid an intermediate archive file, but the receiving end still needs the correct destination and a checked exit status. No transfer command is needed for the exercises.

## 7. Read a run report as evidence

A useful resource report states the source of each number: host capability, container allowance, observed usage, or estimated peak. These are different quantities. A plan should not present an estimate as a measurement.

```python
report = {"allowed_cpus": 54, "planned_workers": 16,
          "cpus_per_worker": 2}
print(report["planned_workers"] * report["cpus_per_worker"]
      <= report["allowed_cpus"])
```

**Output:** `True`.

This checks one constraint only. It says nothing about memory, ownership, or whether the experiment completed. In a real comparison, engine build, table version, and seed identity must also match the intended design.

When reading match results, distinguish infrastructure failure from a game loss. A worker that never produced an outcome adds an unknown or failed-run count, not a loss. The same cleaning rule applies to the live JSONL: absent derived results remain separate.

## Common mistakes

- Budgeting from the host count instead of the container allowance.
- Mixing GiB and bytes in one formula.
- Treating background launch as completed work.
- Assuming every remote disk survives every lifecycle event.
- Recording missing worker output as a game loss.
