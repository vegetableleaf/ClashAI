## Why this matters for ClashBot

The Icebow match summaries in `scratchpad/gauntlet/L74/loss_review/matches.jsonl` contain outcome labels and observed opponent cards. A useful question is which observed cards appear most often in recorded losses. Answering it involves filtering rows, collecting counts, and sorting the result.

These tools also appear throughout simulator analysis and training code. A RoyaleSim or crforge experiment may produce many records, while imitation-learning and reinforcement-learning pipelines repeatedly select and transform examples. Today we practise the Python operations without introducing the later mathematics.

Shorter code is not automatically better code. The goal is to make a transformation easy to read and verify. We will start each compact form from a familiar loop, then name the limitation that matters for a ClashBot report.

## 1. Turn a loop into a comprehension

A **list comprehension** builds a list by describing what to produce for each input item. It combines an output expression with a loop. Compare this familiar version:

```python
costs = [6, 3, 1]
doubled = []
for cost in costs:
    doubled.append(cost * 2)
print(doubled)
```

It prints `[12, 6, 2]`. The equivalent compact form is:

```python
costs = [6, 3, 1]
doubled = [cost * 2 for cost in costs]
print(doubled)
```

It also prints `[12, 6, 2]`. Read it as “cost times two, for each cost in costs”. The expression before `for` describes the output item. The loop after `for` describes where its inputs come from. The original list stays unchanged.

Use a normal loop when you need several named intermediate values or detailed error reporting. A comprehension is most helpful when one clear expression captures the transformation. Compressing a long chain of decisions into one line makes a beginner's report harder to audit.

## 2. Filter while transforming

A **filter** keeps only items satisfying a condition. A comprehension can put an `if` condition after its loop. Here we keep names of cards that fit the elixir budget:

```python
cards = [{"name":"Xbow", "cost":6}, {"name":"Skeletons", "cost":1}]
names = [card["name"] for card in cards if card["cost"] <= 5]
print(names)
```

It prints `['Skeletons']`. The condition is evaluated for each card. Only a passing card contributes its name. This example checks a simplified budget rule, not all live play constraints. A card could be affordable yet absent from the hand.

The same pattern selects match rows:

```python
rows = [{"derived":"WIN"}, {}, {"derived":"LOSS"}]
losses = [row for row in rows if row.get("derived") == "LOSS"]
print(len(losses))
```

It prints `1`. Missing labels do not accidentally become losses because the condition asks for the exact string. If a later report excludes dry runs, that is an additional explicit condition, not something this expression does automatically.

## 3. Build a dictionary with a comprehension

A **dictionary comprehension** produces name-value associations. It uses braces and a colon between the output name and output value.

```python
cards = [{"name":"Xbow", "cost":6}, {"name":"Knight", "cost":3}]
cost_by_name = {card["name"]: card["cost"] for card in cards}
print(cost_by_name)
```

It prints `{'Xbow': 6, 'Knight': 3}`. This is useful when later code needs direct lookup by card name. A dictionary can hold only one value for a particular name. If the input repeats a name, a later assignment replaces the earlier value.

That replacement is a significant limitation for match reports. You cannot build a dictionary from date to one match and expect it to preserve every match on that date. To group many rows, each date must refer to a list or a summary count. P02 will use lists of rows inside a grouping dictionary.

## 4. Sort without mutating the source

**Sorting** arranges items according to an ordering rule. The built-in `sorted` returns a new list. This makes it easier to preserve the original input sequence for another calculation.

```python
counts = [4, 1, 3]
ranked = sorted(counts, reverse=True)
print(ranked)
print(counts)
```

It prints `[4, 3, 1]` and `[4, 1, 3]`. `reverse=True` asks for descending order. For dictionaries representing cards or matches, Python needs you to say which value should determine the ordering.

A **sort key** is the value used for comparison. The `key=` argument accepts a function that computes that value from each item. Despite the shared word, this use of “key” does not mean you must be sorting a dictionary.

```python
def loss_count(item):
    return item[1]

items = [("Xbow", 4), ("Giant", 7)]
print(sorted(items, key=loss_count, reverse=True))
```

It prints `[('Giant', 7), ('Xbow', 4)]`. Each item is a pair, and index one holds its count. The function receives one item at a time; it does not receive the whole list.

## 5. Use lambda for a tiny function

A **lambda** creates a short function from one expression. It is useful when a function is so small that a separate name would add little explanation.

```python
items = [("Xbow", 4), ("Giant", 7)]
print(sorted(items, key=lambda item: item[1], reverse=True))
```

It prints `[('Giant', 7), ('Xbow', 4)]`. The parameter is `item`; the expression after the colon supplies the return value. Lambda is not faster sorting or a special game rule. It is another spelling for this small function.

For a report, define what happens when counts tie. **Deterministic ordering** means the same input produces the same ordering. Alphabetical tie-breaking makes a ranking predictable even if the grouping dictionary was populated in a different sequence.

```python
counts = {"Xbow":2, "Giant":2, "Knight":1}
names = sorted(counts, key=lambda name: (-counts[name], name))
print(names)
```

It prints `['Giant', 'Xbow', 'Knight']`. Python compares the first part of the tuple first, then the second part when needed. Negating the count puts larger counts first under ordinary ascending sorting. The name then breaks ties alphabetically.

## 6. Number items with enumerate

**Enumeration** pairs each item with its position. `enumerate` supplies the index automatically, avoiding a manually updated counter.

```python
names = ["Xbow", "Knight"]
for number, name in enumerate(names, start=1):
    print(number, name)
```

It prints `1 Xbow` and `2 Knight`. The `start` argument controls the first number. Starting at one is useful for human-facing report ranks and line numbers. Ordinary list indexing still starts at zero; display numbering does not change that rule.

The variables `number, name` unpack each pair. **Unpacking** assigns the parts of a sequence to separate variables. You have seen it with tuples; enumeration simply provides those tuples for you. A loader can similarly enumerate lines to include a useful source line number in an error message.

## 7. Pair sequences with zip

`zip` pairs corresponding items from separate sequences. This is useful when names and costs arrive in separate lists but have matching order.

```python
names = ["Xbow", "Knight"]
costs = [6, 3]
for name, cost in zip(names, costs):
    print(name, cost)
```

It prints `Xbow 6` and `Knight 3`. By default, zip stops at the shorter input. If one list has three items and the other has two, only two pairs appear. That can silently discard information if you expected equal lengths.

In today's pairing exercise, equal lengths are an explicit assumption. In a real parser, check lengths or use a representation that keeps related values together from the start. A list of card dictionaries often avoids the risk of separate lists drifting out of alignment.

You can combine enumeration and pairing. The loop target then becomes `number, (name, cost)`: one number and one nested pair. Write the ordinary loop first if that shape is difficult to read, then convert it to a comprehension only after the values make sense.

## 8. Ask whether any or all conditions hold

`any` returns true if at least one supplied value is true. `all` returns true if every supplied value is true. These operations summarise boolean conditions rather than counting them.

```python
costs = [6, 3, 1]
print(any([cost <= 2 for cost in costs]))
print(all([cost <= 2 for cost in costs]))
print(any([]), all([]))
```

It prints `True`, `False`, and `False True`. There is an affordable one-cost card, but not every card fits two elixir. For empty input, no true example exists for `any`; no false example exists to contradict `all`. This empty-input behaviour matters when checking a list that may contain no matches.

Do not mistake `all(valid_rows)` for a check that at least one row exists. If your report needs both nonempty input and a condition true for every row, express both requirements. This prevents an empty dataset from appearing to prove a claim about observed matches.

## 9. Produce values only when requested

A **generator** produces values one at a time rather than building a complete result list immediately. The keyword `yield` gives one value to the caller and pauses the function. The next request resumes where execution paused.

```python
def loss_rows(rows):
    for row in rows:
        if row.get("derived") == "LOSS":
            yield row

stream = loss_rows([{"derived":"LOSS"}, {"derived":"WIN"}])
print(list(stream))
print(list(stream))
```

It prints `[{'derived': 'LOSS'}]` and then `[]`. The generator has been **consumed** after the first conversion. It does not restart automatically. Call the generator function again to create another traversal.

A **generator expression** uses parentheses for a similar compact form: `(row for row in rows if condition)`. Passing that directly to `sum`, `any`, or `all` can avoid an intermediate list. Lazy production reduces storage for intermediate results, but does not make the underlying computation disappear.

## In the real project

The syllabus lists no required source for B10. We use `scratchpad/gauntlet/L74/loss_review/matches.jsonl`, which contains this exact one-line fragment in an observed loss record:

```text
"opp_cards": ["BlowdartGoblin", "Goblins", "SkeletonArmy", "SkeletonBalloon", "SkeletonKing", "SuspiciousBush"]
```

This is data and prints nothing. The field name identifies the opponent-card observations. The bracketed value is a list of recorded names. Its six entries do not establish a complete eight-card deck. Use “observed opponent cards” in your report rather than silently upgrading observations into a full deck identity.

To count cards in losses, select explicit non-dry rows labelled LOSS, then visit `set(row.get("opp_cards", []))`. A **set** contains distinct values, so repeated sightings of one card contribute once per match. Missing card observations contribute no names. Sort the resulting counts with an explicit tie rule.

A high loss count against a card can reflect frequent encounters rather than a difficult matchup. It is not a loss rate until you include the relevant encounter denominator. P02 produces per-card summaries with both wins and losses. Multiple card groups overlap because a single opponent can show several cards in one match.

## Common mistakes

- Compressing several difficult decisions into one unreadable comprehension.
- Forgetting that repeated dictionary names overwrite earlier values.
- Ranking counts while describing them as rates.
- Counting repeated sightings twice within one match.
- Reusing a consumed generator and expecting the original values.
- Forgetting that zip stops at the shorter input by default.
