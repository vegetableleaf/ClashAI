# I01 · Reproducibility: seeds, hashes and pinned versions

**Time:** about 3 hours · **You will be able to:** build a reproducibility manifest and reject comparisons that mix engine or table versions.

## Why this matters for ClashBot

A repeated seed does not recreate a match if the engine rules changed. The same checkpoint can make different decisions under different decoding settings, and the same engine name can resolve to different compiled artifacts. Reproducibility requires more than remembering one integer.

`scratchpad/gauntlet/L74/crforge/fork/MAIN.md` records engine revisions, table versions and the rule that paired comparisons must use the same library build. It also records that running jobs keep their pinned build until their next start.

This lesson builds a small **manifest**, a structured record of the inputs that define an experiment. The exercises hash harmless synthetic bytes and one named public project source file. They neither load a production checkpoint nor change any configuration.

## 1. A seed controls one source of randomness

A **seed** initializes a pseudorandom number generator. A **pseudorandom** sequence is generated deterministically from internal state, even though its values are used as random samples. Reusing the seed reproduces the sequence only when the generator and calls are the same.

```python
import random
first = random.Random(8)
second = random.Random(8)
a = [first.randrange(10) for _ in range(4)]
b = [second.randrange(10) for _ in range(4)]
print(a == b)
```

It prints `True`. The local generators avoid interference from unrelated random calls elsewhere in the program. Adding one extra draw to only one generator would shift its later sequence.

An experiment may have separate environment, action-sampling and data-shuffling generators. Record each seed and its role. Setting Python's random seed does not automatically set PyTorch's generator. P07 used both a seeded environment reset and a separate PyTorch sampling seed.

A fixed seed also does not guarantee identical floating-point results across all hardware and software. Some operations depend on execution order. State the environment in which exact equality is expected and use tolerances only where justified.

## 2. Hash the bytes you intend to identify

A **hash** is a fixed-length fingerprint calculated from data. SHA-256 is a commonly used hash algorithm. A **digest** is its output. Matching digests are strong evidence of identical bytes, but do not establish that those bytes are correct, safe or scientifically valid.

```python
import hashlib
a = hashlib.sha256(b"icebow").hexdigest()
b = hashlib.sha256(b"icebow\n").hexdigest()
print(len(a), a == b)
```

It prints `64 False`. The newline is part of the bytes, so it changes the digest. A text editor's line-ending conversion can therefore change a file hash without changing what a reader thinks the words say.

Hashing the actual bytes is useful for checkpoint and engine identity. Hashing a filename is not enough: the file's contents can change while its name stays the same. Conversely, two differently named files can contain identical bytes.

Read only the explicitly selected file. A recursive search through arbitrary data directories is unnecessary for this lesson. The exercise uses `pipeline/cf_credit.py` as a harmless source artifact and prints no file contents.

## 3. Canonicalize a configuration deliberately

A **configuration** is the collection of settings for a run. A **canonical representation** is a consistent encoding used so equivalent configurations produce the same bytes. For a simple JSON dictionary, sort field names and remove optional whitespace before hashing.

```python
import json
a = {"gamma": 0.9, "batch": 32}
b = {"batch": 32, "gamma": 0.9}
left = json.dumps(a, sort_keys=True, separators=(",", ":"))
right = json.dumps(b, sort_keys=True, separators=(",", ":"))
print(left == right)
```

It prints `True`. Dictionary insertion order no longer changes the encoding. The separators argument removes spaces around punctuation; it does not alter the numeric values.

Canonicalization is a policy decision. Numeric 1 and 1.0 may encode differently even if some code treats them similarly. A missing field and a field set to null may mean the same thing for one optional feature and different things for another.

The project often requires an absent optional setting to preserve historical behaviour and configuration identity. For a documented null-equivalent option, remove only that option when it is absent or null. Do not remove every false, zero or empty value. Zero can be a meaningful setting, such as disabling a penalty.

An **absent-setting test** checks that adding an optional feature does not alter historical behaviour when the feature is disabled. A matching configuration hash is one part of that evidence; unchanged rollout records or outputs supply the behavioural part.

## 4. Pin versions across the comparison

To **pin** a version means to record and use a specific immutable revision or artifact rather than a moving label. An engine build, card table version, policy checkpoint and decoder configuration jointly define much of a ClashBot evaluation.

```python
parent = {"engine": "build-a", "tables": "tables-1", "seed": 42}
candidate = {"engine": "build-b", "tables": "tables-1", "seed": 42}
same_environment = all(parent[name] == candidate[name]
                       for name in ("engine", "tables", "seed"))
print(same_environment)
```

It prints `False`. The matching seed and tables do not cancel the engine change. If the engine revision is the treatment being studied, design an explicit engine comparison. Do not hide it inside a policy comparison.

A **confound** is an unintended difference that can explain an observed result. Switching tables during a learning-rate experiment creates a confound. Re-evaluating both parent and candidate on the new tables restores a comparable pair for that environment.

A moving path such as a current-build pointer can be convenient for new jobs, but existing jobs should retain the artifacts they started with. Repointing their dependencies midway through a run makes its identity ambiguous.

Record both human-readable names and digests where appropriate. A short label helps discussion; a full digest supports exact identification. Do not assume a truncated identifier is collision-proof merely because it is easier to read.

## 5. Reproduce a result, not only a command

A **reproduction** reruns a procedure under the specified conditions and checks whether the reported result follows. A command line alone may omit environment versions, data filtering, current directory, random seeds or uncommitted source changes.

A useful manifest records source revision or source hashes, engine build, table version, model identifier, configuration digest, seeds, dataset identity, outcome rules and evaluation seat. Include which fields differ intentionally between parent and candidate.

```python
manifest = {
    "engine": "toy-v1",
    "tables": "toy-stats-v1",
    "environment_seed": 12,
    "sampling_seed": 900,
    "outcome_rule": "decisive wins; unknown separate",
}
print(manifest["engine"], manifest["sampling_seed"])
```

It prints `toy-v1 900`. The names are synthetic and make no claim about an installed production build. The outcome rule is included because a denominator change can alter a headline score without changing any match.

Separate **bitwise reproducibility**, identical bytes, from **statistical reproducibility**, comparable results within expected variation. A deterministic simulator replay may require bitwise identity. A stochastic learning study may require repeated-seed evidence. Neither standard should be silently substituted for the other.

When a reproduction fails, first compare manifests. Then isolate the earliest divergence: input records, sampled actions, simulator states or aggregate calculations. This is more informative than changing many settings until a final score happens to match.

Finally preserve negative evidence. If a known old build faults on a particular state and a new build fixes it, the results can differ for a legitimate reason. That does not permit mixing the builds in an otherwise paired policy evaluation.

## Practice plan

The first exercise uses independent random generators to reproduce a short draw sequence. The second computes a digest of the named source file and compares it with a fresh byte read. The count or digest is not hard-coded because the repository can change.

The third exercise canonicalizes a synthetic configuration with one specifically documented null-equivalent optional field. The fourth checks comparison metadata and returns the names of mismatched environment fields.

After completing them, prepare a manifest for your P07 run from the actual settings you used. Do not fill missing values with plausible guesses. An explicit unavailable field is more useful to a teammate than a precise-looking invented identifier.

## Common mistakes

- Treating one seed as controlling every random generator.
- Hashing the filename instead of the file contents.
- Removing meaningful zero values during canonicalization.
- Comparing policies across different engine builds without declaring the confound.
- Claiming matching hashes prove scientific correctness.
