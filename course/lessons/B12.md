# B12 · Testing your code

**Time:** about 4 hours · **You will be able to:** write meaningful assertions, recognise pytest tests, and prove that your checks reject deliberately broken behaviour.

## Why this matters for ClashBot

An Icebow helper can return a plausible number while being wrong at an important boundary. Using `<` instead of `<=` would reject a six-cost X-Bow when exactly six elixir is available. A quick successful run with ten elixir would not expose that defect.

The directory `pipeline/tests/` contains checks for many parts of ClashBot. We will read a short section of `pipeline/tests/test_decision_options.py` and relate it to small functions you can understand completely. You do not need to run the full project suite to learn what these tests are asking.

Later, tests will protect the calculations used in RoyaleSim and crforge experiments, imitation-learning datasets, and reinforcement-learning updates. Passing software tests does not prove that a model plays well. It supports a narrower claim: particular pieces of code satisfy specified behaviours on the cases checked.

## 1. State expected behaviour before checking it

A **test** runs code under stated conditions and checks an expected result. A **test case** is one particular set of inputs and expectations. A useful test starts with a behaviour someone can explain without reading the implementation.

```python
def can_afford(cost, elixir):
    return cost <= elixir

assert can_afford(6, 6) is True, "six elixir affords a six-cost X-Bow"
assert can_afford(6, 5) is False, "five elixir cannot afford a six-cost X-Bow"
print("checks passed")
```

It prints `checks passed`. If either assertion fails, execution stops before that line. The message explains the intended game-related meaning. A bare `assert result` would tell you much less when it fails.

An **oracle** is the source of the expected answer. Here it is the explicit rule that a cost at or below the available budget is affordable. We are not asking the same implementation to generate both actual and expected answers. That would make a shared mistake harder to detect.

## 2. Test boundaries, not just comfortable examples

A **boundary** is where behaviour changes. For affordability, equality is the boundary between enough and not enough elixir. Test below it, at it, and above it.

```python
def can_afford(cost, elixir):
    return cost <= elixir

for elixir, expected in [(5, False), (6, True), (7, True)]:
    assert can_afford(6, elixir) is expected, "check the six-elixir boundary"
print("three boundary cases passed")
```

It prints `three boundary cases passed`. The table contains three input-output pairs. Adding twenty cases far above six would not replace the exact-equality case. Coverage should target ways the code could be wrong, not merely increase the number of assertions.

An **edge case** is an unusual but important input, such as an empty match list or a zero denominator. For a report, no decided matches must produce an unavailable rate, not an invented zero percent. Empty inputs deserve explicit expectations because many loops simply do nothing on them.

## 3. Separate setup, action, and assertion

**Setup** prepares the input. The **action** calls the code under test. The **assertion** compares the result with the expectation. Keeping these stages visible makes a failure easier to diagnose.

```python
def count_wins(rows):
    return sum(row.get("derived") == "WIN" for row in rows)

rows = [{"derived":"WIN"}, {"derived":"LOSS"}, {}]
actual = count_wins(rows)
assert actual == 1, "only the explicit WIN row should count"
print(actual)
```

It prints `1`. `sum` adds the boolean values because True contributes one and False contributes zero. That concise implementation is acceptable here because B10 introduced generator expressions. The expected value remains a separately understood fact about the three input rows.

Keep examples small enough to inspect by eye. A thousand generated records may be useful later, but a tiny example makes the reason for failure clear. If the test contains a complex reimplementation of the same algorithm, both sides can share the same mistaken assumption.

## 4. Recognise pytest's discovery rules

**pytest** is a testing tool installed in the course environment. It finds tests using naming conventions, commonly files named `test_*.py` and functions named `test_*`. It runs those functions and reports passed or failed checks.

```python
def can_afford(cost, elixir):
    return cost <= elixir

def test_exact_elixir():
    assert can_afford(6, 6), "exactly six elixir should afford X-Bow"

test_exact_elixir()
print("manual call passed")
```

It prints `manual call passed`. Defining a test function alone would print nothing and would not execute its assertions. Here we call it manually to make the example self-contained. Pytest's job is to discover and call such functions automatically.

The course runner is different: it appends exercise checks after your submitted code in the same temporary file. Consequently, exercise checks can call your functions directly. You do not need to create a new repository test file or run the entire ClashBot suite for these exercises.

Test discovery does execute imported test modules. Before running an unfamiliar suite, understand its setup and dependencies. A name beginning with `test_` is a convention, not a guarantee that the file has no side effects. Our examples stay local and tiny.

## 5. Check that an error is raised

Sometimes the correct behaviour is rejection. `pytest.raises` checks that code inside a block raises a specified exception. It fails if the expected exception does not occur.

```python
import pytest

def cost(value):
    if value < 0:
        raise ValueError("negative cost")
    return value

with pytest.raises(ValueError, match="negative"):
    cost(-1)
print("rejection checked")
```

It prints `rejection checked`. The `match` argument checks the exception message using a **regular expression**, a text pattern. The plain word used here simply matches that word in the message. More complex patterns are unnecessary for this exercise.

Be specific about exception types. Accepting any exception can let an unrelated NameError appear to satisfy a test for invalid input. Similarly, placing many operations inside the raises block can obscure which operation actually raised. Keep only the intended failing action there.

## 6. Plant a bug to check the test

A **planted check** deliberately supplies a known wrong implementation or input to verify that the test fails. This is a small form of **mutation testing**, where code is changed in a controlled way to challenge the test's sensitivity.

```python
def check_afford(fn):
    assert fn(6, 6) is True, "exact affordability must pass"

def broken(cost, elixir):
    return cost < elixir

try:
    check_afford(broken)
except AssertionError:
    print("planted bug detected")
```

It prints `planted bug detected`. A checker that tested only `fn(6, 10)` would accept the broken implementation. That would not prove the checker is useless for every purpose, but it would expose the missing boundary coverage.

The first interactive exercise asks you to write a checker rather than the affordability function. The exercise harness supplies both correct and deliberately broken functions. This reverses the usual perspective: your task is to make the evidence discriminate between behaviours.

Do not modify real project code to plant these bugs. The examples pass tiny functions as values. B05 taught functions, and B10 used them as sorting arguments. The same ability lets a test receive a candidate implementation without changing an operational file.

## 7. Preserve absent-option behaviour

A **regression** is a previously working behaviour that breaks after a change. An important project pattern is “absent option equals old behaviour”. If a new setting is not supplied, established code paths should retain their previous meaning.

```python
def choose_threshold(config, old=0.5):
    return config.get("tau", old)

print(choose_threshold({}))
print(choose_threshold({"tau":0}))
```

It prints `0.5` and `0`. An absent field and an explicit zero are different inputs. The tempting expression `config.get("tau") or old` would return the old value for zero, because zero is false in a boolean context.

A test should therefore cover absence, a nonzero override, and an explicit zero if zero is allowed by the contract. A **contract** is a clear statement of accepted inputs and promised behaviour. In this teaching helper, zero is allowed. A different real option may have a stricter range, so read its validation before borrowing the example's rule.

Preserving a threshold value is a narrow equality test. A stronger project claim such as byte-identical outputs requires comparing the actual output bytes under controlled conditions. Matching a single scalar does not establish an entire simulation or training run remained identical.

## 8. Check categories as well as totals

An **invariant** is a relationship expected to remain true across valid cases. In a match tally, the sum of exclusive category counts should equal the number of input rows. That is useful but incomplete.

```python
rows = [{"derived":"WIN"}]
wrong = {"WIN":0, "LOSS":1}
print(sum(wrong.values()) == len(rows))
print(wrong["WIN"] == 1)
```

It prints `True` and `False`. The total is correct despite the result being assigned to the wrong category. Use both a total invariant and category-specific checks. Otherwise a counter that swaps every win and loss could still pass.

For real data, avoid hard-coding today's row count. Read the current file in the checker, recompute the expected categories independently, and compare. If the file grows, a correct loader should still pass. Small fixed examples test precise semantics; live-file checks test compatibility with actual data. They serve complementary purposes.

A changing file can also change between two reads. These course exercises do not claim an atomic snapshot of concurrent writes. If a check fails while another process is modifying the source, investigate that timing rather than weakening the assertion to accept arbitrary missing records.

## In the real project

The syllabus points to `pipeline/tests/`. In `pipeline/tests/test_decision_options.py`, lines 33–37 contain:

```python
@pytest.mark.parametrize('kwargs', [{'card_ratio': 0}, {'card_ratio': 1.1}, {'card_T': 0},
                                    {'card_T': float('nan')}, {'spell_aim': 'tower_rule'}])
def test_invalid_options_fail(kwargs):
    with pytest.raises(ValueError):
        DecisionOptions(**kwargs)
```

This excerpt prints nothing by itself. Lines 1–2 use **parametrization**, asking pytest to run the test once per supplied dictionary. `float('nan')` creates **NaN**, a special floating-point value meaning “not a number”, useful for challenging numeric validation. Line 3 declares the test function and its varying input.

Line 4 requires a ValueError. Line 5 constructs the options object. The `**kwargs` spelling unpacks dictionary entries into named arguments: a dictionary containing `card_ratio` supplies that constructor argument. This is the first time you need to recognise that syntax; the exercise functions themselves do not require you to invent a general argument-forwarding system.

The test establishes rejection for the listed cases. It does not prove every possible invalid combination is rejected or that a valid option improves Icebow play. A good explanation keeps the test's claim proportional to its actual assertions.

## Common mistakes

- Testing only comfortable values and missing equality boundaries.
- Defining a test function without ever calling or discovering it.
- Catching any exception when one specific exception is required.
- Comparing totals while ignoring category assignments.
- Copying the implementation into the expected-answer calculation.
- Describing passing unit tests as proof of game performance.
