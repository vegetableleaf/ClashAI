## 1. A different shell, not a different Python

**PowerShell** is a shell and scripting language commonly used on Windows. A **cmdlet** is a command designed for PowerShell, usually named Verb-Noun. Get-Process retrieves information; Select-Object selects properties; Where-Object filters objects.

Python remains Python whether launched from Bash or PowerShell. The shell interprets your launch command first. Confusing those layers can make a correct Python program appear broken. A Bash assignment uses name=value. A PowerShell variable begins with a dollar sign, including during assignment.

Here is a PowerShell example shown in a bash-labelled block only for the course's code display. Run it in PowerShell, not Git Bash:

```bash
# PowerShell syntax
$runLabel = 'Icebow practice'
Write-Output $runLabel
```

**Output:** `Icebow practice`.

The comment names the required shell. Write-Output sends a value to the output stream. Our interactive course accepts only Python and Bash, so PowerShell snippets are reading examples. You will implement their selection logic in Python, which you already know from Part B.

## 2. Objects instead of lines

An **object** groups named properties with values. PowerShell pipelines usually carry objects. Bash pipelines usually carry text bytes. A displayed table is only a representation of those objects; it is not necessarily the underlying data.

Suppose a process record has Id, ProcessName, and CPU properties. Id identifies a process. ProcessName describes its executable name. CPU is accumulated processor time, not a percentage of current CPU use. Some properties may be unavailable.

```python
process = {"Id": 431, "ProcessName": "python", "CPU": 2.5}
print(process["Id"])
print(process["ProcessName"])
```

**Output:** `431` and `python`, on separate lines.

This Python dictionary is a teaching stand-in for a PowerShell object. It is not a query of your computer. Capitalisation here mirrors the PowerShell property names so you can compare the two languages.

Do not parse a displayed process table by counting spaces. Names, widths, and formatting can change. Select the properties while they are still structured objects. That is the same reason B06 used JSON parsing instead of slicing arbitrary character positions.

## 3. Filtering with a condition

A **filter** keeps records satisfying a condition. In PowerShell, Where-Object applies a condition to each incoming object. The expression `$_` means the current pipeline object. The comparison operator -eq means equality.

```bash
# PowerShell syntax; output varies with the current machine
Get-Process | Where-Object { $_.Id -eq 431 } | Select-Object Id, ProcessName
```

**Output:** a table containing Id and ProcessName for process 431 if it exists; otherwise no rows. There is no fixed process name or guaranteed row.

Read from left to right. Get-Process produces process objects. Where-Object retains the matching ID. Select-Object keeps two properties. Braces enclose the filtering script. A property is accessed with a dot, just like an attribute in B09.

The corresponding invented-data calculation is:

```python
rows = [{"Id": 431, "ProcessName": "python"},
        {"Id": 812, "ProcessName": "python"}]
selected = [row for row in rows if row["Id"] == 431]
print(len(selected))
```

**Output:** `1`.

Filtering by name would retain both rows. That is sometimes useful for inspection, but it is too broad to identify which experiment owns which process.

## 4. Selection and sorting

**Projection** means choosing properties from each record. It does not change the process itself. Sorting changes the order of displayed records. Neither operation establishes ownership.

```python
rows = [{"Id": 7, "CPU": 8.0}, {"Id": 3, "CPU": 1.0}]
ordered = sorted(rows, key=lambda row: row["CPU"], reverse=True)
print([row["Id"] for row in ordered])
```

**Output:** `[7, 3]`.

The lambda returns the value used for ordering, as in B10. Reverse=True requests largest first. In PowerShell, Sort-Object CPU -Descending performs the corresponding sort. A busy process deserves investigation, not automatic termination.

**Working set** means memory currently resident for a process. PowerShell exposes WorkingSet64 in bytes. Divide by 1024 twice to convert bytes into **MiB**, units of 1,048,576 bytes. This differs from a decimal megabyte.

```python
working_set = 52 * 1024 * 1024
print(working_set / (1024 * 1024))
```

**Output:** `52.0`.

Memory observations can change between queries. Report their time and unit. A process using little memory now may allocate much more while a simulator match is running.

## 5. Exact identity before an action

A **process identifier**, PID, is a number assigned by the operating system. It is not permanent. When a process exits, its ID may eventually be reused. A saved PID from yesterday does not prove identity today.

An **ownership record** is evidence linking a process to a run you launched. It can include PID, start time, and an explicit run label. Compare a fresh observation with that record before considering an action. If any required field is missing, report that identity is unverified.

```python
expected = {"Id": 431, "start": "10:00", "run": "toy"}
observed = {"Id": 431, "start": "10:05", "run": "other"}
same = all(observed.get(k) == expected[k] for k in expected)
print(same)
```

**Output:** `False`.

The equal PID alone was insufficient. The start time and run differ. The exercise will turn this comparison into a reusable function returning a boolean. That function will produce a review decision, not perform a stop.

PowerShell's Stop-Process cmdlet terminates a process. Its -Id parameter chooses an exact PID. Its -WhatIf option previews the requested action. We do not execute either here. Knowing the command's meaning helps you read operational instructions without treating an example number as an authorized target.

## 6. Missing records and stale observations

A process can finish between two observations. No result from a lookup may mean it ended normally, the ID was wrong, or the lookup failed. These are different explanations. Do not select another process merely because it has the same name.

```python
rows = [{"Id": 431, "run": "toy"}]
matches = [r for r in rows if r["Id"] == 999]
message = "not observed" if not matches else "observed"
print(message)
```

**Output:** `not observed`.

For a beginner's report, “not observed” is more precise than “crashed.” To diagnose a crash, combine process evidence with logs and expected completion markers. The stuck watcher does this by considering progress and elapsed time rather than reacting to every unusual line.

A **snapshot** is an observation at one moment. It becomes stale as the system changes. The snapshot in an exercise is fixed so tests are deterministic; the live laptop is not. Keep that difference explicit in your explanation.

## 7. Design a review function

The final exercise combines filtering, identity checks, and a human-readable result. Define a function that selects an exact ID, verifies its expected start and run, and returns either a review record or None. None means insufficient evidence, not permission to guess.

Use pure Python dictionaries so the function is easy to test. A **pure function** calculates a result without changing external state. It does not start processes, stop them, or modify files. Pure decision logic is a good place to learn operational concepts safely.

Test a matching record, a wrong ID, a reused ID, and missing fields. These are distinct failures. The ability to explain why each is rejected matters more than the number of lines in your solution.

This pattern also applies to ClashBot evaluation results. A row without a derived outcome is unknown. It must not silently become a loss just because the result is absent. Missing evidence should remain visible rather than being replaced by a convenient default.

## In the real project

From `scratchpad/gauntlet/L74/liveops/stuck_watch2.py`:

```python
NO_SHOT = ("GAVE_UP", "PROC_GONE", "STOP[adb_down]", "STOP[another_device]")   # a screenshot says nothing / adb is the problem
```

**Output:** none; this assigns a tuple.

The name identifies alert categories where the watcher avoids requesting a screenshot. The first category is a supervisor that gave up. The second is a missing process. The last two identify particular stop reasons. The comment explains that another observation would not help those cases. This is source reading, not a request to run the watcher.

From `.foreman/scratch/a2/COMMON.md`, a short exact excerpt:

> Stop processes by EXACT PID only

This is prose, so it prints nothing. “Stop processes” names an action. “EXACT PID” narrows its target. “Only” rules out broad name-based selection. Our teaching adds the preceding identity check because a PID alone can be stale.

Together these excerpts separate observation, diagnosis, and action. You can inspect a process without stopping it, and you can report an alert without deciding that a restart is appropriate. That separation keeps a practice exercise from interfering with the phone emulator.

## Common mistakes

- Pasting PowerShell syntax into a Bash exercise.
- Treating formatted tables as the underlying records.
- Confusing accumulated CPU time with current CPU percentage.
- Equating a process name with experiment ownership.
- Trusting an old PID without checking identity.
