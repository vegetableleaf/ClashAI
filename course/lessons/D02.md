## 1. Represent the world explicitly

A **simulator** is a program that approximates how a system evolves. A **state** is the represented information needed for its next update. In our first model, state contains tick, elixir, units, and tower_hp. The units field is a count, not a full list of troops. This simplification lets us focus on transitions. A **state transition** maps the current state and an action to the next state. A **model boundary** declares what is included and omitted: this model has no lanes beyond one route, no projectile travel, no targeting choices, and no real card statistics.

```python
state={'tick':0,'elixir':5,'units':0,'tower_hp':20}
print(sorted(state))
print(state['tower_hp'])
```

**Output:** `['elixir', 'tick', 'tower_hp', 'units']` and `20`.

Every field has a purpose. tick labels the observation; elixir controls affordability; units determines toy damage; tower_hp is the target's remaining health. Adding a field without explaining how it changes can create misleading complexity. Removing a needed field can make identical-looking states evolve differently for hidden reasons.

## 2. Define action and update order

An **action** is an input chosen by a player or policy. Our action is either 'deploy' or 'wait'. A **policy** is a rule for choosing actions from observations; later lessons introduce learned policies. Here we supply actions directly. The toy tick contract is: spend three elixir and add one unit if deploy is affordable; existing and newly added units each deal two damage; regenerate one elixir capped at ten; increment tick. Illegal deploy attempts behave like wait. These arbitrary numbers define a clear classroom model rather than real Clash Royale timing.

```python
state={'tick':0,'elixir':5,'units':0,'tower_hp':20}
new=dict(state)
new['elixir']-=3
new['units']+=1
new['tower_hp']-=2*new['units']
new['elixir']=min(10,new['elixir']+1)
new['tick']+=1
print(new)
```

**Output:** `{'tick': 1, 'elixir': 3, 'units': 1, 'tower_hp': 18}`.

The new unit attacks immediately under this toy rule. A different rule could delay its first attack, but that would define a different simulator. Fixing order now lets you explain every later transition. The source evidence will not validate these toy rules; it motivates the discipline of writing them explicitly.

## 3. Preserve the previous state

A **pure function** returns a result without changing caller-owned inputs or hidden external state. Pure transitions are easier to test because the same input gives the same output. dict(state) makes a **shallow copy**: it copies the outer dictionary but shares any nested mutable objects. Our first state contains only numbers, so this is sufficient. Later, when units are dictionaries inside a list, use explicit copies of nested objects or copy.deepcopy. A **deep copy** recursively duplicates nested mutable contents. It costs more, but our tiny teaching simulations prioritize clarity.

```python
from copy import deepcopy
old={'units':[{'hp':10}]}
new=deepcopy(old)
new['units'][0]['hp']=8
print(old['units'][0]['hp'])
print(new['units'][0]['hp'])
```

**Output:** `10` and `8`.

The old snapshot survives the update. If every replay entry referenced one changing dictionary, all entries could end up looking like the final frame. That bug can make debugging impossible: the supposed history has been overwritten. Test both returned values and preservation of inputs.

## 4. Determinism and controlled randomness

**Deterministic** means a specified input state and action produce the same next state under the same implementation. Randomness does not necessarily prevent reproducible replay: a pseudorandom generator is deterministic when its initial state and draw sequence are fixed. The **RNG**, random-number generator, is therefore part of the effective simulator state. A seed identifies the start, but taking one extra draw changes later draws. For a replay, record the seed and action order; for restoring halfway through, preserve generator state or restart from the beginning and repeat all earlier draws.

```python
import random
def damage_sequence(seed):
    rng=random.Random(seed)
    return [rng.randint(1,3) for _ in range(4)]
print(damage_sequence(9)==damage_sequence(9))
print(len(damage_sequence(9)))
```

**Output:** `True` and `4`.

randint includes both endpoints, unlike range's excluded stop. This minimal syntax is introduced here for the exercise. A deterministic random stream is still not evidence that it matches the game's RNG. CRFORGE_S0 records why the number and placement of random draws mattered in seed recovery.

## 5. Replay and invariants

A **replay** reconstructs a sequence by starting from an initial state and applying recorded actions in order. A **trace** is the saved sequence of observations. An **invariant** is a condition intended to hold after every transition, such as elixir staying between zero and ten and health never becoming negative. Replays should include a clear initial observation and then one new observation per step. Comparing the whole trace is stronger than comparing only final tower health: two incorrect trajectories could end at the same result. P04 will add moving units and a hand cycle while keeping this discipline.

```python
state={'tick':0,'elixir':0,'units':0,'tower_hp':20}
trace=[dict(state)]
for _ in range(3):
    state=dict(state)
    state['elixir']=min(10,state['elixir']+1)
    state['tick']+=1
    trace.append(dict(state))
print([s['tick'] for s in trace])
print(all(0<=s['elixir']<=10 for s in trace))
```

**Output:** `[0, 1, 2, 3]` and `True`.

The first trace element is tick zero, before any actions. Three updates create four observations. This off-by-one detail matters when a command at tick R becomes visible at R+1. A replay agreement test checks consistency; comparison with independent observations is needed for realism.

### Practice 2: Implement one step

Write step(state,action) with the declared order: affordable deploy costs 3 and adds a unit; every unit deals 2 tower damage; regen 1 capped at 10; increment tick. Clamp HP at 0. Example: initial state + deploy gives elixir=3,units=1,hp=18.

### Practice 3: Replay a fixed script

Using supplied step, write replay(start,actions), returning the initial state followed by each resulting state. Example: two actions produce three snapshots.

The final mutation check deliberately damages a returned snapshot. Earlier snapshots and the supplied initial state must survive.

### Practice 4: A local seeded RNG

Local randomness isolates this experiment from other code. The test's global-state check ensures your function does not unexpectedly change another component's stream.

### Practice 5: Validate invariants

Write valid(state), requiring integer tick>=0, elixir in [0,10], units>=0, and tower_hp>=0. Inputs contain all fields. Example: elixir=11 is invalid.

This separates a wrong calculation from a wrong assumption about the data. Next try a boundary case: an empty collection, zero elapsed time, a missing observation, or the smallest legal input for that function. Choose the case that actually belongs to its contract.

## Common mistakes

- Mutating the old state while claiming to preserve a replay snapshot.
- Leaving hidden information outside the state or recorded RNG.
- Changing update order halfway through the project.
- Using random global state without recording its seed.
- Calling a deterministic model accurate merely because it repeats.
