# I04 · Working with AI coding agents

**Time:** about 3 hours · **You will be able to:** write a bounded coding brief and independently verify an agent's scope, arithmetic, and evidence.

## Why this matters for ClashBot

An AI coding agent can help write a parser, summarize a log or implement a small test. In ClashBot, an incorrect count or an unnoticed change to decision logic can mislead later experiments even if the final message sounds confident.

`.foreman/scratch/a2/COMMON.md` explicitly treats agent output as a claim that must be checked. It also distinguishes mechanical work from decisions about design and live behaviour. We use that principle to practise giving precise tasks and reviewing results.

This lesson does not invoke another agent or ask one to operate the repository. Its interactive exercises work with synthetic briefs, path lists and outcome records. You learn the review method before applying it to a real collaboration.

## 1. A brief is an interface between people and tools

A **brief** states the task, allowed inputs, outputs, constraints and acceptance checks. An **acceptance check** is an observable condition that determines whether the requested result is complete. A vague request such as “improve the report” leaves too many decisions implicit.

A stronger request names the exact input file, output fields and data rule. For example: parse a supplied list of match records, count WIN and LOSS, preserve DRAW and unknown separately, and return a dictionary without writing files.

```python
brief = {
    "goal": "summarize supplied outcomes",
    "input": "in-memory match records",
    "output": "counts and decisive win rate",
    "constraint": "no file writes",
    "check": "all rows belong to exactly one bucket",
}
print(brief["check"])
```

It prints `all rows belong to exactly one bucket`. The check is concrete enough to fail if the parser loses records.

A brief should identify decisions the worker may make and decisions it must escalate. In a small coding task, choosing variable names is usually routine. Changing the outcome definition or deploying a model changes the task's meaning. Put those boundaries into the brief instead of relying on an implied understanding.

## 2. Specify ownership before requesting edits

A **scope boundary** states what the task may affect. A **write set**, introduced in I02, lists the exact output paths. In a shared checkout, another worker may be editing adjacent files. A successful local change can still be unacceptable if it overwrites unrelated work.

```python
allowed = {"course/lessons/H01.md", "course/exercises/H01.json"}
changed = {"course/lessons/H01.md"}
print(changed <= allowed)
```

It prints `True`. The subset operator checks that every changed path is allowed. It does not inspect content quality, so scope review and correctness review remain separate checks.

Use exact paths for a narrowly scoped task. A prefix check can be too permissive: a path beginning with a similar string may not belong to the intended directory. Resolve path semantics deliberately when building real tooling. The exercises use normalized repository-relative strings to keep the comparison transparent.

Also distinguish permission to edit from permission to stage, commit or publish. These are separate actions. A coding brief can authorize a reversible file change while leaving all repository-history actions outside scope.

When reviewing a change, inspect the actual changed files rather than trusting the worker's stated list. A polished summary can accidentally omit a generated artifact or unrelated cleanup.

## 3. Make the worker's numbers independently reproducible

**Independent verification** means deriving the result from the underlying evidence using a check that does not simply repeat the claim. If an agent reports 80% wins, dividing the reported 80 by 100 does not verify the original match counting.

Re-read the supplied records and apply the outcome rule yourself. Unknown values must remain separate. Test a fixture containing a missing result so the denominator rule is exercised, not merely mentioned.

```python
rows = [{"derived": "WIN"}, {"derived": "LOSS"}, {}]
wins = sum(row.get("derived") == "WIN" for row in rows)
losses = sum(row.get("derived") == "LOSS" for row in rows)
unknown = sum(row.get("derived") not in ("WIN", "LOSS", "DRAW")
              for row in rows)
print(wins / (wins + losses), unknown)
```

It prints `0.5 1`. Dividing by all three records would give one third, which is the planted error a reviewer should detect.

A **fixture** is a small controlled input used in a test. Fixtures let you specify the correct result by inspection. Real-data tests add a different kind of evidence: the implementation can handle the actual schema and current file contents.

Use both where appropriate. A real log containing only wins would not test the unknown-outcome branch. A synthetic fixture alone might miss the fact that the real log stores uppercase strings rather than nested result dictionaries.

## 4. Check the checker, not only the solution

An **oracle** is the rule used to decide whether a test passed. A weak oracle may approve incorrect work. For example, asserting that a returned rate lies between zero and one accepts many wrong denominators.

```python
wrong_rate = 1 / 3
print(0 <= wrong_rate <= 1)
```

It prints `True`. The range check is useful as a basic invariant but insufficient as a correctness test.

An **invariant** is a property that should always hold, such as wins plus losses plus draws plus unknown equalling the number of parsed records. Combine invariants with exact fixture expectations and negative controls.

A starter that already passes the tests may reveal that the tests do not require the learner to implement anything. In this course, checking both solution success and starter failure is an explicit quality requirement. It verifies the exercise's basic instructional contract.

A good review also checks whether the test exercises the implementation rather than a hard-coded answer. If a parser always returns a fixed historical count, a second fixture or a fresh recomputation should expose it.

Do not confuse test execution with test success. A command can run and exit nonzero. A final report should include the actual result and any unverified checks, not merely say that verification was attempted.

## 5. Give feedback that leads to a repair

A **reproduction case** is the smallest input that shows the defect. Good feedback names the expected behaviour, actual behaviour and relevant constraint. “This is wrong” gives little help; “a missing derived field is being counted as a loss” points directly to the failure.

```python
feedback = {
    "input": [{"derived": "WIN"}, {}],
    "expected": {"wins": 1, "unknown": 1},
    "problem": "missing outcome was counted as a loss",
}
print(feedback["problem"])
```

It prints `missing outcome was counted as a loss`. The feedback describes the observable defect without guessing which line caused it.

Ask for a focused repair and rerun the affected checks. Avoid adding unrelated cleanup to a bug-fix request, because extra changes make it harder to isolate the cause of a regression. A **regression** is a previously working behaviour that breaks after a change.

An agent's explanation can be useful even when its conclusion is wrong. Preserve the useful evidence, identify the unsupported leap and request the missing test. The goal is a correct, reviewable artifact rather than agreement with the worker.

A **handoff** should state what changed, what was checked, what remains uncertain and the next authorized step. For a research parser, it should also state input filtering, unmatched records and count totals. That enables another reviewer to reproduce the analysis without reading the entire conversation.

The project rule to re-tally agent-produced numbers is not a judgement about one particular model. It is a general engineering habit: generated code and confident prose still need observable evidence. The same habit applies when reviewing your own work.

## Practice plan

The first exercise validates a structured brief. The second checks that a reported write set is contained in an explicit allowlist. The third independently recomputes an outcome rate and compares it with a claim. The last exercise detects a planted wrong denominator.

For each, include a failing example as well as a passing one. A scope checker tested only on allowed paths could accidentally return True for every input. A numerical verifier tested only on one exact count could be hard-coded.

Finish by writing a short brief for a hypothetical agent to review your P07 report. Give it the measured counts, the outcome convention and the exact questions to check. Keep its authority to analysis only. The resulting brief should be understandable without access to your earlier conversation.

## Common mistakes

- Treating an agent's final summary as proof of its changes.
- Giving broad edit access when only two files are needed.
- Rechecking a percentage from the agent's own rounded percentage.
- Using only permissive range checks as correctness tests.
- Expanding a focused repair into unrelated cleanup.
