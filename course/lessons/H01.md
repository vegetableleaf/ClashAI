## Why this matters for ClashBot

ClashBot must choose whether to spend elixir now or keep it for defence. An X-Bow can look promising on the current board and still leave the bot unable to answer the next attack. Imitation learning, covered in part G, learns from recorded actions. Reinforcement learning asks what happened after the bot chose its own actions.

The trainer in `pipeline/rl_royale.py` connects decisions to match outcomes. The real bot eventually acts through a phone emulator, but this lesson uses only a small Python game. RoyaleSim and crforge model much more of Clash Royale than our toy does. A good result in our toy establishes that our calculations work, not that a live opponent can be beaten.

The match file `scratchpad/gauntlet/L74/loss_review/matches.jsonl` also matters here. Learning and evaluation both depend on what an outcome means. An unfinished or unlabelled match is not evidence of defeat. We will keep unknown outcomes visible instead of silently turning them into training labels.

## 1. Name the pieces before writing a loop

An **agent** is the decision maker. An **environment** is the system it interacts with. A **state** describes the environment at one moment. An **observation** is the information the agent receives about that state. The distinction matters in ClashBot: an emulator reader may miss a unit even when the unit exists in the game.

An **action** is a choice the agent makes, such as waiting or deploying X-Bow. A **reward** is a number returned after an action. An **episode** is one complete interaction, such as one match from its initial deal to the final result. A **policy** maps observations to actions or to probabilities of actions. These words describe roles; they are not Python classes you must import.

Our toy state has elixir and a clock. Waiting gains one elixir. Playing X-Bow costs six. We deliberately omit movement, towers and enemy actions for the first calculation. This is a teaching model, not a claim about real elixir regeneration.

```python
state = {"elixir": 5, "tick": 0}
action = "wait"
state["elixir"] = min(10, state["elixir"] + 1)
state["tick"] += 1
print(action, state["elixir"], state["tick"])
```

It prints `wait 6 1`. The cap prevents eleven elixir. The clock records one toy transition. A **transition** is the move from one state to the next, together with its action and reward.

## 2. Keep the rules separate from the policy

An environment should apply the rules even when the policy makes a poor choice. Otherwise an unaffordable X-Bow could appear for free and the learner could discover that bug. We use a pure function: it returns a new dictionary instead of changing its input. This makes replay checks easier.

```python
def step(state, action):
    elixir = state["elixir"]
    if action == "wait":
        elixir = min(10, elixir + 1)
    elif action == "xbow" and elixir >= 6:
        elixir -= 6
    else:
        raise ValueError("action is unavailable")
    return {"elixir": elixir, "tick": state["tick"] + 1}

start = {"elixir": 6, "tick": 0}
after = step(start, "xbow")
print(start["elixir"], after["elixir"])
```

It prints `6 0`. The original state still has six elixir. Raising an error makes an illegal request visible. A different environment could define an illegal move as waiting, but it would need to document that convention. Mixing the two conventions between training and evaluation changes the game.

A policy might always wait until six elixir and then play. That rule gives us a baseline to compare against, not something the real bot must obey. A learned policy can eventually use board information to decide when spending six is sensible.

## 3. Reward is immediate; return includes the future

A **return** adds rewards across time. A **discount factor**, usually written gamma, is a number between zero and one that reduces the contribution of later rewards. With rewards zero, zero, one and gamma 0.9, the first decision's discounted return is 0.81. It receives credit for the later win even though its immediate reward was zero.

```python
rewards = [0, 0, 1]
gamma = 0.9
total = 0.0
for t, reward in enumerate(rewards):
    total += gamma ** t * reward
print(round(total, 2))
```

It prints `0.81`. The first reward has exponent zero, so it is not discounted. Moving that exponent to one would discount every reward one extra time.

We often need the **return-to-go**, meaning the discounted sum starting at each decision. Work backwards: the last return is the last reward, and each earlier return is its reward plus gamma times the next return.

```python
running = 0.0
returns = []
for reward in reversed([0, 0, 1]):
    running = reward + 0.9 * running
    returns.append(running)
print([round(x, 2) for x in reversed(returns)])
```

It prints `[0.81, 0.9, 1.0]`. This recurrence avoids repeatedly adding the same suffix. H02 will compare these observed returns with predictions. For now, returns are arithmetic on rewards already collected.

Discounting also needs a time unit. A discount per recorded decision differs from a discount per simulator tick when decisions have unequal gaps. Our toy uses one transition per step. Do not copy its gamma into a production configuration and assume the same horizon.

## 4. Explore without confusing randomness with learning

**Exploration** means trying actions whose outcomes are uncertain. **Exploitation** means choosing what currently seems best. A deterministic rule can repeat the same mistake forever if it never tries an alternative. Random actions provide information, but random actions alone do not update a policy.

An **epsilon-greedy** policy chooses a random legal action with probability epsilon and its preferred action otherwise. This is a simple illustration; the later policy-gradient lessons sample from learned action probabilities instead.

```python
import random

rng = random.Random(7)
legal = ["wait", "xbow"]
epsilon = 0.0
action = rng.choice(legal) if rng.random() < epsilon else "wait"
print(action)
```

It prints `wait`. Epsilon zero disables exploration. We still create a local random generator so that other code cannot accidentally change its sequence. With nonzero epsilon, the distribution of many choices matters more than a single choice.

Legal actions depend on state. At five elixir, the legal list contains only waiting. Sampling first and checking affordability later can distort the action probabilities the trainer thinks it used. Record what was actually chosen from the legal set. H04 will explain why probability bookkeeping is essential for updates.

## 5. A result must be observed before it becomes a label

The live match file stores outcomes as strings in the `derived` field. The relevant observed values are `WIN`, `LOSS` and `DRAW`; missing or unrecognised values belong in an unknown bucket. This is a **data-cleaning** rule: transform raw records into a clearly defined analysis set before computing statistics.

For this course, decisive win rate is wins divided by wins plus losses. Draws are known outcomes, but are reported separately and excluded from that decisive denominator. If you want wins divided by all completed matches, label it differently and include draws explicitly. Never change denominator conventions halfway through a comparison.

```python
rows = [{"derived": "WIN"}, {}, {"derived": "DRAW"},
        {"derived": "LOSS"}]
counts = {"WIN": 0, "LOSS": 0, "DRAW": 0, "unknown": 0}
for row in rows:
    outcome = row.get("derived")
    bucket = outcome if outcome in ("WIN", "LOSS", "DRAW") else "unknown"
    counts[bucket] += 1
print(counts["WIN"] + counts["LOSS"], counts["unknown"])
```

It prints `2 1`. The missing result did not become a loss. With no decisive matches, use `None` for the rate: zero would falsely claim an observed zero-percent win rate. A small unknown count is still worth reporting because missingness may concentrate in crashes or difficult matches.

## Common mistakes

- Treating the observation as a perfect copy of the simulator state.
- Rewarding an illegal X-Bow because affordability was checked after deployment.
- Discounting the first reward by gamma instead of by one.
- Counting a missing outcome as a loss or a draw.
- Calling random action selection a trained policy.
