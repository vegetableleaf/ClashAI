# F01 · What learning means: data, model, loss, training

**Time:** about 3 hours · **You will be able to:** separate examples, predictions, targets, loss, and evaluation in a ClashBot learning task.

## Why this matters for ClashBot

ClashBot has to decide which Icebow card to play, where to place it, and when to act. A program can contain rules written by a person, or it can contain adjustable numbers learned from examples. Learning changes how those numbers are chosen; it does not remove the need to specify inputs, objectives, and checks.

The syllabus lists no source for F01. We use `pipeline/train_gen.py`, the generalist training program, and `scratchpad/gauntlet/L74/loss_review/matches.jsonl`, the real match report. They illustrate two different kinds of evidence: examples used to learn decisions and outcomes used to assess play. A better prediction score is not automatically a better live match result.

## 1. Begin with a question

A **prediction task** specifies what to estimate from available information. “Improve the bot” is too broad to be one prediction task. “Estimate the opponent's next card from the observed history” has a defined input and output.

A **feature** is a measured input to a model. Elixir, clock time, and tower HP can be features. A **target**, also called a **label**, is the answer associated with an example during learning. The opponent's next observed card can be a target for a next-card task.

```python
example = {"elixir": 8, "tower_hp": 1500, "next_card": "Tesla"}
features = [example["elixir"], example["tower_hp"]]
target = example["next_card"]
print(features, target)
```

**Output:** `[8, 1500] Tesla`.

These values are invented for teaching. If the task predicts the next card, including that same next_card field among the inputs would give away the answer. That mistake is **leakage**: information unavailable at the intended prediction time enters the model. F06 covers split-related leakage more fully.

## 2. A model is a rule with adjustable values

A **model** maps features to a prediction. A **parameter** is an adjustable value in that mapping. You already know functions, so start with a function whose multiplier can change.

```python
def predict(elixir, multiplier):
    return multiplier * elixir

print(predict(8, 0.5))
print(predict(8, 0.75))
```

**Output:** `4.0` and `6.0`.

The input remained eight. The parameter changed, so the prediction changed. This tiny numerical model is not an actual next-card predictor; it is a way to isolate what “adjustable” means.

Not all variables are learned parameters. A fixed arena size is part of the representation. A count of training examples describes the data. A chosen number of training steps controls the procedure. Distinguishing these roles makes training configuration files easier to read.

A **baseline** is a simple comparison method. For example, always predict the average target measured on training examples. If a complicated model cannot improve on a reasonable baseline, its extra machinery has not yet demonstrated value.

## 3. Loss measures a particular error

A **loss function** assigns a numerical penalty to a prediction compared with its target. Lower loss usually means better agreement under that chosen definition. It does not mean better in every possible sense.

For a numerical target, **squared error** is the difference squared. Squaring makes positive and negative errors contribute positively and penalises large errors more strongly.

```python
prediction = 6
target = 4
error = prediction - target
print(error, error**2)
```

**Output:** `2 4`.

The **mean squared error**, MSE, averages squared errors across examples. The mean makes the scale easier to compare when example counts differ, although the populations must still be comparable.

```python
predictions = [2, 4, 6]
targets = [2, 3, 5]
mse = sum((p-y)**2 for p,y in zip(predictions,targets)) / len(targets)
print(round(mse, 3))
```

**Output:** `0.667`.

Zip pairs values by position. Check equal lengths before using it in a reusable loss function: zip silently stops at the shorter input. An accidentally shortened target list could otherwise make a calculation look valid.

For category predictions, squared error is usually not the intended loss. F04 and F05 will introduce probability-based losses. This lesson keeps arithmetic simple so you can track the flow of information.

## 4. Training selects parameter values

**Training** is the procedure used to adjust a model using training examples. One simple training method is to try several parameter values and keep the one with the lowest training loss. You do not yet need calculus to understand this search.

```python
xs, ys = [1, 2], [2, 4]
candidates = [0, 1, 2, 3]
scores = {}
for weight in candidates:
    scores[weight] = sum((weight*x-y)**2 for x,y in zip(xs,ys))/len(xs)
best = min(scores, key=scores.get)
print(best, scores[best])
```

**Output:** `2 0.0`.

The search recovered the multiplier that exactly explains these invented examples. This is a complete tiny training procedure. It is inefficient for millions of parameters, but it clearly separates data, model, loss, and selection.

A **training algorithm** is the rule used to make these adjustments. Gradient descent in F03 is a more directed method. Neural-network training in F08 uses libraries to calculate many derivatives. Those later tools still implement the same broad loop: predict, measure error, adjust, repeat.

## 5. Generalisation means working beyond the examples

**Generalisation** means useful performance on examples not used to fit the model. A model could memorise training answers while failing on new matches. A zero training error alone cannot establish generalisation.

```python
memorised = {1: 2, 2: 4}
print(memorised.get(3, "unseen"))
```

**Output:** `unseen`.

This lookup table perfectly recalls two examples but says nothing about a third. A rule multiplying by two would extrapolate to three, but whether that rule is appropriate depends on the actual task and data.

A **held-out set** contains examples not used for parameter fitting. Evaluating on held-out examples asks whether the learned relationship extends beyond the training rows. F06 distinguishes validation used for choices from a final test kept separate.

Rows from the same match are related. Randomly separating individual frames can place nearly identical situations in both training and evaluation. Even before learning split procedures, remember that “different row” does not necessarily mean “independent evidence.”

## 6. Supervised learning and reinforcement learning

**Supervised learning** uses examples with targets. **Imitation learning** is a form of learning behaviour from demonstrations, such as predicting a human's card choice from the board they saw.

A human action is an observed label, not proof of the unique best move. Several placements may be sensible. High imitation accuracy therefore means agreement with the recorded demonstration under the measurement definition.

**Reinforcement learning** learns from interaction and a **reward**, a numerical feedback signal associated with behaviour or its outcome. A **policy** is the rule choosing actions from observations. In ClashBot, a policy can be evaluated by playing simulator matches, where its actions affect future states.

```python
rewards = [0, 0, 1]
print(sum(rewards))
```

**Output:** `1`.

This shows a simple total reward, not a complete reinforcement-learning algorithm. Part H will explain delayed credit, exploration, and policy updates. Here, notice that a match outcome does not directly tell us which earlier card choice caused it.

Imitation and reinforcement learning can cooperate. Demonstrations can provide an initial policy, then interaction can supply feedback. Neither removes the need to validate the simulator and measure the final system in its intended setting.

## 7. Clean the evidence before calculating

The live match log contains summary rows, not a ready-made supervised next-card dataset. Some rows have derived equal to WIN, LOSS, or DRAW. Others have no derived outcome. Exclude unknowns from outcome-based denominators and report them separately.

```python
rows = [{"derived":"WIN"},{"derived":"LOSS"},{}]
known = [r for r in rows if r.get("derived") in ("WIN","LOSS")]
unknown = sum(r.get("derived") not in ("WIN","LOSS","DRAW") for r in rows)
print(len(known), unknown)
```

**Output:** `2 1`.

Draws remain a separate known category. Our decisive win rate excludes them and says so explicitly. If another report uses a different draw convention, compare definitions before comparing percentages.

The real-data exercise reads the file once and keeps that snapshot in rows. Its tests recompute the counts from that same snapshot, so normal future appends do not create a hard-coded-count failure. The exercise prints only aggregate evidence.

## Common mistakes

- Putting the target among prediction-time inputs.
- Calling every configuration value a learned parameter.
- Treating low training loss as proof of generalisation.
- Assuming a demonstrated action is uniquely optimal.
- Counting missing outcomes as losses.
