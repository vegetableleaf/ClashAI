## Milestone 1 — define a strict result grammar

A **parser** converts text into structured fields. A **grammar** states which text forms are accepted. We accept only a complete standalone line containing a UTC timestamp, run name, explicit table version, the seat marker CLXIII W, and integer wins and total.

A **regular expression** is a pattern for recognizing text. Python's `re` module provides it. In our pattern, `\d+` means one or more digits, `\S+` means a non-whitespace word, and `(?P<name>...)` stores a matched piece under a name. Escaped square brackets match literal brackets. `fullmatch` requires the whole line to conform.

```python
import re
match = re.fullmatch(r"W (?P<wins>\d+) / (?P<total>\d+)", "W 3 / 5")
print(match.groupdict())
```

It prints `{'wins': '3', 'total': '5'}`. Convert the numeric strings to integers before arithmetic. A match with total zero or wins greater than total is invalid even if its text fits the pattern.

The full supplied pattern also extracts time, run and tables. We deliberately reject prose containing several results and records without explicit table labels. This loses some usable historical information, but it avoids silently attributing a version or seat. Report that selection rule.

## Milestone 2 — read the real log with an audit trail

An **audit trail** records what input was accepted and what was not. Read the named log as UTF-8 text, split it into lines, and call the parser on each nonblank line. Return accepted rows, nonblank line count and unmatched count.

```python
accepted = 2
unmatched = 3
nonblank = 5
print(accepted + unmatched == nonblank)
```

It prints `True`. This accounting check prevents unnoticed dropped lines. Unmatched text is not necessarily corrupt: it may be commentary, a failed evaluation message or an older result without the required metadata.

Do not print all unmatched lines. They are unnecessary for the numerical report, and a mixed operational log can contain unrelated details. Report counts and the parser rule. If a specific unmatched record needs investigation, inspect only the relevant safe fields.

The live-match data rule remains distinct. In `loss_review/matches.jsonl`, missing `derived` outcomes are unknown matches. Here an unmatched text line is an unparsed log line, not an unknown match. Never combine these counts into one denominator.

The tests reread the current file and verify accepted/unmatched accounting. They do not require a historical line count, because new evaluations may be appended.

## Milestone 3 — select one comparable pair

A **selection rule** determines which records enter the comparison. Use exact run and table labels. If more than one accepted record matches, select the latest UTC timestamp. With the fixed timestamp format used here, lexical string order matches chronological order.

```python
times = ["2026-10-29T15:00:00Z", "2026-10-29T14:00:00Z"]
print(max(times))
```

It prints `2026-10-29T15:00:00Z`. This shortcut requires the same timezone and fixed-width format. Do not extend it to arbitrary local-time strings.

Return None if a requested run is absent. Missing evidence is not a zero-win result. The final report should then say the comparison is unavailable, preserving which record is missing.

Do not average every checkpoint of arm B. Those checkpoints represent different stages of training and often overlapping evaluation conditions. Choosing the best observed checkpoint after seeing all results also introduces selection bias. Our historical reproduction names the specific update in advance.

Table matching does not prove same-build pairing. The engine provenance must be checked separately before interpreting the comparison as a controlled causal experiment. The capstone records this as an explicit limitation rather than guessing a build identifier.

## Milestone 4 — recompute rates and their intervals

For each selected aggregate line, compute CLXIII wins divided by its reported total. The log's total belongs to that evaluation's scoring convention. Do not relabel it as the decisive denominator from the separate live-match file without checking the evaluator's convention.

```python
wins, total = 18, 24
rate = wins / total
print(f"{rate:.1%}")
```

It prints `75.0%`. This synthetic example illustrates formatting. The real result must come from the selected row.

Compute a 95% Wilson interval for each marginal win proportion using the formula from H10. **Marginal** means considered individually rather than as a matched difference. These intervals communicate finite-sample uncertainty for each rate under the binomial model.

The two aggregate counts are insufficient to reconstruct a paired-difference interval. To do that, you need to know which seeds changed from loss to win and which changed from win to loss. Matching total counts alone does not recover the joint outcomes.

Also, simulator matches from different decks may not be identically distributed. The Wilson calculation is a useful descriptive summary here, while a full analysis should preserve the evaluation design and use the corresponding paired or clustered uncertainty method.

## Milestone 5 — compare from the correct seat

Calculate candidate CLXIII rate minus baseline CLXIII rate. Multiply by 100 to express **percentage points**. A negative difference means CLXIII won less often against the candidate opponent in this comparison.

```python
baseline = 0.8
candidate = 0.7
bot_delta_pp = 100 * (candidate - baseline)
print(round(bot_delta_pp, 1))
```

It prints `-10.0`. This is a ten-percentage-point decrease, not a ten-percent relative decrease. The relative decrease would be 12.5% of the baseline rate.

For a decisive no-draw interpretation, the opponent's win-rate change is the negative of the bot's change. The aggregate log alone does not establish how draws are scored, so the safest report says “CLXIII win rate decreased,” followed by the qualified interpretation that the opponent appears harder under that metric.

A **descriptive comparison** reports the observed difference. A **causal conclusion** attributes it to the training treatment. The latter requires control of alternative explanations and appropriate uncertainty. This capstone can complete the descriptive arithmetic without pretending those extra requirements are satisfied.

Use the sign and the seat in the output field names. A field called simply `improvement` is ambiguous. `clxiii_delta_pp` makes the calculation auditable.

## Milestone 6 — assemble the report and write it up

Return a report with baseline identity, candidate identity, common tables, both counts, both rates, marginal intervals, CLXIII difference and limitations. Include parser acceptance and unmatched-line counts from your real-data run.

The report should state that the source is an aggregate evaluation log and that per-match pairing has not been independently reconstructed. It should also distinguish an unavailable comparison from a completed comparison with an unfavourable result.

A teammate can act on a clear next step: obtain the pinned evaluation manifest and paired per-match records, then recompute the matched uncertainty. This is more useful than declaring the opponent training successful or failed solely from a rounded headline.

## Common mistakes

- Counting prose summaries again as new independent evaluations.
- Treating an incomplete W / line as zero wins.
- Reading CLXIII wins as opponent wins.
- Comparing table versions without a declared cross-version design.
- Constructing a paired confidence interval from marginal counts alone.
