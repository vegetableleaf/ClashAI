The calculations here are deliberately small models. They help you reason about state used by live emulator code and by RoyaleSim or crforge. They do not reproduce either engine's full timing rules. Later lessons distinguish measured game behavior from a teaching approximation.

## 1. Values have types

A **value** is a piece of information a program can use. A **type** describes what kind of value it is and what operations make sense for it. Python's **integer** type, `int`, represents whole numbers such as six elixir units or a count of plays.

A **floating-point number**, type `float`, represents a numeric approximation that can include a fractional part, such as `2.8` seconds. A **string**, type `str`, represents text. A **boolean**, type `bool`, represents one of two truth values: `True` or `False`.

```python
print(6)
print(2.8)
print("X-Bow")
print(True)
```

It prints `6`, `2.8`, `X-Bow`, and `True` on four lines. The spelling of booleans matters: Python capitalizes them, whereas JSON uses lowercase `true` and `false`. Neither spelling is an ordinary quoted string when used as a truth value.

The built-in `type` reports a value's type. You call it with parentheses just as you call `print`:

```python
print(type(6))
print(type("6"))
```

It prints `<class 'int'>` then `<class 'str'>`. You do not need to understand classes yet; B09 covers them. For now, read those displays as type labels. The two values need different treatment even though printing either alone would display `6`.

## 2. Give a value a name

A **variable** is a name referring to a value. **Assignment**, written with one equals sign, binds a name to the value of an expression. Read `elixir = 10` as "let elixir refer to ten," not as a mathematical question about equality.

```python
elixir = 10
xbow_cost = 6
remaining = elixir - xbow_cost
print(remaining)
```

It prints `4`. Python evaluates the right side of each assignment before binding the name on the left. The third line uses the values already assigned. The fourth prints the resulting value rather than the word `remaining`.

Choose descriptive names. `tower_hp` is clearer than `x` when you mean tower **hit points**, the quantity representing remaining durability. Use underscores between words; spaces are not allowed inside a Python variable name. Names are case-sensitive, so `elixir` and `Elixir` are different.

## 3. Assignment can update a value

A name can be assigned again. The new assignment replaces what that name refers to; it does not rewrite previous calculations automatically.

```python
elixir = 10
remaining = elixir - 6
elixir = 8
print(remaining)
print(elixir)
```

It prints `4` then `8`. `remaining` was calculated when `elixir` was ten. It is not a live formula that continuously tracks the other name. This matters when simulating a match: each update must be computed at the intended moment.

```python
elixir = 10
elixir = elixir - 6
print(elixir)
```

It prints `4`. The old value is read on the right, subtraction produces a new value, and then the name is rebound. This is not a contradictory equation. It is an ordered instruction to change program state.

**State** means the values describing a system at a particular moment. For our tiny model, state might be current elixir and tower HP. The real project has far more state, including units, positions, and timing information.

## 4. Arithmetic has rules

Python uses `+` for addition, `-` for subtraction, `*` for multiplication, and `/` for division. Division with `/` produces a float even when the numeric result is whole. Parentheses group calculations explicitly.

```python
print(6 + 4 * 2)
print((6 + 4) * 2)
print(6 / 2)
```

It prints `14`, `20`, and `3.0`. Multiplication takes precedence over addition unless parentheses change the grouping. **Precedence** is the rule determining which operations happen first. When a formula is unfamiliar, parentheses can make your intent easier to read.

`//` performs floor division, rounding the quotient downward. `%` gives the remainder. For nonnegative game quantities these are useful for dividing complete groups from leftovers:

```python
print(7 // 3)
print(7 % 3)
```

It prints `2` then `1`: seven contains two complete groups of three with one left. Do not use floor division when you need fractional elixir; it would discard information relevant to timing.

## 5. Model elixir with explicit units

A **unit** states what a number measures, such as seconds, elixir, or hit points. Units prevent meaningless arithmetic. Adding three seconds to six hit points is syntactically possible in Python but conceptually wrong.

For this lesson's simplified 1x regeneration model, one elixir arrives every 2.8 seconds. Treat elapsed time divided by 2.8 as continuous gained elixir. This deliberately ignores startup delays, discrete engine rounding, and phase transitions.

```python
seconds = 5.6
gained = seconds / 2.8
elixir = 3 + gained
print(elixir)
```

It prints `5.0`. The calculation adds two elixir to a starting value of three. The decimal display reflects the float calculation, not an extra half unit. B04 extends this approximation into repeated steps and phase multipliers.

Elixir is capped at ten in our model. The built-in `min(a, b)` returns the smaller value. It lets you express a cap without learning conditions yet:

```python
elixir = min(10, 9 + 5.6 / 2.8)
print(elixir)
```

It prints `10`. The uncapped result is eleven, but the cap limits stored elixir. The order matters: cap the regenerated amount before subtracting a play if your model says regeneration happens first.

## 6. Model tower damage with a floor

A **floor** is a lower bound. `max(a, b)` returns the larger value, so `max(0, hp - damage)` keeps a toy tower's remaining HP from becoming negative.

```python
tower_hp = 300
damage = 350
remaining_hp = max(0, tower_hp - damage)
print(remaining_hp)
```

It prints `0`. The damage value is illustrative, not a current card statistic. Real damage depends on game level and rules. Keeping an exercise's assumed numbers separate from verified game data prevents accidental misinformation.

Do not silently mix hit points with fractions of maximum HP. `0.5` could mean half health, but it is not half a hit point unless that is the chosen representation. Name fractional quantities clearly, such as `hp_fraction`, and write down the intended range.

## 7. Format a readable message

An **f-string** is a string prefixed with `f` that inserts expression values inside braces. It lets a report combine labels and numbers without confusing quoted arithmetic with evaluated arithmetic.

```python
card = "X-Bow"
cost = 6
print(f"{card} costs {cost} elixir")
```

It prints `X-Bow costs 6 elixir`. The braces mark places to evaluate expressions. They are not printed. The surrounding text remains literal.

A **format specification** controls how a value is displayed. `:.1f` asks for one digit after the decimal point:

```python
elixir = 3 + 1 / 2.8
print(f"Elixir: {elixir:.1f}")
```

It prints `Elixir: 3.4`. This changes the display, not the stored value. For repeated simulation, keep the more precise value and round only for reporting unless your model explicitly requires rounding state.

The built-in `round(value, digits)` produces a rounded numeric value. Binary floating-point cannot represent every decimal exactly, so tiny discrepancies are normal. Tests for calculations should compare with a small tolerance when needed. A **tolerance** is an allowed small difference; it is not permission for a conceptually wrong formula.

## In the real project

From `course/server.py`:

```python
TIMEOUT_S = 30
```

This real line prints nothing. `TIMEOUT_S` names the value. The equals sign assigns it. `30` is an integer. The `_S` suffix communicates seconds. Uppercase is a convention for a **constant**, a value intended to remain fixed during use; Python does not enforce that convention by capitalization alone.

Compare it with our `seconds` variable. Both are numbers with time units, but one limits how long an exercise may execute and the other models elapsed game time. Equal types do not make quantities interchangeable. Meaning still comes from names, documentation, and use.

## Plan the calculation before typing

For each exercise, list the given values, desired value, and units. Decide whether the answer should be text or numeric. Then calculate one example by hand. If the code disagrees, inspect assignment order and arithmetic grouping before changing the expected result.

For elixir, ask whether regeneration, capping, and spending happen in that order. For damage, ask whether remaining HP should be floored at zero. For reports, distinguish the stored number from its formatted display. These questions become even more important in full simulator code.

## Common mistakes

- Quoting a number needed for arithmetic.
- Reading assignment as an equality test.
- Assuming an earlier result updates when another variable changes.
- Rounding state repeatedly instead of formatting the final report.
- Mixing seconds, elixir, and HP because all are numeric.
