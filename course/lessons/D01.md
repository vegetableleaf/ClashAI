## 1. Time advances in ticks

A **tick** is one discrete update of a simulation. A **tick duration** says how much simulated time that update represents. We use 20 ticks per second in teaching examples, so one tick is .05 seconds. A **phase** is an interval in a match with a particular rule, such as an elixir multiplier. Do not confuse simulated time with wall-clock time, the real time your computer spends executing code. A thousand simulation ticks can run much faster than fifty real seconds. The conversion is simple arithmetic but must be stated at every interface.

```python
ticks_per_second=20
tick=60
print(tick/ticks_per_second)
print(1/ticks_per_second)
```

**Output:** `3.0` and `0.05`.

The first output is elapsed simulated seconds; the second is seconds per tick. When comparing logs, ask whether a timestamp identifies the state before or after that tick's update. SME documents that convention for its trace. We will make our own miniature convention explicit in D02.

## 2. Elixir is a bounded resource

A **resource** is a quantity spent by actions and replenished by rules. Elixir is bounded between zero and ten in our examples. Fractional regeneration must survive between ticks, so use floats in the teaching model. If one elixir takes 2.8 seconds at normal speed, a dt-second update adds dt/2.8 before capping at ten. Double and triple rates multiply that gain. The real engine may use integer units and rounded per-tick increments; the float formula is an approximation for learning, not a promise of exact parity.

```python
def regen(elixir,dt,multiplier=1):
    return min(10.0,elixir+dt*multiplier/2.8)
print(regen(5,2.8))
print(regen(9,2.8,2))
```

**Output:** `6.0` and `10.0`.

Capping matters because waiting at full elixir does not build an unlimited reserve. Spending and regeneration order also matters at a boundary. For the toy projects, spend at the start of a tick if affordable, then regenerate. If you choose the opposite order, document it and update tests accordingly; do not mix the two halfway through a replay.

## 3. A phase schedule is a rule

A **boundary condition** specifies what happens exactly when an interval changes. We use a deliberately simplified phase schedule: below 120 simulated seconds use multiplier one, from 120 up to 180 use two, and from 180 onward use three. This is a teaching rule, not a complete description of Clash Royale regulation, overtime, and mode-specific rules. A production model must obtain the correct schedule for its match mode and version. Test values just below, exactly at, and just above each boundary.

```python
def toy_phase(seconds):
    if seconds<120: return 1
    if seconds<180: return 2
    return 3
print([toy_phase(t) for t in [119.9,120,179.9,180]])
```

**Output:** `[1, 2, 2, 3]`.

The first condition excludes 120, so exactly 120 reaches the second branch. The second excludes 180, so exactly 180 reaches the last branch. Conditions are checked in order. An accidental <= changes the boundary and can create one incorrect tick, which may eventually alter a close battle.

## 4. Coordinates have units and orientation

A **coordinate system** defines how numbers describe positions. Our teaching tile board is 18 wide and 32 tall, with x increasing rightward and y increasing toward our side. Forward movement therefore decreases y. A **normalized coordinate** is scaled relative to a frame, often into zero through one. A **game unit** is an engine's internal distance unit; the SME passage states 1000 game units per tile for that comparison. Screen normalization, perspective, and camera offsets mean screen coordinates are not automatically normalized game coordinates. Conversions need a declared source and destination.

```python
game_x,game_y=4500,20500
print(game_x/1000,game_y/1000)
y=20.5
speed_tiles_per_second=2
print(y-speed_tiles_per_second*.5)
```

**Output:** `4.5 20.5` and `19.5`.

The first calculation converts game units to tiles only. It does not map a phone screenshot to the board. The second moves a unit forward one tile in half a second. Speed multiplied by time gives distance. For a whole-cell index, floor the tile coordinate only after checking that it lies inside the board.

## 5. Lanes and deck roles

A **lane** is a route between opposing towers. In a teaching grid, x<9 is left and x>=9 is right; this simplifies the centre and bridge geometry. A **win condition** is the main mechanism intended to damage the enemy tower enough to win. Icebow's X-Bow is a siege win condition: protect a useful lock while managing defense. Tesla is defensive infrastructure, Knight provides a durable body, Ice Wizard slows threats, Skeletons support cheap cycling, and Tornado repositions units. Rocket and The Log supply spell effects and damage. These roles explain why affordability and hand order matter, without hard-coding a strategy into the simulator.

```python
costs={'X-Bow':6,'Tesla':4,'Knight':3,'Ice Wizard':3,
       'Skeletons':1,'Tornado':3,'Rocket':6,'The Log':2}
print(len(costs))
print(costs['X-Bow']<=5)
print(sum(costs.values()))
```

**Output:** `8`, `False`, and `28`.

These are the lesson's base card-cost values. A **hand** is the currently available subset of cards; a **cycle queue** holds the cards that will return later. Affordability alone is insufficient if X-Bow is not in hand. P04 will implement a four-card hand and four-card queue, while explicitly leaving out special abilities and evolution mechanics.

## Guided practice and review

### Practice 1: Convert ticks to seconds

Write seconds(ticks,rate=20). Example: 60 ticks gives 3.0 seconds.

State the rate in a comment. A number like 60 without units could mean either one minute or three seconds.

### Practice 2: Regenerate with a cap

Write regen(elixir,dt,multiplier=1), using dt*multiplier/2.8 and cap 10. Example: regen(5,2.8,2)=7.

Multiplying the stored elixir would instantly create resources at a phase transition. Only regeneration speed changes.

### Practice 3: Phase boundaries

Implement toy_phase(seconds): 1 below 120, 2 below 180, else 3. Example: exactly 120 returns 2.

This exercise teaches executable boundaries. It deliberately does not certify a live match's phase schedule.

### Practice 4: Move forward on the board

Write forward(y,speed,dt), decreasing y and clamping at 0. Example: forward(20,2,.5)=19.

The clamp represents the toy destination. Real units have collision and targeting rules that are intentionally absent here.

### Practice 5: Check hand and affordability

Write legal(card,hand,elixir,costs), True only if card is in hand, has a supplied cost, and is affordable. Example: an affordable X-Bow outside hand is False.

A **short-circuit** Boolean expression stops evaluating once its result is determined. It prevents a missing-cost lookup from raising an error here. B04 introduced and; this example shows why condition order matters.

Before running a finished answer, trace a tiny input by hand. Record the values before the function runs, the value returned, and whether any input was changed. This separates a wrong calculation from a wrong assumption about the data. Next try a boundary case: an empty collection, zero elapsed time, a missing observation, or the smallest legal input for that function. Choose the case that actually belongs to its contract.

When a check fails, read the assertion message before changing the code. Recreate that input in isolation, print the intermediate quantities, and compare them with your hand calculation. Remove temporary debug prints when you understand the discrepancy. ## Common mistakes

- Confusing seconds with ticks.
- Multiplying normalized screen y directly into game y without a verified mapping.
- Moving forward by increasing y in the declared player-oriented board.
- Letting elixir exceed ten.
- Treating the toy phase schedule or toy unit statistics as production game rules.
