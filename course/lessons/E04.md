## 1. Why another language appears

Rust is a **compiled language**: a compiler translates source into executable instructions before the program runs. It checks types and many memory-use rules during compilation. Efficient native execution can help simulations perform many ticks, while compile-time checks can prevent some classes of memory mistakes.

Neither speed nor correctness follows automatically from the language name. A slow algorithm remains slow in Rust. A mathematically wrong damage formula may compile successfully. ClashBot still needs tests, measured timings, and comparisons against observations.

Think of the project as cooperating layers. Python coordinates experiments and learning. A simulator advances game state. An adapter connects the simulator's operations to Python. Different layers can use different languages while agreeing on shapes, units, and meanings.

A Python exercise can model those agreements without reproducing Rust's memory system. That is our goal: read interfaces accurately, then check the arithmetic and state expectations in a language you already know.

## 2. Function signatures

A **function signature** states a function's name, inputs, and output type. Rust introduces a function with fn. Each parameter is written name: type. An arrow introduces the return type.

```java
// Rust syntax, shown in a java-labelled display block
fn remaining(hp: i32, damage: i32) -> i32 {
    (hp - damage).max(0)
}
```

**Output:** none; this declares a function.

The display label does not change the language. Read the comment before copying any code. The course runner cannot compile Rust, so these snippets are for recognition. The equivalent Python is runnable:

```python
def remaining(hp, damage):
    return max(hp - damage, 0)
print(remaining(100, 30))
```

**Output:** `70`.

The Rust type **i32** is a signed 32-bit integer. The function accepts two such integers and returns another. Negative intermediate values are possible, although this function clamps its final result to zero.

The body ends with an expression without a semicolon. In Rust, the final expression can supply the return value. A semicolon would make it a statement instead. This difference is easy to miss when coming from Java, where statements commonly end with semicolons.

## 3. Let and mutability

Rust uses let to bind a name. A binding is immutable by default: you cannot later assign a different value to it. The word mut permits mutation.

```java
// Rust syntax
let cost: i32 = 6;
let mut elixir: i32 = 8;
elixir = elixir - cost;
println!("{}", elixir);
```

**Output:** `2`, inside a Rust function.

**Mutation** means changing existing state. In a simulator, advancing a tick usually mutates units, projectiles, and elixir. A helper calculating a coordinate may only return a value. Look for mut and assignments to help identify that difference.

Python does not enforce the same binding rule:

```python
cost = 6
elixir = 8
elixir = elixir - cost
print(elixir)
```

**Output:** `2`.

The same result does not mean the languages have identical guarantees. Our Python tests can check behaviour, but they cannot prove that an equivalent Rust program meets its compiler's borrowing rules.

## 4. Structures

A **struct** groups named fields into a type. It resembles a small class whose first purpose is carrying data. A simulator coordinate might group x and y; a unit record might group hit points and a side.

```java
// Rust syntax
struct Tower {
    hp: i32,
    side: i32,
}
```

**Output:** none; this defines a type.

The fields have declared types, and commas separate them. A Rust implementation block, written impl followed by the type name, can define associated functions and methods. You only need to recognise the boundary here; we are not building a Rust class library.

```python
tower = {"hp": 100, "side": 0}
print(tower["hp"], tower["side"])
```

**Output:** `100 0`.

The dictionary is a learning analogue, not an exact replacement. Rust checks field existence and types before running. A Python dictionary can gain arbitrary entries unless your own code validates them.

When reading a state structure, write down each field's unit and purpose. Two integer fields can represent entirely different things. Swapping tick and hp may still satisfy a type checker if both are i32, so semantic tests remain necessary.

## 5. Borrowing in plain English

**Ownership** is Rust's system for determining which value is responsible for stored data. A **borrow** temporarily accesses a value without taking ownership of it. An ampersand introduces a reference. A mutable reference, written &mut, allows changes through that reference under compiler-enforced rules.

A shared reference such as &BattleState means “read this state.” A mutable reference such as &mut BattleState means “access this state in a way that can change it.” These simplified descriptions help you read signatures; detailed lifetimes are beyond this introductory lesson.

```python
original = {"hp": 100}
branch = original.copy()
branch["hp"] -= 30
print(original["hp"], branch["hp"])
```

**Output:** `100 70`.

This example demonstrates separate data, not Rust borrowing. For nested Python state, a shallow copy does not necessarily separate nested objects. The branch may still share its lists with the original.

ClashBot's counterfactual simulations need independent states: exploring one move must not alter another branch. Rust's ownership tools help organise access, but correct snapshot and copying behaviour still needs an explicit contract and tests.

## 6. Results, options, and assertions

A calculation may fail or find no entity. Rust often represents these possibilities in types rather than using a magic number. **Option** means a value may be present or absent. **Result** means an operation may succeed or return an error.

The method expect extracts a successful or present value, otherwise stops with a diagnostic message. In a regression test, this can express an assumption that should hold. In an interactive application, a recoverable failure might need gentler handling.

```python
entities = {"knight": {"hp": 100}}
assert "knight" in entities, "The test setup should contain a Knight"
print(entities["knight"]["hp"])
```

**Output:** `100`.

This is an analogy for a checked assumption. It does not implement Rust's Option type. The assertion message explains which setup expectation failed, making the failure useful.

A **regression test** checks behaviour that should remain correct after a change. A **planted failure** deliberately introduces a known error to verify that the test detects it. A test that passes even when the intended bug is present does not protect the intended rule.

## 7. Integer arithmetic and damage stages

A simulator can apply integer reductions at multiple stages. Rounding after each stage may differ from rounding only once at the end. Write out intermediate values rather than combining formulas prematurely.

```python
damage = 133
first = damage * 40 // 100
second = first * 40 // 100
print(first, second)
```

**Output:** `53 21`.

These values explain the historical test's motivating example. They are not a universal rule for every card or every game version. The test has a specific setting and target.

The exercise asks you to implement sequential integer reductions. It does not ask you to decide whether that rule belongs in a different engine. That decision would require evidence beyond a short lesson.

A useful debugging table has initial damage, first reduction, second reduction, and final HP. If the final answer differs, identify the first stage that diverges. This is much more informative than simply declaring “the damage is wrong.”

## In the real project

From `scratchpad/gauntlet/L74/parity/diag_night/r7c/fork/buff_pulse_reduction.rs`:

```java
// Rust source
fn n(x: i32, y: i32) -> Vec2 {
    Vec2::new(x * K, y * K)
}
```

**Output:** none; this defines a coordinate helper.

The signature receives two signed integers and returns Vec2, a two-coordinate type. The second line constructs that value after scaling each coordinate by K. The final brace ends the function. The block's first comment is an explanatory display label; the three function lines are the exact source excerpt.

A second excerpt from the same file:

```java
// Rust source
    for _ in 0..40 {
        assert!(s.debug_set_pos(blue, at));
        s.tick();
    }
```

**Output:** none on successful test execution; a failed assertion interrupts the test.

The loop visits forty values; the upper endpoint is excluded, like Python range(40). The underscore says the loop variable is unused. The assertion requires position-setting to succeed. The next line advances one tick. The brace closes the loop body.

The exclamation mark denotes a **macro**, a construct that expands code during compilation. For this lesson, recognise assert! and println! as familiar assertion and printing operations. You do not need to write your own macro.

## Common mistakes

- Treating Rust examples as Java because of the display label.
- Adding a semicolon to a returned final expression.
- Assuming an integer type tells you its unit.
- Treating shallow copies as independent nested simulator states.
- Assuming compilation alone proves the game rule.
