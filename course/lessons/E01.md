## 1. A shell starts programs

A **shell script** is a text file containing shell commands. Bash reads it in order. In A02 you used individual commands; now we combine them. Unlike Python, Bash treats many words as program names and arguments, not expressions. An **argument** is a piece of information passed to a command.

Run lesson examples in Git Bash. The interactive runner starts Bash for you. Each exercise starts a fresh process, so a variable created in one exercise is unavailable in the next. Predict the output before running each example.

```bash
printf '%s\n' 'Icebow experiment' '20 seeds'
```

**Output:** two lines, `Icebow experiment` and `20 seeds`.

The **format string** `%s\n` tells printf to print a string followed by a newline. Repeated arguments reuse the format. Prefer predictable formatting for machine-readable output. Keep human commentary separate from records that another program must parse.

## 2. Assignment and expansion

A **shell variable** stores text. Assignment has no spaces around the equals sign. A dollar sign asks Bash to replace a variable reference with its value; this is **expansion**.

```bash
run='icebow trial'
seeds=20
printf '%s: %s\n' "$run" "$seeds"
```

**Output:** `icebow trial: 20`.

Writing spaces around the assignment asks Bash to execute a command instead. Numbers are normally text too. Use **arithmetic expansion**, written with double parentheses after a dollar sign, for integer arithmetic.

```bash
wins=12
losses=8
printf '%s\n' "$((wins + losses))"
```

**Output:** `20`.

Integer division drops the fractional part. Calculate confidence intervals in Python, as in C05, rather than trying to make Bash a statistics language. Let each program do a small job with a clear input and output.

## 3. Quoting preserves an argument

**Quoting** controls which characters Bash interprets. Single quotes preserve literal text. Double quotes allow variable expansion while preserving spaces inside the resulting value. Unquoted expansion can split one value into several arguments and expand wildcard characters.

```bash
run='Icebow trial'
printf '<%s>\n' "$run"
printf '<%s>\n' '$run'
```

**Output:** `<Icebow trial>`, then `<$run>`.

The first command receives one name containing a space. The second receives the literal dollar sign and letters. Think of quotes as protecting boundaries, not decoration. Paths with spaces need the same protection.

A useful debugging habit is to print each intended argument on its own line inside angle brackets. If a supposed single path becomes two lines, investigate quoting before investigating Python. It is possible for the Python program to be correct but receive the wrong inputs.

## 4. Positional arguments and functions

A **positional argument** is identified by position: the first is dollar-one, the second dollar-two. A **function** groups shell commands under a name. Within a function, positional arguments refer to that function's inputs.

```bash
describe() {
  printf 'run=%s seeds=%s\n' "$1" "$2"
}
describe 'Icebow trial' 20
```

**Output:** `run=Icebow trial seeds=20`.

Braces surround the function body. The closing brace needs its own line or a preceding semicolon. Unlike Python, indentation helps humans but does not define the body.

The special expression `"$@"` expands to all arguments while keeping their boundaries. The command shift removes leading positional arguments. A launcher can consume a run name and worker count, then forward the remaining options.

```bash
show_tail() {
  shift 2
  printf '%s\n' "$@"
}
show_tail trial 2 'seed=7' 'note=two words'
```

**Output:** `seed=7` and `note=two words`, on separate lines.

The exercise functions receive all required inputs. A larger command-line tool should also validate missing arguments before consuming them. A run name accidentally interpreted as a worker count is an input error, not evidence that the simulator is broken.

## 5. Exit status and decisions

An **exit status** is an integer reporting whether a command succeeded. Zero means success; nonzero means failure. This differs from Python's truth value of zero. Bash if checks a command's status, not whether printed text says “OK.”

```bash
if test 8 -ge 6; then
  printf '%s\n' 'X-Bow affordable'
else
  printf '%s\n' 'wait'
fi
```

**Output:** `X-Bow affordable`.

The test command's -ge operator means integer “greater than or equal.” The closing fi ends the conditional. Square brackets are an alternative spelling of test; spaces around those brackets matter.

```bash
false
status=$?
printf 'status=%s\n' "$status"
```

**Output:** `status=1`.

Dollar-question-mark holds the previous command's status. Capture it immediately, because another command replaces it. Inside a function, return 1 reports failure to its caller. Exit 1 ends the entire script. A failed simulator must not silently become a zero-win result.

## 6. Loops and pipelines

A **loop** repeats commands. Bash for visits words, often run names or seed numbers.

```bash
for seed in 0 1 2; do
  printf 'seed=%s\n' "$seed"
done
```

**Output:** `seed=0`, `seed=1`, and `seed=2`.

A **pipeline** connects one command's standard output to another command's input. **Standard output**, or stdout, is the normal result stream. **Standard error**, stderr, carries diagnostics. They are separate unless explicitly combined.

```bash
printf '%s\n' WIN LOSS WIN | grep -c '^WIN$'
```

**Output:** `2`.

The anchors mean start and end of a line. This works for deliberately simple text. It is not a JSON parser. Decode real match records with Python's json.loads; a string can contain WIN without being the match outcome.

By default, a pipeline usually reports its last command's status. The setting `set -o pipefail` makes an earlier stage's failure visible. The separate setting set -e has exceptions in conditionals and pipelines; it does not replace understanding which failures you check.

## 7. Background work and waiting

A **background job** runs while the shell continues. An ampersand starts a command in the background. Dollar-exclamation-mark records the most recent background process ID, or **PID**. The wait command waits for that particular child and returns its status.

```bash
printf '%s\n' 'toy worker finished' &
child=$!
wait "$child"
printf '%s\n' 'collector ready'
```

**Output:** `toy worker finished`, followed by `collector ready`.

Launching is not finishing. A collector must wait before reading results. With several jobs, store every PID and check every wait. File existence does not prove a completed experiment: the file may be empty or partially written.

Parallel workers should write separate temporary files. A parent can collect those files in seed order after successful waits. This avoids scrambled JSON lines and identifies missing seeds. P05 develops this arrangement using just two workers at once.

## In the real project

From `scratchpad/gauntlet/L74/plan1026/opp/learner/launch_arm.sh`:

```bash
P=$1; RUN=$2; CPUS=$3; PY=$4; CFG=$5; shift 5
```

**Output:** none; assignments are shown for reading, not standalone execution.

Read left to right. P takes the first input. RUN takes the run name. CPUS receives the CPU selection. PY receives the interpreter path. CFG receives the configuration path. Semicolons separate commands on one line. Finally, shift 5 leaves only optional overrides. This is why argument order matters.

From `scratchpad/gauntlet/L74/plan1026/opp/learner/arm_d3.sh`:

```bash
for U in "$@"; do
  N=${RUN}_u$U
```

**Output:** none; this is the beginning of a larger loop, shown for reading only.

Line one iterates over each remaining update argument without splitting it. Line two constructs a checkpoint label from the run name and update. Braces distinguish the variable name RUN from the following suffix. The rest of the loop performs operational work; this excerpt only teaches its naming and iteration pattern.

The scripts separate launching training from evaluating saved updates. Reading that division helps you avoid treating “job started” as “experiment passed.” A meaningful report also needs engine and table versions, opponent, seed set, completed outcomes, and uncertainty.

For live-log analysis, missing derived results are unknown, not losses. Draws also need their own category. The decisive win rate uses wins divided by wins plus losses. A Bash launcher should preserve those categories by passing structured records to a Python summariser rather than manufacturing a denominator from the number of file lines.

## Common mistakes

- Adding spaces around assignment and accidentally calling a command.
- Using an unquoted path containing spaces.
- Treating printed success text as a reliable exit status.
- Collecting output before workers finish.
- Counting raw text instead of parsing structured records.
