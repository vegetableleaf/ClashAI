# H03 · Policy gradients

**Time:** about 6 hours · **You will be able to:** derive a two-action policy gradient and run a tiny REINFORCE update with a detached baseline.

## Why this matters for ClashBot

ClashBot's policy assigns probabilities to decisions. Training must increase the probability of useful decisions without pretending that a simulator's discrete card deployment is differentiable. A gradient cannot travel through a Python branch that declares which tower fell.

The trainer in `pipeline/rl_royale.py` instead differentiates action log probabilities. The simulator supplies rewards; the neural network supplies differentiable probabilities. This separation is the central idea of policy-gradient learning.

The examples use wait versus deploy as toy actions. They do not establish that deploying X-Bow is always good. A real Icebow match contains defensive placements, cycle management and opponents whose responses change the future. We begin with one decision so the learning signal can be checked exactly.

## 1. Write the objective before the update

A **policy gradient** is the derivative of expected return with respect to policy parameters. A **parameter** is a learned number, such as a network weight. Write the expected reward for two actions explicitly before using a neural network.

Suppose deploy returns +1 and wait returns -1 in a one-step toy situation. Let p be the probability of deploy. The **objective**, the quantity we want to increase, is J = p * 1 + (1 - p) * -1 = 2p - 1.

```python
p = 0.6
expected_reward = p * 1 + (1 - p) * -1
print(round(expected_reward, 2))
```

It prints `0.2`. Raising p by 0.01 raises expected reward by 0.02. This conclusion depends on this toy reward table. If an opponent punishes the deployment, the reward table changes and so does the desirable update.

The model often stores a **logit**, an unrestricted score converted to a probability. For two actions we can use p = sigmoid(theta). From part F, sigmoid's derivative is p(1-p). The chain rule therefore gives dJ/dtheta = 2p(1-p). At p = 0.5, the gradient is 0.5.

## 2. Move the derivative onto a log probability

For a discrete action a, write expected reward as a sum over actions: J = sum_a pi(a) R(a). Differentiating gives sum_a grad pi(a) R(a). The identity grad pi(a) = pi(a) grad log pi(a) rewrites this as an expectation of R(a) grad log pi(a).

This is the **score-function estimator**. We sample an action, observe its reward, and multiply that reward by the gradient of its log probability. We do not differentiate the reward-producing environment. In a full episode, **REINFORCE** uses sampled returns in this construction.

```python
import math
p_deploy = 0.5
reward = 1.0
loss = -math.log(p_deploy) * reward
print(round(loss, 4))
```

It prints `0.6931`. The minus sign turns a quantity we want to increase into a **loss** that an optimizer minimizes. For a positive return, reducing this loss raises the sampled action's probability. For a negative return, it lowers that probability.

A log probability is negative for probabilities strictly between zero and one. A negative log probability does not imply a negative training signal. The return and the overall minus sign determine the update direction.

## 3. Verify the direction with autograd

PyTorch's **autograd** records operations on tensors and calculates their derivatives. Part F introduced it; here we use it to check the sign of a policy update. A single logit represents the deployment preference.

```python
import torch
theta = torch.tensor(0.0, requires_grad=True)
p = torch.sigmoid(theta)
loss = -torch.log(p) * 1.0
loss.backward()
print(round(theta.grad.item(), 2))
```

It prints `-0.5`. Gradient descent subtracts the gradient, so theta increases. That raises the deployment probability. If you remove the minus sign from the loss, descent would move the policy away from a rewarded action.

A **Categorical distribution** represents several discrete actions with probabilities that sum to one. It can sample an action and calculate that action's log probability. For a neural policy, passing logits lets PyTorch perform the stable probability calculations.

```python
import torch
dist = torch.distributions.Categorical(logits=torch.tensor([0.0, 0.0]))
print(round(dist.log_prob(torch.tensor(1)).item(), 4))
```

It prints `-0.6931`. Action indices are integers; index one is deploy in this example. The action meaning must remain consistent between collection and training. Swapping the indices can produce a numerically valid update for the wrong behaviour.

## 4. Subtract a baseline without changing the target

H02 introduced advantages. Replacing return by return minus a state-dependent baseline can reduce gradient variance. Why does this leave the expected gradient unchanged? The baseline term sums to b(s) * sum_a grad pi(a|s), and probabilities sum to one. The derivative of one is zero.

That argument assumes the baseline does not depend on the sampled action in a way that breaks the cancellation. A value estimate computed from the state before choosing the action is the usual example. A reward copied from the sampled outcome is not such a baseline.

When the baseline is produced by a neural network, **detach** means treat its numerical value as constant for this particular loss. Without detaching, the policy loss can change the value prediction merely to reduce its own loss.

```python
import torch
logp = torch.tensor(-0.7, requires_grad=True)
value = torch.tensor(0.2, requires_grad=True)
advantage = (torch.tensor(1.0) - value).detach()
loss = -(logp * advantage)
loss.backward()
print(round(logp.grad.item(), 1), value.grad)
```

It prints `-0.8 None`. The policy loss changed the log-probability gradient but did not train the value estimate. A separate value loss can train that estimate. Shared network layers require additional care, but the distinction between the two losses remains.

## 5. One sample is noisy; a batch is evidence

A **batch** is a collection of sampled transitions used together for an update. Averaging their policy losses reduces sensitivity to any single lucky outcome. It does not remove biased data, a simulator exploit or a broken observation pipeline.

For an episodic toy game, collect actions and their log probabilities, compute returns-to-go, then average negative log probability times detached advantage. Clear old gradients before backpropagation, and take one optimizer step. The exercises use a one-step reward table to keep the entire run tiny.

```python
import torch
logp = torch.tensor([-0.7, -0.2])
advantages = torch.tensor([1.0, -1.0])
loss = -(logp * advantages).mean()
print(round(loss.item(), 2))
```

It prints `0.25`. A scalar loss is not a win rate. A lower policy loss on the current batch does not necessarily imply better performance on fresh episodes. Report an evaluation reward separately.

For exact debugging, compare the expected sampled estimator with the analytic gradient. At p = 0.5, deploy's score derivative is 1-p = 0.5. Wait's score derivative is -p = -0.5. Weight each by its reward and probability: 0.5 * 1 * 0.5 + 0.5 * -1 * -0.5 = 0.5. This equals the earlier derivative.

In longer matches, returns depend on subsequent actions, and the policy's state distribution also changes. The same estimator principle extends to trajectories, but variance grows. This motivates the baselines from H02 and the bounded update objective in H04. Do not solve noisy learning by selecting only winning episodes; that changes the sampling distribution and discards necessary counterevidence.

## In the real project

The syllabus gives no source path for H03. We use these real lines from `pipeline/rl_royale.py`:

```python
    lp_new = t["lp_gate"] + t["lp_card"] + t["lp_cell"]
    A, w = B["A"][idx], B["w"][idx]
```

The first line adds log probabilities for the recorded decision components. Adding logs corresponds to multiplying conditional probabilities. The second retrieves stored advantages and weights for the selected rows. Here `idx` selects a minibatch. Neither line prints anything.

This is production PPO bookkeeping, not a plain REINFORCE implementation. We cite it to locate the same ingredients: differentiable log probabilities and numerical advantages. H04 adds the old-policy ratio and clipping. Our exercises avoid importing the production module, so they run with only the course's CPU PyTorch installation.

A card component alone is not necessarily the probability of the whole action. If timing or placement is sampled too, record the corresponding probability under the same decoding rules. Otherwise training can attribute an outcome to a different distribution from the one that generated it.

## Practice plan

In the first exercise, derive the analytic gradient and check it at the symmetric policy. In the second, implement the scalar policy loss for both positive and negative advantages. In the third, use autograd to verify that the baseline receives no gradient from the policy objective.

The final exercise trains a tiny two-action policy from sampled rewards. Set the seed and restrict PyTorch to one CPU thread. Use only a few dozen small batches; there is no need for a simulator process, a checkpoint file or an emulator. Return the learned deployment probability and compare it with the initial probability.

The deterministic seeded result is a software check. It is not a claim about general reinforcement-learning reliability. If the toy fails, inspect the action mapping, minus sign, cleared gradients and reward assignment before increasing the number of updates. More compute cannot correct a reversed objective.

## Common mistakes

- Differentiating a Python reward branch instead of the action log probability.
- Forgetting the minus sign when using an optimizer that minimizes loss.
- Allowing the policy objective to backpropagate into its baseline target.
- Using only winning episodes to make a batch look cleaner.
- Reporting training loss as though it were held-out win rate.
