## Why this matters for ClashBot

ClashBot combines research code with components that can interact with an account and a phone emulator. A lesson about reading logs should not accidentally become an account operation. The same distinction applies to sharing a report: useful aggregate results do not require copying private configuration.

The syllabus points to `.gitignore`. Its public cache and virtual-environment rules provide a safe way to explain what Git ignores and what it does not protect. We inspect only those harmless lines, not private files or authentication values.

The exercises use invented dictionaries and path strings. They practise allowlisting, minimal reporting and incident-response decisions without opening any private material. A successful result is code that handles the synthetic examples correctly, not a claim that the entire repository has been audited.

## 1. Treat private authentication material as authority

A **credential** is information that grants access to an account or service. Its sensitivity comes from what someone can do with it, not from whether its filename looks important. A credential copied into a report can be reused by someone who receives that report.

A **secret** is information intended to remain private. Authentication material is one example; private account information can also deserve restricted handling. The course never needs real values to explain the principle.

```python
record = {"wins": 12, "private_auth": "SYNTHETIC_PLACEHOLDER"}
public_report = {"wins": record["wins"]}
print(public_report)
```

It prints `{'wins': 12}`. The invented placeholder never enters the output. The safest reporting design selects needed fields before formatting rather than printing everything and hoping to remove sensitive text afterwards.

A **data-minimization** rule keeps only what the task requires. For a win-rate report, counts, filtering rules and evidence identifiers are usually sufficient. Full account settings are unrelated to the calculation and should not be loaded just because they are nearby.

Do not use real authentication material as a test fixture. A synthetic marker tests whether a field is omitted without creating an exposure. A test should verify behaviour, not reproduce the very incident it is supposed to prevent.

## 2. Prefer an allowlist to an ever-growing denylist

An **allowlist** names the items explicitly permitted. A **denylist** names items explicitly forbidden. For a narrowly scoped report, an allowlist is often simpler to review because new unexpected fields remain excluded by default.

```python
record = {"wins": 3, "losses": 1, "internal_note": "private"}
allowed = ("wins", "losses")
report = {name: record[name] for name in allowed if name in record}
print(report)
```

It prints `{'wins': 3, 'losses': 1}`. Adding another field to the input will not automatically publish it. The code's output contract remains small.

The same idea applies to file reads. If an exercise needs one named public log, read that path. Do not search every nearby folder for something that looks useful. Restricting input scope improves both privacy and reproducibility: a newly added unrelated file cannot silently change the result.

A path allowlist should use exact normalized paths or carefully resolved directory containment. A naive string prefix can accept a similarly named sibling. Our exercise compares explicit repository-relative names and does not open them, so the rule is easy to inspect.

Allowlists do not solve every security problem. A permitted field can itself contain inappropriate content if the schema changes. Keep the allowed fields narrow, validate their types and avoid treating arbitrary text as executable instructions.

## 3. Understand what ignoring files actually does

A **Git ignore rule** tells Git which otherwise untracked paths to omit from ordinary discovery and addition behaviour. It is a convenience for generated or local files. It is not encryption, an access-control system or a way to erase already recorded history.

A **tracked file** is a file already recorded in Git's index or history. Adding an ignore pattern does not automatically remove such a file from tracking. This distinction matters when responding to an accidental inclusion.

For teaching, represent the decision with two Boolean values: whether a path matches an ignore pattern and whether it is already tracked.

```python
matches_ignore = True
already_tracked = True
hidden_from_tracking_by_rule = matches_ignore and not already_tracked
print(hidden_from_tracking_by_rule)
```

It prints `False`. The expression is a simplified model of the principle, not a complete implementation of Git's pattern rules.

Virtual environments and caches are commonly ignored because they are generated and large. That says nothing about whether every ignored file is private or every tracked file is safe to share. Review content and task scope independently.

Do not run staging or history-rewriting commands as part of a course exercise. The lesson can teach the concepts through pure functions and synthetic states. Actual repository repair is a separate task with a specific scope and owner.

## 4. Respond to an exposure without spreading it

An **exposure** occurs when private material reaches an unintended audience or location. **Revocation** disables an old credential. **Rotation** replaces it with a new one. Removing a visible copy does not establish that no one copied it before removal.

For an actual credential exposure, the responsible owner should disable the exposed credential through its issuing service, replace dependent configuration as appropriate and assess where copies may remain. The course teaches this response order without handling any actual value.

```python
incident = {"exposed": True, "old_access_disabled": False}
needs_owner_action = incident["exposed"] and not incident["old_access_disabled"]
print(needs_owner_action)
```

It prints `True`. Deleting a local line alone would not make `old_access_disabled` true. The distinction is the important learning objective.

An **incident note** should record what kind of material was affected, where the exposure occurred, what containment was completed and what remains pending. It should not repeat the private value in the note. A placeholder description is enough to coordinate the response.

Keep permissions explicit. Discovering a problem does not authorize an exercise to change service credentials or rewrite repository history. Report the issue to the responsible owner with a concise description that does not reproduce the material.

For this course, all incident examples are synthetic. There is no requirement to search for private content, verify a real credential or contact an external service.

## 5. Separate project permission from service rules

**Authorization** means permission from the relevant authority for a specific action. Repository edit permission, account-owner permission and a service's rules are different things. One does not automatically replace the others.

Supercell's published terms restrict automation software, bots and emulators used to modify or interfere with its services. Its fair-play policy identifies gameplay automation and describes account penalties. These are reasons to treat live-account experiments as consequential, not as an automatic extension of a local coding lesson. See the [official terms](https://supercell.com/en/terms-of-service/) and [official fair-play policy](https://supercell.com/en/safe-and-fair-play/), checked for this lesson on 2026-10-29.

The course exercises remain offline: synthetic environments, named local public logs and in-memory calculations. They do not log into an account, drive the emulator or make network requests. This keeps the learning task distinct from an operational experiment.

```python
request = {"kind": "offline_analysis", "within_course": True}
allowed = request["kind"] == "offline_analysis" and request["within_course"]
print(allowed)
```

It prints `True`. A request labelled live operation would fail this toy course-scope check. The function is not a universal permission engine; it encodes the narrow exercise boundary.

A **risk review** asks what the action could affect and whether the right permissions and evidence exist. For a local aggregate report, the main concerns are input scope and correctness. For live account activity, execution behaviour and service restrictions become relevant too.

Do not assume that a research purpose creates an exception. If an exception is needed, it must come from the relevant authority and be explicit. Keep technical capability separate from permission: being able to automate an action does not establish that it is allowed.

## In the real project

The safe opening of `.gitignore` contains:

```text
# --- Virtual environments (huge; recreate from requirements.txt) ---
.venv/
venv/
env/
ENV/

# --- Python caches ---
__pycache__/
```

Line one explains the purpose of the following environment-directory patterns. Lines two through five list different conventional directory names. Line six is blank spacing. Line seven introduces cache rules, and line eight names Python's bytecode-cache directory.

This excerpt demonstrates generated-file hygiene. It does not prove that private material is absent from the repository, and it does not authorize inspecting other ignored paths. The text itself prints nothing.

No private file is needed for the lesson. The real project connection is the distinction between local/generated files and version-controlled source, together with the limits of what an ignore rule can accomplish.

## Practice plan

The first exercise selects only approved report fields from a synthetic record. The second checks an exact path allowlist without reading any file. The third models the tracked-file limitation of ignore rules. The final exercise returns a response category for a synthetic exposure.

Use deliberately unexpected input fields in your tests. A helper that copies every field except one known private field will fail when a new field appears. The allowlist solution should remain stable.

Finish with a short note separating three questions: Can the code perform an action? Does the task authorize it? Do the relevant service rules permit it? Keeping those questions distinct makes the course's offline boundaries understandable rather than merely ceremonial.

## Common mistakes

- Printing an entire configuration to debug one numerical field.
- Using real private material in a test fixture.
- Assuming an ignore rule removes tracked history.
- Treating deletion of a copy as revocation of access.
- Inferring service permission from repository or account ownership.
