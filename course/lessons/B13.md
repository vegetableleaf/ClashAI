# B13 · Reading other people's code

**Time:** about 4 hours · **You will be able to:** trace entry points, inputs, outputs, and state changes in unfamiliar ClashBot source without launching it.

## Why this matters for ClashBot

You will rarely understand a whole research repository before needing to answer a specific question. For ClashBot, that question might be how a match reaches a report or why a watcher marks a live process as stalled. A repeatable reading method lets you answer a bounded question without guessing about the rest.

This lesson examines `scratchpad/gauntlet/L74/crapi/crapi.py`, the battle-log poller source, and `scratchpad/gauntlet/L74/liveops/stuck_watch2.py`, the watcher source. We inspect selected functions as text. We do not run the poller or watcher, operate the phone emulator, or start a background process.

The same reading method will later help with RoyaleSim and crforge interfaces and with imitation-learning and reinforcement-learning loops. Follow the values first. A complicated filename or a model-related function name does not change the basic questions: what enters, what changes, what leaves, and what evidence supports that interpretation?

## 1. Begin with a bounded question

A **reading question** names one behaviour you want to explain. “Understand everything” has no useful stopping point. “What makes this classifier return its fallback label?” is small enough to answer from a function and its immediate inputs.

Before reading details, write down the question and the expected kind of answer. Are you looking for a returned value, a printed message, a file update, or a loop condition? This keeps a long file from pulling you into unrelated implementation details.

```python
def classify(reason):
    if "loading screen" in reason:
        return "loading_stuck"
    return "other"

print(classify("ready"))
```

It prints `other`. The question “what happens to unmatched reasons?” can be answered without understanding the rest of a live system. The final return provides the fallback after the earlier condition fails.

A **fallback** is the behaviour used when more specific cases do not apply. Fallbacks are important in logs because real messages may contain reasons the author did not anticipate. Do not confuse a generic label with evidence that no problem occurred.

## 2. Find the entry point, then trace inward

B08 introduced the entry guard. In an unfamiliar script, locate that guard and identify the function called from it. Then inspect that function's parameters and the values passed into them.

```python
def main(limit):
    return limit + 1

if __name__ == "__main__":
    print(main(2))
```

Run as a script, it prints `3`. The path is guard, call to `main`, return value, print. A longer real script may parse command-line flags between the guard and the call, but the direction of data flow is the same.

**Data flow** means the movement and transformation of values through a program. Trace one representative value through that flow. A polling interval begins as command-line text, becomes a float through argparse, then becomes an attribute read by the loop. This is more informative than memorising every import.

Entry points are not the only executable statements. Imports and other top-level operations can run before the guard. Reading source as text avoids those effects while you establish the structure. Never import an operational module merely to discover what functions it contains.

## 3. Make an input and output map

For each function, identify its parameters, returned value, and side effects. B08 defined side effects as changes beyond the returned value. Reading a file, printing, updating a collection passed by the caller, and launching a child process all deserve attention.

```python
def unseen(rows, seen):
    return [row for row in rows if row["file"] not in seen]

rows = [{"file":"a"}, {"file":"b"}]
print(unseen(rows, {"a"}))
print(rows)
```

It prints `[{'file': 'b'}]` and then the original two-row list. The function selects records into a new list. It does not save them or add their identifiers to `seen`. This separation helps you reason about the selection before discussing a later persistence operation.

**Persistence** means retaining data beyond the current process, usually in a file or database. A function returning new rows and a function appending those rows to a file have different responsibilities. Keeping those responsibilities distinct is useful even when a real script calls them in immediate succession.

Record assumptions as well as inputs. The toy function assumes every row has `file`. It also preserves input order. If a caller supplies duplicate unseen rows, both remain; filtering against an existing set does not automatically remove duplicates within the new batch.

## 4. Trace one normal case by hand

A **trace table** records variable values after each meaningful step. You do not need a special tool: a few rows on paper are enough. For a classifier, track the current rule, whether it matched, and the return value if it did.

```python
def classify(reason, rules):
    for substring, label in rules:
        if substring in reason:
            return label
    return "other"

rules = [("loading screen", "loading_stuck"), ("loading", "generic")]
print(classify("loading screen for 400 s", rules))
```

It prints `loading_stuck`. The first rule matches, so execution returns immediately. The second rule is never tested for this input. Reordering the rules could change the result because the broader word “loading” also appears in the message.

This is an example of **control flow**, the order in which statements execute. Data flow tells you which values move; control flow tells you which branches and calls are taken. You need both to explain why a particular label appears.

After the normal case, trace an unmatched case and a case matching more than one condition. Those examples expose fallback and priority behaviour. Reading only one happy path often leaves the most important assumptions invisible.

## 5. Follow state across repeated events

A **stateful** component remembers information between calls. B09's Unit remembered its health. A watcher remembers the most recent progress time and whether it has already reported an alert.

```python
def progress_times(lines, start):
    last = start
    for text, timestamp in lines:
        if text.startswith("[ladder] result: "):
            last = timestamp
    return last

events = [("[ladder] result: WIN", 20), ("loading", 99)]
print(progress_times(events, 0))
```

It prints `20`. A later unrelated message does not count as match progress. Tracking the latest log line and tracking the latest meaningful result are different behaviours. A watcher that confuses them may miss a stalled game while messages continue to arrive.

To trace this function, start `last` at zero. The first event changes it to twenty. The second event leaves it unchanged. The final return exposes the remembered meaningful time. This small table is often enough to understand the core of a much larger monitoring loop.

## 6. Distinguish source statements from current evidence

A comment describes an author's intention or observation. Executable statements define behaviour for given inputs. A runtime log records what happened in a particular execution. These are related sources, but they do not support identical claims.

If a docstring says a watcher is a proposal, do not call it deployed merely because the file exists. If a threshold appears in a constructor default, do not assume a particular process used that default. The caller may override it. If a loop can emit an alert, that does not show an alert actually occurred last night.

A **hypothesis** is an explanation that still needs evidence. For example, “the poller missed a period because it ran too infrequently” is a hypothesis until supported by timestamps and records. Reading a comment about a recommended interval tells you where to investigate, not what actually happened.

When writing your own annotation, use wording such as “this branch returns an empty list when...” or “this call passes the parsed interval into...”. These statements are tied to visible code. Save claims about production state or model improvement for evidence that can establish them.

## 7. Read unfamiliar syntax locally

Do not stop at every unfamiliar name. First ask whether it affects your reading question. A helper call can temporarily be treated as a box with named inputs and an output. Then open that helper if its details determine the answer.

For example, you can understand that a poller obtains rows, filters already-seen records, and appends the remainder before fully understanding how it builds a record identifier. However, you cannot claim its deduplication is correct without eventually checking that identifier's meaning.

A **type annotation** can help identify intended shapes. `reason: str` suggests text, while `tuple[str, str]` suggests a pair of strings. As B09 explained, annotations are not automatic proof that every runtime value has that shape. Compare them with how values are constructed and checked.

The exercises use string inspection for one source-reading task. This is intentionally limited. Counting lines that begin with `def ` is not a complete Python parser; it counts top-level definitions in the stated textual form. It does not discover every callable or decide whether a function is correct.

## In the real project

First inspect this exact tail of `poll_own` in `scratchpad/gauntlet/L74/crapi/crapi.py`, lines 243–247:

```python
    seen = load_seen(path)
    rows = [dict(fetched=now_iso(), battle=b) for b in reversed(api.get(f"/players/{q(tag)}/battlelog") or [])
            if battle_key(b) not in seen]
    append_jsonl(path, rows)
    return len(rows)
```

This excerpt is not a runnable exercise and prints nothing itself. Line 1 obtains identifiers already seen at the selected path. Line 2 asks an external-data interface for battle records, substitutes an empty list for a false-valued response, traverses the result in reverse, and builds dictionaries with a fetched timestamp and battle value. **Reversed traversal** visits a sequence from last to first.

Line 3 retains records whose computed identifier is not in the existing set. Line 4 passes the selected rows to the append helper, a persistence side effect. Line 5 returns the number selected. The identifier helper's name denotes a record identifier here. The excerpt does not establish that every possible duplicate within one returned batch is eliminated.

Next, inspect `classify` in `scratchpad/gauntlet/L74/liveops/stuck_watch2.py`, lines 52–56:

```python
def classify(why: str) -> tuple[str, str]:
    for sub, label, hint in CLASSES:
        if sub in why:
            return label, hint
    return "other", "read overnight.out"
```

It prints nothing; it returns data. Line 1 declares a text input and a two-string result. Line 2 unpacks each rule into its substring, label, and human hint. Line 3 checks the substring. Line 4 returns the first matching pair. Line 5 supplies the fallback after all rules fail. This is the same priority structure you traced in the toy classifier.

Finally, lines 79–81 of the watcher contain:

```python
        if PROGRESS_RE.match(line):
```

This excerpt prints nothing. Line 1 tests a **regular expression**, a text-matching pattern, for a progress event. Line 2 updates the remembered progress time and clears the no-progress alert flag. Line 3 returns no alerts for this event. Progress changes state even though it produces an empty output list.

## Common mistakes

- Reading a whole file linearly without a specific question.
- Importing an operational script just to inspect its names.
- Assuming an empty returned list means no internal state changed.
- Treating a comment or default as proof of current runtime behaviour.
- Ignoring rule order when several conditions can match.
- Claiming complete deduplication after inspecting only one membership check.
