# B07 · Errors, tracebacks and debugging

**Time:** about 4 hours · **You will be able to:** locate a failing statement, distinguish common error types, and handle expected bad input without hiding defects.

## Why this matters for ClashBot

An Icebow report can fail before it prints a single win rate. A match row may lack `derived`, a number may arrive as text, or an optional simulator dependency may be unavailable. Understanding the failure is more useful than changing unrelated code until the error disappears.

The live match summaries in `scratchpad/gauntlet/L74/loss_review/matches.jsonl` contain missing fields as well as completed records. The source file `scratchpad/gauntlet/L74/liveops/stuck_watch2.py` also handles imperfect log input. These are concrete reasons for learning error handling now.

ClashBot's later RoyaleSim and crforge experiments add more software layers. A dependency error during setup does not measure the quality of an imitation-learning model or a reinforcement-learning policy. First establish which operation failed. Only then interpret what the run tells you.

## 1. An error is information

An **exception** is Python's way of reporting that an operation could not finish normally. Unless some surrounding code handles it, execution stops and Python prints a **traceback**: a list of calls leading to the failure.

```python
row = {"n_plays":8}
print(row["derived"])
```

It prints no normal result. It ends with `KeyError: 'derived'`. A **KeyError** means a requested dictionary entry does not exist. This is not a claim that the whole dictionary is broken. The dictionary has `n_plays`; it simply does not have the requested field.

Treat the error name and message as a precise observation. “The code is broken” is too broad to guide a repair. “This lookup assumes every row has derived, but this row lacks it” identifies both the failed operation and the assumption to revisit.

## 2. Read the traceback from calls to cause

Consider two functions:

```python
def label(row):
    return row["derived"]

def describe(row):
    return "Outcome: " + label(row)

print(describe({}))
```

It prints no completed description. The traceback shows the outer call to `describe`, then its call to `label`, then the failing dictionary lookup, followed by `KeyError: 'derived'`. Exact temporary filenames and line numbers depend on the exercise runner.

A **call frame** is the information for one currently executing function call. Read the frames top to bottom to see how execution arrived there. Then inspect the final error line and the lowest relevant frame to locate the immediate cause. This combines the context of the caller with the concrete failing statement.

Do not assume the topmost line is where you should edit. A caller can pass valid data to a helper with an incorrect assumption. Equally, a helper can correctly reject data that its caller prepared badly. Trace the value across the boundary before deciding which assumption is wrong.

## 3. Recognise different failure categories

A **TypeError** means an operation received a kind of value it cannot use in that way. A string containing digits is still a string:

```python
plays = "8"
print(plays + 1)
```

It prints no total and raises `TypeError`, because this addition mixes text and an integer. Converting the text makes the intention explicit:

```python
plays = "8"
print(int(plays) + 1)
```

It prints `9`. The function `int` converts suitable numeric text into an integer. Conversion is not guaranteed to succeed:

```python
print(int("unknown"))
```

It prints no number and raises **ValueError**, meaning the kind of input is acceptable but its particular value is unsuitable. Here a string is allowed, but this string does not describe an integer. Replacing it with zero would erase the distinction between unknown and genuinely zero plays.

A **NameError** means Python cannot find the name you used. Misspelling `counts` as `count` is a typical cause. A **SyntaxError** means the program text cannot be parsed, for example because a closing parenthesis is missing. Syntax errors happen before ordinary execution reaches the intended statements.

## 4. Missing software is a separate problem

A **ModuleNotFoundError** means Python could not locate a requested module. A **module** is a unit of Python code that can be imported; B08 develops that idea. The message `No module named 'jpype'` refers to the Python bridge used when code communicates with Java, relevant to crforge.

That message alone does not prove that Java is unavailable, that a simulator rule is wrong, or that the learned bot has become weaker. It says this Python interpreter cannot locate that module. An **interpreter** is the program executing Python code. Different virtual environments can give different interpreters access to different installed packages.

Before changing anything, record which command and interpreter produced the traceback. The interactive exercises use the course environment. A project command may normally use another environment. Do not install software or launch a simulator as a guess during this lesson. You are learning to identify the failing layer, not repair every possible installation.

## 5. Handle an expected missing field

`try` introduces statements that may raise an exception. An `except` block says what to do for a particular exception type. The handler runs only if a matching exception occurs inside the `try` block.

```python
def get_label(row):
    try:
        return row["derived"]
    except KeyError:
        return "UNKNOWN"

print(get_label({}))
print(get_label({"derived":"WIN"}))
```

It prints `UNKNOWN` and `WIN`. We are deliberately defining missing-label behaviour. The function does not claim the row is a loss. It also does not catch every possible failure: passing a number instead of a dictionary is still a programming mistake worth seeing.

Keep the `try` block small. If you wrap file reading, decoding, counting, and formatting in one broad block, it becomes difficult to know which assumption failed. A narrow block ties the fallback to one understood operation. For ordinary optional dictionary fields, `get` from B06 is often simpler; the example teaches how exception handling works.

## 6. Account for malformed JSON

A **malformed** record is text that does not follow the required format. A process interrupted while writing can leave a partial last line. The JSON decoder reports that as `json.JSONDecodeError`. This exception is a specialised kind of `ValueError`.

```python
import json

lines = ['{"derived":"WIN"}', '{', '   ']
rows = []
bad = 0
for line in lines:
    if line.strip():
        try:
            rows.append(json.loads(line))
        except json.JSONDecodeError:
            bad += 1
print(len(rows), bad)
```

It prints `1 1`. There is one accepted row, one malformed nonblank line, and a blank line that is ignored. This policy is appropriate only when the report explicitly includes the malformed count. Silently skipping records would make a smaller denominator look complete.

Another defensible policy is to stop on the first malformed line and report its location. P02 uses a strict loader rather than silently continuing. Neither policy turns an invalid record into a valid match. The important point is to choose an explicit meaning and expose missing evidence.

## 7. Debug with small observations

**Debugging** means finding and correcting the cause of unwanted behaviour. A simple method is to print the values immediately before a suspicious operation. Start with a small example you understand instead of the entire match log.

```python
row = {"n_plays":"8"}
value = row["n_plays"]
print("value:", value)
print("type:", type(value))
print("converted:", int(value))
```

It prints `value: 8`, `type: <class 'str'>`, and `converted: 8`. The first line alone hides the difference between text and a number. Printing the type reveals the important fact. A **minimal example** is the smallest input that still demonstrates the issue.

Use a repeatable debugging loop. State what you expected. Record what actually happened. Identify the smallest input that shows the difference. Change one relevant statement. Run the small example again, then check another input that should still work. This is the beginning of the testing discipline developed in B12.

Temporary print statements are useful during investigation, but remove them from a final report function whose output has a defined format. Otherwise debugging text can be mistaken for data or make an output check fail.

## 8. Assert an assumption

An **assertion** checks that a condition is true. If false, it raises `AssertionError`. Add a message explaining the expected behaviour, not merely repeating “failed”.

```python
def spend(elixir, cost):
    assert 0 <= elixir <= 10, "elixir must be between 0 and 10"
    assert cost >= 0, "cost cannot be negative"
    assert cost <= elixir, "cost exceeds available elixir"
    return elixir - cost

print(spend(10, 6))
```

It prints `4`. An attempted `spend(3, 6)` would raise `AssertionError: cost exceeds available elixir`. This checks a simplified exercise model, not every timing rule in the game. In particular, it does not simulate future regeneration or a pending play.

Assertions are valuable for learning and tests. They are not a replacement for normal production validation because Python can run with assertions disabled. For a public function that must reject invalid input under every execution mode, explicit checks that raise `ValueError` are more suitable.

## In the real project

The syllabus lists no required file for B07. We use the real watcher at `scratchpad/gauntlet/L74/liveops/stuck_watch2.py`, lines 123–127, as a short error-handling example:

```python
            data = f.read()
    except OSError:
        return [], pos
    end = data.rfind(b"\n") + 1
    return data[:end].decode("utf-8", "replace").splitlines(), pos + end
```

This excerpt prints nothing; it is part of a function. Line 1 reads from an already opened file. Line 2 catches **OSError**, an exception family for operating-system operations such as file access. Line 3 returns no new lines and preserves `pos`, the reading position, on that path.

Line 4 finds the last complete newline. The `b` prefix marks **bytes**, raw stored values rather than decoded text; you only need to recognise that distinction here. Line 5 decodes the complete prefix, splits it into lines, and advances the position by the number of consumed bytes. An incomplete final line remains for a later read. That is more precise than treating any available characters as a complete event.

The watcher is operational source, so we inspect it as text. Its existence and error handling do not establish that it is currently running. Its opening description calls it a proposal. Keep source behaviour, runtime status, and match performance as separate claims.

## Common mistakes

- Reading only the first traceback frame and missing the failing operation.
- Catching every exception and returning zero, which hides missing evidence.
- Fixing a TypeError without checking whether the conversion is meaningful.
- Treating a missing dependency as a model-quality result.
- Using assertions as the only permanent validation for external input.
