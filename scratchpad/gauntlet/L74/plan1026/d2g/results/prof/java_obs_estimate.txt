Estimate
  kept on the Python thread with the Java obs: policy forward + crforge step + apply + decide + queue wait
    = 67.2 of 79.1 sample-% -> removable = 15.0% of actor_main (upper) ; 6.4% if the IW press observe
    (ability_commands, 8.6%) has to stay in Python (lower).
  crforge update CPU = 15,466 x 0.926 (python thread) x (1 - removed) + 15,466 x 0.074 (JVM threads) + 0.049 x 256
    upper removal: 13,345 core-s -> 1.07x fin16 ; lower removal: 14,568 -> 1.17x fin16   (gate 1.15x)
  So the Java obs alone brings the update to about 1.07-1.17x: inside the gate only if the IW press observe moves to the
  Java side too. Two facade costs are independent of it: unit_types_json/digest recomputed on every call (3.5% of
  actor_main; caching it is a one-line class of fix) and the C2 compiler thread (6.8% of actor CPU; C1-only removes it
  but slows the engine code by as much, measured 1.25x).
  Caveat: the 1.24x is at 18 actors on 20 logical CPUs; at 4 uncontended actors the main thread is 0.99x and the JVM
  threads add ~7%, so the gap grows with contention (shared-core / cache effects, b). The saturated test (24 actors on
  16 CPUs) died in the pod-33308 crash and was not re-run.
