Square One: imitate, search, distil, then learn live

A replacement for the sim → PPO pipeline, built from six research files and this week's measurements. The short version: the policy never saw the board, the reward never carried a signal, and the environment never matched the game. The new pipeline fixes those three in that order and grades every stage before the next one is allowed to start.

3 · The pipeline

Five stages. Each ends in a pre-registered gate on fixed instruments; a stage that fails its gate is reported as a null and the next one does not start. The order is the order the causes were measured in: representation, then data, then a learning signal that can improve on the data, then the live game.

STAGE 0 · week 1

Contract & instruments

One observation builder (entity list + raster) for engine state and detector output, contract-tested on recorded live frames. Corpus rebuilt from all 613 x/y replays through the engine, every phase kept, mask validated. Engine-vs-live fidelity numbers. Scripted opponent ported into the engine. Eval harness fixed.

GATE mask forbids <0.5% of pro cells · detector→obs vs engine→obs agreement reported · board-blind control per split
STAGE 1 · weeks 1–2

Imitation v3

New net: entity tokens + spatial patch tokens with coordinates, full-resolution per-cell head (no 12×8 upsample, no tanh cap), card head, supervised state-conditioned gate, categorical value head, past-actions channels, mirror augmentation, "wait for this card" action. Outcome-weighted BC as the one ablation.

GATE train top-1 > 17.6 · val top-1 > 15.44 + band, 3 seeds · embedding cosine spread ≫ 0.991 · engine winrate vs fixed opponents ≥ old init at n = 500
STAGE 2 · weeks 2–4, parallel

Corpus ×3 → ×10

Crawler restored, every positioned replay converted. Then the detector as an inverse-dynamics model: measure placement-recovery precision/recall on engine ground truth, label pro video, add to the corpus. Two-point data-scaling fit decides whether to keep going.

GATE IDM precision/recall measured · val top-1 rises with corpus size on the fixed val set
STAGE 3 · weeks 3–6

Search teacher, DAgger student

At states the student visits in the engine: Gumbel-top-k over its top 8–16 (card, cell) proposals + wait, each scored by re-driving the deterministic prefix and rolling out ~15 s (Supercell's oracle value). The improved target is aggregated with the pro corpus and the student is updated by supervised learning — no policy gradient, no critic warm-up, no rails.

GATE searched target agrees with pros ≥ student on 500 pro states · teacher beats frozen student ≥ 60% (n = 500) · distilled student > student on winrate and agreement, 3 seeds
STAGE 4 · week 5+

Live layer

Deploy through the shared obs builder, sampled gate, EMA weights, trained act period. Live learning: a critic trained from engine rollouts + live matches reranks the proposer's top-k (Best-of-Q / IBRL); every live match is re-driven in the engine from detected plays so the search teacher can improve the student on the states it actually met live. The owner grades here.

GATE live protocol: fixed mode, N-match blocks, EMA checkpoint, detector obs · winrate and plays/match vs the stage-1 and stage-3 checkpoints

Stages 1 and 2 run on the box; stage 3's teacher is the one engine-heavy step and scales with emulator count (§6). Stage 4 is the only stage that touches the live path, and only after stage 3 has a checkpoint worth playing.

Stage 3 in one paragraph, because it is the new idea

The old pipeline asked a sparse win/loss signal to improve a policy through a policy gradient, and measured that it cannot at this scale. The new one asks the engine to improve the policy directly: for a given board, try the policy's own best few candidates, let the deterministic engine play each forward a few seconds, and keep the one that leaves the board better. That improved choice is guaranteed to be at least as good as the policy's own under the value used, so the student learns from a teacher that is strictly better than itself — Supercell's escape from the same ceiling (Boney et al. 2020: 71.4 ± 8.8% vs their production BC). Querying the teacher on the student's own states, not the pro's, is the DAgger half; Supercell measured plain BC-of-the-oracle at 17.4% vs DAgger's 23.3% wins on the same oracle. The engine has no snapshot op, so branching means re-driving the prefix — deterministic (211/211) and ~0.4–3 s per branch — which is why this is feasible now and was not before the engine existed.

5 · How each stage is graded

Fixed val sets
The v2 engine-board val (1,333 rows, 33 replays) stays as the cross-pipeline anchor; the rebuilt corpus gets its own by-replay split with a board-blind control per split (12.08 / 37.66 on v2 val).
Agreement
Top-1 / top-5 pro-cell agreement, always with plays/match under the sampled gate rule beside it. Exact-cell agreement is a smoke test (Supercell shipped at ~4% per-frame), not the objective.
Engine winrate
vs a fixed set of ghost-pool timelines (non-reactive) and vs the ported scripted bot (reactive), n = 500 per arm, crowns and match length reported. This is the "worse than a scripted bot" claim made measurable.
Seeds
3 paired seeds per arm before any design decision; byte-identical launch check between arms.
Live
Fixed mode, N-match blocks per checkpoint, EMA weights, detector observations; winrate, plays/match, elixir-at-play histogram vs pros. Owner's grade has the final say.
Health
Logit saturation, policy entropy, gate p vs target, embedding spread — logged every checkpoint, alert bands set from a measured frozen-checkpoint run, _latest.pt written every N updates.

7 · What could still stall — stated before we start

  • b The truncated-rollout value may be wrong. "Let the engine run 15 s with no more deploys" is Supercell's oracle value and it worked with 256 arms per decision; ours starts at 8–16. The stage-3 gate "searched target agrees with pros ≥ student" is the pre-registered check that search moves toward good play at all.
  • b The engine may not match the live game closely enough. 77.7% crowns-match is an outcome number; no transition-level engine-vs-live number exists. Stage 0 produces one before any engine-trained checkpoint is graded live.
  • b The corpus may still be too small even at ×10. The scaling fit in stage 2 is how we find out early instead of late.
  • b Ghost opponents do not react. Winrate against them can be gamed; that is why the scripted bot is ported into the engine and why self-play against past checkpoints is added once stage 3 produces one.
  • a The live path has seams we already measured (opponent-elixir slot, hand-slot pixels, act period). Stage 0's contract test is the fix; nothing is graded live until it passes.
